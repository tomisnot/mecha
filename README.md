# mecha

**让 dsh 中的 AI 深度接入有状态、能自主执行任务的软件。**

mecha 是面向 dsh 的插件与软件接入框架，提取多个实际项目在接入 AI 时的共同需求：软件启动与连接、能力接口、长任务衔接，以及按需使用的状态与操作记录机制。AI 部分复用 dsh 和 Codex 等成熟宿主，领域能力由各个软件提供。

人通过 AI 提出意图、调整操作、推进工作；软件维护自己的状态，执行具体任务，并通过自己的界面呈现结果。**AI 是助手，是人的外骨骼；人驾驶这套 AI 机甲去干活。** 这也是 mecha 名字的由来。

## 软件接入 AI，与 skill 获得状态

mecha 从两个方向解决同一个问题：

- **从软件出发**：如何让寄宿在 dsh 中的 AI，更方便地深入操作一个已有状态、业务规则和执行能力的软件？
- **从 dsh 出发**：如何获得功能更强大的 skill，让其背后的程序自行维护状态、执行任务，供 AI 跨多次调用持续使用？

两条路径收敛于同一种形态：**skill 提供使用知识，工具接口提供操作能力，软件承担状态与执行责任。** 对 dsh 用户而言，这是带有软件后端的 skill；对项目开发者而言，这是软件的 AI 接入面。

状态可以是实验配置、训练记录、论文库，也可以是正在执行的任务及其进度。它们属于软件，独立于某一次对话。AI 无需靠上下文记住全部事实，也无需用一轮轮推理亲自推进程序已经能完成的流程。软件可以按请求执行，也可以运行自己的自动化；具体方式由项目决定。

当前的接入形态由 Python 运行机制、MCP 聚合端点和 dsh 插件共同组成，通过统一启动器完成装配。mecha 减少重复接线；把领域能力设计成真正好用的接口，仍然是项目开发的一部分。

## 深度接入意味着能够操作软件

实际工作通常围绕已有状态持续进行：读取当前情况，修改需要变化的部分，执行一步，观察结果，再决定下一步。

以数字化实验室为例，人可能这样指挥 AI：

> 保留其余设置，把这一通道的脉冲推迟一点。先单独检查采集，再跑一轮；读回实际参数，把信号变化展示出来。

AI 应能通过接口操作组件、增量修改配置、执行局部流程和读取结果。完整配置提交适合准备好的一次运行；调试还需要更细的操作粒度，包括较低层的设备能力和可组合动作。这些接口直接表达软件的对象与操作，无需让 AI 模拟点击 GUI。

**调试是实验室的日常工作。** 因此，接入设计既要覆盖正常流程，也要支持分步执行、诊断和反复调整。软件负责参数约束、状态一致性和实际执行；需要毫秒级响应的采集与控制由相应程序或设备完成。AI 根据人的意图组织操作、分析反馈，人持续判断方向和结果。

数字化实验室是 mecha 希望支持的应用方向。具体设备接口、实时控制、互锁和实验可视化由实验室项目实现；当前 mecha 提供的是软件与 AI 协作的公共机制。

## 已经在使用的项目

mecha 的公共部分来自实际项目的共同需求。这些项目独立维护自己的领域实现，也各自发展出了适合工作的观察与交互方式。

| 项目 | 软件负责什么 | 人如何观察工作 |
|---|---|---|
| [Energy Level](https://github.com/tomisnot/energy-level) | 里德堡原子与多体物理仿真、配置、后台计算和运行结果 | 运行卡片、原子阵列、关联与演化可视化 |
| [ML Toolbox](https://github.com/tomisnot/ml-toolbox) | 数据与处理管道、方法试验、训练、任务排队和结果存档 | 方法检视页、指标对比、训练曲线与 TensorBoard |
| [PaperPilot](https://github.com/tomisnot/get-paper) | 论文台账、扫描记录、兴趣画像和草稿 | 论文工作台、关系图、画像池和业务仪表盘 |

它们共享的是接入与运行机制。物理模型、训练策略、论文组织方式，以及怎样把结果呈现给人，都属于各自的软件。

## mecha 提供什么

| 公共机制 | 作用 |
|---|---|
| 软件启动与连接 | 按站点声明启动多个项目，管理进程、发现端点、处理重连与工具表变化 |
| AI 能力接入 | 声明查询、命令和工具，经 MCP 聚合给宿主调用；业务实现留在项目中 |
| 宿主适配 | 接入 dsh 插件与宿主服务，也支持 Codex；复用宿主的 AI 运行能力 |
| 长任务衔接 | 提供任务状态、等待、取消与结果引用接口；按项目声明对接宿主，dsh 可通过后台任务桥跟踪执行 |
| 软件侧基础组件 | 提供装配、操作关联、事件记录、产物托管、写权与基础只读监控等可组合机制 |

**软件负责自己的事实，项目决定怎样让人看懂它。** 操作记录可以帮助追溯，但理解一场实验、一次训练或一份推荐，需要领域数据和相应视图。mecha 提供基础记录与接线，项目建设自己的可视化和工作界面。

写权和审批按场景使用。有人机独占需求的软件可以切换写权；PaperPilot 默认人与 AI 共享写权。人的控制体现在提出目标、观察结果、调整方向和介入具体任务，也可以由项目提供相应的权限策略。

软件状态、进程存活、AI 连接和写权是不同的事情。软件侧的状态与业务能力独立于 AI 宿主；更换宿主不改变项目的领域模型。任务并发、持久化与恢复策略由项目负责。

## 安装与启动

当前采用源码安装。需要 Python 3.10+；整站 AI 接入使用 MCP 可选依赖。使用 dsh 时，需先安装并配置 dsh，确保其命令在 PATH 中可用。

```bash
git clone https://github.com/tomisnot/mecha.git
cd mecha
python -m pip install -e ".[mcp]"
```

接着按所选项目的说明安装其领域依赖。如果项目声明了 dsh 插件构建产物，还需准备对应资产；使用本仓共享面板源码时，在 mecha 仓根执行 `npm install`，并按项目说明安装、构建其插件。各项目使用独立 Python 环境时，应在相应环境中安装兼容版本的 mecha。

项目通过 `mecha_site.py` 声明软件入口、数据根、就绪条件和交互面。将下面的路径替换为实际检出的项目目录：

```bash
# 打开项目选择与启动页，默认使用 dsh
python -m mecha --root ../energy-level

# 直接启动多个项目，共享 AI 宿主
python -m mecha --all --root ../energy-level --root ../ml-toolbox

# 只查看启动计划
python -m mecha --dry-run --all --root ../energy-level
```

`--root` 可重复指定，`--all` 跳过项目选择页。启动器按声明启动软件、建立聚合端点并装配 dsh 插件与连接。控制台可查看服务状态与运行输出；实验结果、训练曲线等在项目自己的界面中查看。

### Codex 与无宿主模式

软件侧的机制也可用于其他入口。当前还提供 Codex 适配：

```bash
python -m mecha --ai-host codex --root ../energy-level
python -m mecha --ai-host none --root ../energy-level
```

Codex 模式需要可用的 `codex` 命令及本地登录凭据，由 mecha 托管 `codex app-server` 并提供本地 Web 界面。它使用 `_mecha_runtime/codex-home/` 下的隔离配置，复制本地登录凭据并按需继承传输设置，不复制用户会话。工具表变化后需要重连 Codex MCP 客户端。具体实现与验证范围见 [Codex 接入说明](docs/codex-host-support-plan.md)。

`--ai-host none` 只启动软件、聚合端点和控制台。`--ai-host` 决定初始选择，控制台可以切换宿主；`--no-browser` 关闭 mecha 控制台和托管宿主界面的自动打开，项目自身页面的启动行为由项目配置决定。

## 接入自己的软件

接入的起点是软件已有的状态与业务能力。项目需要明确：

1. **状态与执行**：数据存在哪里、由谁维护，任务怎样执行、停止和恢复。
2. **操作接口**：AI 能读取哪些事实、修改哪些对象、组合哪些动作；按实际工作选择完整提交、增量操作或更低层的诊断接口。
3. **反馈与呈现**：调用返回什么，怎样查询任务和结果，人通过什么界面理解与介入工作。
4. **宿主接线**：把能力接到工具面，以站点声明交给 mecha 启动和聚合，并提供项目的使用说明或 skill。

具体接入步骤见 [接入指南](docs/接入指南.md)，框架 API 与责任边界见 [开发者指南](docs/开发者指南.md) 和 [服务说明](docs/服务说明.md)。也可以只使用所需的库组件；Python 核心使用标准库，不要求安装 AI 宿主。

当前默认本地 Jobs 的任务表保存在进程内，默认产物定位符也仅在当前存储实例内有效。需要跨重启查询任务或恢复工作时，项目应提供持久的业务记录与结果引用。mecha 不提供通用的实时调度或业务恢复保证。

## 开发与验证

```bash
python checks/run_all.py
python checks/run_all.py --only authority
python checks/run_all.py --suite integration
python checks/run_all.py --all
```

默认运行核心契约；集成、面板资产、真实项目和发布扫描分开选择。按改动影响选择验证范围，外部项目缺失会明确显示 SKIP。各套件的依赖与运行方式见 [验证说明](checks/README.md)。
