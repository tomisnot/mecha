# ADR：按需要保存架构决策

ADR 用来保存重要取舍及理由，帮助后来者理解系统。它是沟通工具，不是每次开发的手续。
2026-10-13 起取消固定章节、固定标题和验证章节的机器门禁；旧记录保留历史语境，不据其恢复已退役规则。

## 什么时候写

状态所有权、公共契约、依赖边界或部署方式发生重大变化，而且提交说明不足以交代时，写一份简短记录。
一般 bug 修复、重命名、补注释、测试调整不必单独写 ADR。

## 怎么写

说清问题、决定、主要理由与代价。只有确实考虑过的替代方案才写；无需为了凑章节发明备选。
验证证据有帮助时可以附上，但不强制统一章节或为文档另造 check。
文件名可以沿用 `YYYY-MM-DD-短名.md`，已有四态目录继续用于检索：

- `proposed/`：未定案。
- `implemented/`：当时已经采用的决定。
- `rejected/`：当时未采用的方案及理由。
- `archived/`：已被取代的历史材料。

重要决定变更时交代前后关系即可。保留有价值的历史理由，不要求完整继承每一段散文或另设豁免清单。
当前设计与历史记录冲突时，以当前用户要求和有效设计为准；相关文档随改动同步。

## 验证与文档的关系

软件是否正确要靠架构约束和适当的结构、结果验证。文档有某个标题、日期一致、写了“已验证”，都不能代替这些证据。
不再运行 ADR 格式、每模块局限说明、散文计数门禁，也不将一般写作建议升级成门禁。
