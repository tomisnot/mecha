# 写权模式的 UI 面：Authority.watch 通知缝 + 双端切换按钮

> **状态**：implemented
> **作者**：mecha v2（兑现 `EL能力面取舍` 与 phase5 接线 ADR 里"接 GUI 模式按钮时
> 需写 ADR"的预留）
> **日期**：2026-09-24

## Problem

mode（HUMAN/AI/LOCKED）是协调态、刻意**不落 History**（authority.py 声明：它不是
域状态）。后果：UI 想实时反映"此刻谁能写"，**没有任何可订阅的来源**——史订阅收不到
mode 变更。于是出现了实测到的脱节：人工控制端点（:8767）切了模式，GUI 侧边栏与控件
只读态**不会跟着变**；用户要求"GUI 和 web 各有一个按钮切到对面模式、前端对应打开
关闭"，以及"启动弹窗要说清模式从哪开始"——这三件事全部卡在同一个缺口上：**mode 没
有通知机制**。

## Decision

1. **库侧加 `Authority.watch(callback) → disposer`**：每次**真变化**（新 mode ≠
   旧 mode）在 `switch_mode` 的调用线程上同步回调；坏订阅者抛错被吞（与
   `History.subscribe` 同纪律）；同模式重复切换幂等不通知（UI 不吃重复刷新）。
   `switch_mode` 顺带获得幂等语义（原来重复切会白改一遍状态，无副作用但无意义）。
   V2Bridge 转发为 `watch_mode(cb)`（回调收 mode 字符串，适配器层抹掉 Mode 枚举）。
2. **消费面归宿主，库不 import UI**：Qt 编组（信号回主线程）在 EL 的
   `monitor_panel` 做；HTTP 轮询在端点页做。库只保证"变更会通知到订阅者"。
3. **通知不补发**：订阅者起步先读一次 `mode` 再挂 watch（协调态允许瞬时滞后，
   以读为准）。不为此建"最后状态缓存"——那是第二个真值。

## Consequences

换来：GUI 控制卡与网页控制台都能实时反映模式；AI 模式下 GUI 控件物理只读
（`set_readonly` 从此有真实调用方，不再是"声明了没人接"的死机制——P2/D2 的账）；
mode 变更路径仍只有一条（authority 拒非 human 侧），两个按钮只是同一效果的两个入口。
付出：Authority 多一个进程内订阅列表（崩溃即失，与 mode 本身同生死，无持久化负担）；
`switch_mode` 从"赋值"变成"赋值+通知"，测试面加 F2 组（真变化才通知/幂等/退订/
坏订阅者四条）。

## Alternatives considered

**否决：mode 落 History（当作域状态记事件）。** mode 是操作者协调态不是域状态；
落史 ⇒ GUI 的每次接管都往权威史里掺非键值事件，fold 快照被污染（`field.B_gauss`
的"现值"和 mode 混在一张表里），且"AI 写了什么"的审计面被稀释。这正是当初
"mode 不落史"决策的理由，不因 UI 需求翻案。
**否决：UI 轮询 bridge.mode 拿实时性。** 判据里 poll 间隔要么短到浪费（100ms 级
轮询一个几乎不变的值），要么长到"按了按钮两三秒没反应"——用轮询绕开"没有通知缝"
这个真缺口，是把架构债转嫁成运行时浪费。轮询只留给网页控制台（它没有事件通道，
2s 一次的状态行是展示刷新，不是正确性依赖）。
**否决：把驾驶舱面板塞回 dsh 插件当"web 按钮"。** 人类控制权依附 dsh 进程，违背
"软件不依附 dsh"（总纲 §1.2 事实 3）；且 dsh 的 client 半刚随 v1 退役。网页控制台
挂在人工控制端点上：token 鉴权、服务端钉 actor=human、dsh 不在也能用。
