# Phase 1 定主权：门在执行器上 + actor 由通道钉死 + 史独立于 dsh

> **状态**：implemented
> **作者**：mecha v2
> **日期**：2026-09-23

## Problem

v1 的两条洞（总纲 §9）：dsh 部署里出现两套写权门、AI 可绕过 seam 直写/直跑。
审计实测（D-6）：`.mecha` 焊死在 resolve_root，数据布局没有注入通道。
判据缺口：没有一条"构造绕过必须红"的致死性测试。

## Decision

- `Gate.set` 四步顺序钉死：`authority.gate(actor)` → `validate` → **落到执行器**
  （快照是 Gate 私有属性，只读投影返回副本）→ `History.append`。
- `Channel` 是 frozen dataclass，actor 构造时钉死且只接受 `human`/`ai`；
  `switch_mode` 只接受 human 通道（AI 不能给自己解锁）。
- History 的 `LogSink` 是注入的 Protocol；`JsonlLogSink` 为 local 出厂默认，
  路径来自 `resolve_data_dir(root, dir_name)`——不给目录名当场报错（D-6 销号）。
- 每次 set 带 `call_id` 落进事件（互引半边；dsh 侧接线归 Phase 5）。
- 写权出厂 `LOCKED`（nothing ships enabled 用在写权上）。
- 判据：`checks/phase1_assembly_selfcheck.py` + `checks/assembly_endtoend_selfcheck.py`
  （洞1/洞2 构造绕过必须红 + L7 对偶不误报 + 重启独立重建）。

## Consequences

换来：一套门、一份真值、可归因、dsh 缺席全照常（端到端判据实测）。
付出：宿主必须显式装配（注入目录名、开闸），没有"跑起来就能写"的默认便利。

## Alternatives considered

**否决：门做在包装层 / schema 省略敏感键。** 见 rejected/门做在包装层。
**否决：actor 作为 set 的字符串参数。** 请求内容可伪造；通道对象钉死是唯一
  能机械验证的形态（判据：`Channel("admin")` 构造即红）。
**否决：History 直接绑 dsh session log。** 违反"软件不依附 dsh"（rejected/绑定-dsh-session-envelope）。
