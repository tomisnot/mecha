# 硬件互锁（interlock）：从框架退役，归属修正到 Provider 层（A-1 拍板）

> **状态**：implemented
> **作者**：mecha v2（回应《待办-代替v1六件事》附录 A-1）
> **日期**：2026-09-23

## Problem

v1 有 `mecha/interlock.py`，自述是"硬件档强制层——L3 不可逆动作的最后一道闸；
铁律二：不可逆动作过『人 + 硬件互锁』双闸，且**互锁不能是软件/AI 策略**（限值
在固件/硬件层强制）"。v2 全库 `git grep -i interlock` → **0 命中**（本轮实测复核，
`*.py` 里连字符串提及都没有）。

审查 A-1 问：这是"故意退役"还是"遗漏"？若是前者该写 ADR，若是后者该登记。
一条**写下来的铁律**在 v2 无对应件，沉默是最贵的（§9 反模式）。

## Decision

**故意退役，且这不只是退役——是归属修正：硬件互锁从来就不该在 mecha 框架层。**

1. **人闸这一半：v2 已覆盖。** `Authority` 出厂 `LOCKED` + 只能由 human-side
   开闸（`switch_mode(mode, side="human")`）就是"人 + 硬件双闸"里的**人闸**，
   而且比 v1 更强——开闸动作本身进 append-only 史、可归因（谁在何时放开了写权）。

2. **硬件闸这一半：归属 Provider，不进框架。** 铁律二自己说"互锁不能是软件/AI
   策略，限值在固件/硬件层强制"。mecha 是**操作者无关的软件层**——它实现不了
   固件限值，也不该假装能。v1 把 `interlock` 放进库，恰恰违背了它自己那条铁律
   （软件层里的"硬件互锁"只能是软件策略，是假的），也违背总纲硬纪律"边界写机制
   不写分类"（库不该内置"互锁"这个领域概念）。

3. **对 EL 不阻塞（本轮确认）**：EL 是纯仿真，无可互锁的硬件。v2 的 EL Provider
   不需要任何 interlock 对应件。

4. **真硬件项目接入时怎么办**：硬件限值在**那个项目的 Provider** 里表达（它才
   知道限值在哪个固件/寄存器），框架侧通过既有的 `validate` 钩子（Gate 的写入门）
   拒掉超限写——**机制已存在，不缺件**。届时该 Provider 写自己的 ADR 记录限值来源。

## Consequences

换来：v2 框架里没有"假的硬件互锁"（软件冒充固件闸是最危险的假绿——它让人以为
有硬件保护其实没有）；铁律二的精神（真限值在硬件层）通过"Provider 拥有 + validate
强制"落地，归属正确。付出：v1 那份 `interlock.py` 的 `SimInterlock`（仿真自动放行）
在 v2 无对应——但仿真本来就不需要放行逻辑（没有硬件可拦），删之无损失。

## Alternatives considered

- **否决：v2 照搬 `interlock.py`（含 `HardwareInterlock`/`SimInterlock`）。**
  软件层里的 `HardwareInterlock` 是矛盾修辞——它拦不住任何真硬件超限，只提供
  虚假安全感。铁律二明令禁止"软件/AI 策略当互锁"，照搬即违令。
- **否决：登记为"待补的遗漏"。** 若当真有硬件项目要接，缺的不是一个库模块而是
  那个项目的固件接口——库补 `interlock.py` 也接不上任何真硬件。登记成遗漏会误导
  后人去写一个永远只能是假的模块。
- **否决：写进总纲而非本篇。** 总纲不记具体能力去留（那是 ADR 的活）；且"为什么
  框架里没有 interlock"是决策考古问题，正是 ADR 该回答的。
