# 边界问题：现在建机制，分类内容推迟到 n=2

> **状态**：implemented
> **作者**：mecha v2（制度源自总纲 §5.4 + 硬纪律 10）
> **日期**：2026-09-23

## Problem

"什么归框架、什么归项目"争了几个月不得解。只有一个消费方（EL）+ 一个部署（dsh）时，任何 core/seam/bundle 分类都是"1 个项目的形状"，定了就是又一次先验划界——v1 的手写血统标签正是这么漂移失效的（L8 付过两次账）。但完全不处理也不行：没有机制，下一轮又会退回手写清单。

## Decision

**分两类处置，混为一谈即重犯 v1 的错。**

**现在必须建的机制（三件，缺一即返工）**：

1. **角色声明**：每个 seam 在自己身上标 `role ∈ {definition, provider, consumer}`；Definition **允许**是具体服务而不是接口。拒收标准：出现"无角色标注的扩展点"。
2. **生成的 capability map**：`docs/capabilities.md` **由脚本从声明生成，不许手写**，内容 = 能力名 / 角色 / 有哪些 provider / 谁消费。拒收标准：该文件被手工编辑过 ⇒ 判据红。
3. **汇总就绪**：map 的字段格式必须能让第二个项目的能力表**直接并表**，且有一条判据验证"两个项目的 map 能 diff 出共有能力"。拒收标准：只能靠人读两份 map 找共同点。

**明确推迟、不在 v2 定的分类内容**（本 note 即为"不许沉默推迟"的登记）：

- 哪些 seam 该从单包拆出去；
- `queries` / `mcp_tools` / `hooks` 是否算独立 seam —— **v2 先按"Surface 的注册项"实现**，等第二个项目出现同类需求再升格；
- History / Spill / Approval 三家各自该不该有第三个 provider。

**重新考虑的统一条件**：出现第二个有据的消费方（n=2），或第一个明确说"我不要这个"的项目。

## Consequences

换来：边界问题不必再靠辩论解决；分类不会以"1 个项目的形状"被焊死；机制零运行时耦合、成本极小。

付出：`docs/capabilities.md` 与生成脚本、角色标注、并表判据都要我们自己维护；"推迟"意味着第二个项目接入前，拆包决策悬着。

放弃：现在就给出权威的能力归属表。

## Alternatives considered

**否决：现在就写死 core/seam/bundle 分类表。** n=1 的分类没有证据基础，等于把 EL 的形状第二次焊进"通用"（总纲 §5.4 表第二行）。

**否决：什么都不建，等 n=2 再说。** 到那时拿不出可机械汇总的证据，还是得靠人议——正是我们要摆脱的状态。§5.4 第三行"汇总装置"存在的理由就是它。

**否决：手写 `docs/capabilities.md` 再配一个"别改这文件"的口头约定。** 手写清单必然漂移（L8）。dsh 的原话依据：capability-seams 末行"服务从 Cordis 声明中发现；角色在 `scripts/gen-doc-graphs.ts` 中分类，并设有完整性守卫"——**分类是生成的，不是手写的**。

**否决：把推迟项留空不写 ADR。** 违反硬纪律 9/10；沉默推迟与静默拍定同罪。
