# 边界机制补三洞：运行时图接声明表、完整性守卫、真表并表

> **状态**：implemented
> **作者**：mecha v2（响应审查《边界机制三件交付落地.md》建议 1-4）
> **日期**：2026-09-24

## Problem

《审查-边界机制三件交付落地.md》实测（基线 3e86ec4）：三件边界机制（角色声明 /
生成 map / 汇总就绪）落地不均——

1. **缺口 B（最重）**：`bridge._assembled` 经 `assemble()` 建栈（D-33），但
   `serve_mcp → _build_gui_tools` 又 `Surface(engine)` **新建一个裸的**，丢弃装配点
   带 19 条角色的那份。实测：声明表 19 条 vs 运行时服务面 3 条。**角色声明描述的
   是一张运行时不存在的图**；map 忠实生成自这张假图；visibility 类"从角色表投影"
   的机制拿到空表。
2. **缺口 A**：守卫只验"已声明的合法"，**漏声明抓不到**——新加机制忘写
   `roles.register` 照样全绿。实测 `authority` 正漏在表外（它是脊椎件却不在 19 条里）。
3. **机制 3 只有形式**：并表判据拿**手写合成表**当"第二项目"，ADR 承诺的"真实 EL 表
   Phase 5 生成后复用同一 diff 函数"未兑现（EL 仓 grep `build_roles` = 0 命中）。
   判据绿只证明"能 diff 我自己写的表"。

## Decision

**补洞，不加新抽象。** dsh 原文（`2026-06-13-capability-seams.md`）钉死了方向：
归属分层靠**角色声明 + 生成的 map + 守卫**表达，物理拆包只在变化速率真分叉时做
（"Don't split preemptively"）。因此**否决**"抽 `mecha/adapters.py` 基类把 bridge
骨架升库"的方案（n=1 的预防性拆分）；`examples/energy_level/` 继续作为"参考实现 +
EL 消费配置"的双重身份，但**它的运行时图必须与声明表一致**，且第二项目接入时照
EL 的 map 生成方式出自己的表。

四处修复：

1. **1a 消双图**：`V2Bridge._assembled` 保存装配点的 `surface`（连同 roles）；
   `serve_mcp` 经 `_build_gui_tools(..., surface=self._surface)` 复用它——工具注册、
   QUERY 项、角色登记全落在**同一张运行时图**上。`surface` 参数可选（缺省仍自建），
   纯内存判据装配不受影响。
2. **1b 服务面 ⊇ 声明表守卫**：capability_map_selfcheck 新增断言——
   `assemble(ToyEngine)` 产出的 `sw.surface.roles` 必须包含 `build_roles()` 的**全部**
   (name, role) 条目。谁再"建了装配点又丢掉它的图"，当场红。
3. **完整性守卫（缺口 A）**：单一来源 = **import 图**，不手写清单（L8）——枚举
   `mecha/*.py` 的 AST import 关系，凡**被装配链（assembly/gate/history/surface/
   monitor/tools/authority/…）import 的机制模块**，其能力名必须在 `build_roles()`
   有条目；同时 `declare_roles` 补上实测漏网的 `authority`（DEFINITION）。违例用
   合成 import 图自测（守卫不哑）。
4. **真表并表（机制 3）**：EL 仓新增 `scripts/gen_capability_map.py`（schema-only
   引擎，不建 cache；复用 `mecha.assembly.build_roles(engine_name="ElEngine",
   project="energy-level")` + EL 自己的 QUERY/工具注册项），生成 `docs/capabilities.md`
   入库；mecha 判据的 `_el_project_entries()` 改**读 EL 真表**（合成表退役），
   并表 diff 函数原样复用——"两项目能并表"从声明变成实测。

## Consequences

换来：map 描述的就是运行时真相（19=19）；漏声明从"靠自觉"变成 import 图守卫；
并表被两个真实项目证明过一次（EL 真表 + 主表机械 diff）；D-33 的"装配单点"从
"调用了"补全为"用的就是它建的图"。
付出：`_build_gui_tools` 多一个可选参数；EL 仓多一个生成脚本 + 一份入库 map（与
mecha 侧同纪律：手改即红，判据比对生成结果）；完整性守卫是 import 图近似——纯
运行时注册（不经 import 的机制）不在其射程，诚实登记。
放弃：adapters.py 基类 / counter 示例（本轮不做 n=2 的物理预拆分；counter 若将来
真出现第二项目，作为 n=2 的触发物连同 seam 拆分一起评估——统一条件不变）。

## Alternatives considered

**否决：抽 `mecha/adapters.py`（OperatorBridge 基类 + to_mcp 投影升库）。** 这正是
dsh note 点名反对的预防性拆分：n=1 下"骨架 vs 领域"的拆包没有第二个变化速率作证；
且它把问题误诊为"归属没分层"，实为"分层机制没接通"——机制已在（roles/map/守卫），
缺的是运行时一致性。基类一旦入库就成了新的承重墙，反而制造"示例该不该用库基类"
的第二场争论。
**否决：把 `examples/` 整体搬进 `mecha/`。** 同上，且污染库边界（库不许 import 宿主
词；bridge 的 `_ACTOR_CHANNEL` 恰是宿主词表，该留在消费侧）。
**否决：只修 1a 不补守卫。** D-33 就是前车之鉴——"修了装配点、没守卫图一致性"，
半路漂回去无人知。
**否决：机制 3 维持合成表 + 文档注明"待 n=2"。** ADR 已承诺 Phase 5 出真表，承诺
不兑现就是懒推迟（硬纪律 9）；且真表生成成本极低（schema-only 引擎，秒级），没有
继续欠着的理由。
