# EL 领域实现搬回 EL 仓：examples/ 退役，"个性知识归所属项目"兑现

> **状态**：implemented
> **作者**：mecha v2（用户裁决 2026-09-24："个性知识应该集中于其所属项目中，
> 而不是我们这个通用框架"）
> **日期**：2026-09-24

## Problem

可观察事实：EL 生产代码 `src/v2_bind.py` 写 `from examples.energy_level.bridge
import V2Bridge`，实测解析到 `<mecha 仓>\examples\energy_level\bridge.py`
——**项目依赖框架的"示例"目录**。EL 的领域知识（物理引擎、工具清单、驱动换算、
GUI 适配器）住在通用框架仓里，违背框架自己的定位（"mecha = 人机同门"）与
dsh 的归属原则（个性知识归所属项目/插件，宿主只留通用件）。

历史原因诚实登记：Phase 5 建 `examples/energy_level/` 时定位是"参考实现"——
框架需要一处真消费方来打判据（洞1/洞2 的证伪面）。该职责如今已由三件边界机制
（角色声明 + 两仓真表 + 守卫）接管，"框架替项目保管领域代码"不再有必要，
反而制造了 import 方向的反例。

## Decision

1. **`examples/energy_level/` 五文件整体迁回 EL 仓，包名 `mecha_v2`**
   （engine.py / tools.py / bridge.py / hub.py / __init__.py），落 EL 根。
   包内 import 改相对（`from .engine import …`）；对库的依赖仍走 `mecha.*`。
2. **mecha 仓不留领域代码**：`examples/` 整目录删除。mecha 判据中真引擎面
   （phase5_el / phase5_bridge / phase5_hub）改从 `EL_ROOT` 路径注入 import
   （`sys.path.insert(0, str(EL_ROOT))` + `from mecha_v2.…`）——缺 EL 即红的
   纪律不变，只是 import 源从"框架内示例"换成"项目仓"。
3. **消费方真实性守卫（check_real_consumers）扫描根同步**：`mecha/` +
   `examples/` → `mecha/` + EL 仓（EL_ROOT 下非 checks 代码）。provider.log.local
   的证据符号 `assemble` 的真实引用现在在 EL 仓 `mecha_v2/bridge.py`——守卫
   跨仓 grep 才证明"库机制真有人用"，这比 grep 自己的 examples 更诚实。
4. **capability map 归属不变**：mecha 表 = 出厂声明（现在 provider 列的
   "energy-level" 字样保留——那是声明参数，不是代码位置）；EL 表由 EL 仓
   `scripts/gen_capability_map.py` 从 `mecha_v2` 生成。并表判据不动。
5. **EL 侧接线**：`src/v2_bind.py`、`checks/*`、`scripts/gen_capability_map.py`、
   `skills/energy-level/SKILL.md` 的 `examples.energy_level.*` 全部改
   `mecha_v2.*`。EL 判据跑动时 sys.path 已含 EL 根，零额外配置。

## Consequences

换来：import 方向与教义一致（项目→库，库不藏项目）；"给 EL 加一个 MCP 功能"
的全部触点收敛到 EL 一仓（mecha_v2/tools.py 注册 + 引擎方法 + 判据）；mecha 仓
瘦身成纯框架（库 + ToyEngine 判据 + 跨仓集成判据）。
付出：mecha 的三个 phase5 判据从"仓内直跑"变成"依赖 EL_ROOT 存在"（此前
hub/bridge 判据本就如此，现在 el 判据也显式化）；两仓耦合点从"共包"变"共路径
约定"（EL_ROOT 常量 + MECHA_EL_ROOT 环境变量，已有先例）。
放弃：examples/ 作为"n=2 抄的模板"的角色——模板职责移交 EL 真表 + 架构详解
§9（消费配置导览）；真出现第二项目时，它抄的是"EL 怎么用库"的公开面，不是
框架私藏的副本。

## Alternatives considered

**否决：只把 bridge 搬回、engine/tools 留作"官方示例"。** 半吊子——v2_bind 依赖
的是整条链（bridge→engine→tools），拆开搬则留下的半截仍被项目 import，方向
反例照旧。"官方示例"的价值已由真表与判据承担。
**否决：EL 仓复制一份、mecha 保留原样（fork 而非搬迁）。** 两份真值必漂——
正是本仓最恨的"两套账"（硬纪律：判据测装配，装配只有一处）。
**否决：包名沿用 `examples.energy_level` 放进 EL 仓。** 名字本身在宣告错误
归属（"这是示例"），且 EL 仓已有 src/ 结构，`mecha_v2` 明确"这是 EL 的 v2
接入层"。改名成本 = 一次全仓替换，值得。
**否决：等 n=2 出现再搬。** 反例每天都在（生产 import 路径），且搬动成本随
时间只增不减（判据/文档/SKILL 都在引用旧路径）；用户裁决已明确，非推迟项。
