# 命令面：治理闸前置 + 声明式 opt-in（查得住、也说得清）

> **状态**：implemented
> **作者**：mecha v2（第三个项目 n=3 证伪报告的发现 7 / 发现 8 与两项自审的落地）
> **日期**：2026-09-26

## Problem

1. **检查滞后于副作用**：`CommandRegistry.invoke` 里两条正交的写权闸**一条前置一条后置**——
   `scope` 在调 handler 之前（`commands.py:368`），而 authority 的 `gate.set` 住在 `_audit`
   里（`:406`，**回执契约判定之后**，因为"有副作用的命令哪怕回执不合契约也已经动过宿主状态
   ⇒ 必须留痕"）。后果：**副作用不在 Gate 里**的项目（域状态外置：外置库 / 外部 API）
   会出现「**改动已落地、只是审计失败**」= **静默越权**；老项目因为副作用本来就在 Gate 里
   而被掩盖。框架自己也矛盾——`scopes.py` 两处都写着"在任何副作用之前"。
2. **声明了治理、实际不拦**：`approval_required` 当年**只是声明**、不落到任何分派路径
   ⇒ 项目写了"这条命令需要人工批准"就**以为被保护**，而它**照跑不误**
   ⇒ **比没有这个字段更坏：制造虚假安全感**。
3. **归因会撒谎**：`_call_handler` 不把本次的 `Channel` 交给 handler ⇒ 多操作者**共享一张
   命令表**（AI 走 MCP、Web 走 human）时 handler 分不清"这单是谁交的" ⇒ 宿主闭包只好捕获
   装配期的 ai 通道 ⇒ **人类写被误归因为 ai**（静默错，比拒绝更坏）。

## Decision

1. **authority 检查前置**：`Gate` 新增 `check(channel)`，内容**就是 `set` 的第 1 步**
   （`authority.gate(side)`），且 **`set` 自己也调它** ⇒ 这套判定**只有一份**；
   `invoke` 在调 handler 之前对 `side_effect` 且有 gate/channel 的命令先 `check`。
   **留痕仍在原位**（`_audit` 一字未动）。
2. **`approval_required` 真的拦**：`invoke(..., approval=None)`；为真时在**任何副作用之前**
   要一次 one-shot 授权，**没接审批通道即拒绝**（fail closed，与 `LocalApproval` 同语义）。
3. **声明式 opt-in**：`CommandSpec.wants_channel`（显式字段）。声明后 handler 收到本次的
   `channel=`；**不声明 ⇒ 调用形状与从前一字不差**。**不做签名自省。**
4. **`parameters.required` 缺失与空都表示「无必填」**（对齐 JSON Schema）；要必填就
   **显式列出**。

## Consequences

**换来**：副作用外置的项目不再可能"改动已落地才报审计失败"；声明了审批就真的拦；
handler 能按本次通道正确归因（审计 actor 不再撒谎）。

**付出 / 放弃**：

- **放弃"留痕可以更早"**：留痕仍**晚于** handler（理由不变：有副作用且回执不合契约的命令
  也必须留痕）。本次只把**检查**提前，没动记录时序。
- **放弃隐式归因**：handler 想知道"谁调的"必须**多写一行声明**；不声明就仍然拿不到
  （**不猜**）。这是刻意的代价。
- **放弃对老写法的宽容**：见下面「迁移须知 1」（`required` 语义翻转，**本批唯一可能影响
  既有项目的语义变化**）。
- **放弃给 approval 做自动接线**：`assembly.Software.approval` 虽已存在，但 `invoke` 与
  `gate` 同款**由调用方注入**——自动接线会让没声明审批的命令也走一遍审批通道，
  属于**扩大行为面**。

### 迁移须知（两处行为变更，三个项目跟进照此）

1. **`required` 语义翻转**：老写法（有 `properties`、**没写** `required`）从"**全必填**"
   变成"**都不必填**" ⇒ **可能静默接受原本会被拒的调用**。
   ⇒ **要必填就显式列出 `required: [...]`**。
   （杀伤半径由主代理核实：EL **0 条**命令声明 ⇒ 不受影响；GP **不受影响**——它每条都写了
   `required`；ML **5 条**声明 ⇒ 由其自查。）
2. **`approval_required` 真的拦了**：声明 `approval_required=True` 的命令，**调用方必须注入
   `approval=`**（如 `Software.approval`）；**不注入即拒绝**（fail closed）。
   ⇒ 反向也成立：**其实不需要审批的命令请去掉这个声明**（别留一个不干活的声明）。
   （杀伤半径：四个仓**无一处**真的声明 `True`。）

⚠ **别去"统一"两处 `required`**：`parameters.required` **缺失/空 = 无必填**（对齐 JSON
Schema），而 `output_schema.required` **必须非空**（回执契约显式化，消 D-15）。
它们**看起来一样，但不是一处** —— 合并任何一方都会把另一方的语义搞坏。
（与它同类的判断：`phase6` 里"宿主 validator 拒审计键 ⇒ `command_audit_denied`"那处
**是对的、必须保留**，不要因为"看起来像旧形状"就一起改。）

## Alternatives considered

**否决：新增"副作用登记 / 回滚"机制**（要求项目把副作用搬回 Gate 内）。
域状态外置是**合法设计**；要求它搬进 Gate 等于让框架规定宿主的存储形态（越界，L5）。
⇒ 正解是**把已有的检查挪到干活之前**，不是给框架新接缝。

**否决：用签名自省（`inspect`）判断 handler 要不要 channel**。
本仓纪律是"**显式声明优先于魔法**"；自省会猜错被包装/装饰过的签名，而且**行为随签名
静默变化**。

**否决：把 `approval` 做成 `invoke` 的必填参数**。
那会改动**所有**调用点（含根本没声明审批的命令），把"要不要审批"从**命令声明面**挪到
**调用面**——声明面才是它的家。

**否决：保留 `required` 缺失时的"全必填"回退**（即现状）。
它与 JSON Schema 相反，且**"可以填"与"必须填"是两件事**：回退把 `properties` 从"可填"
变成"必填"，正是那条误读的根源。

## Required verification

- `python checks/run_all.py` **全绿**（22 项；含面板资产自测与类型检查那一关）。
- 本批的判据落点在 `checks/phase6_command_surface_selfcheck.py` 的三组：
  `check_required_semantics`（`required` 语义 + 严格性不变）、`check_approval_required`
  （拒绝 + **对偶：点头就放行** + 摇头 + 未声明不破坏）、`check_handler_sees_channel`
  （两通道共用一张表时归因正确 + **不破坏**对偶 + 构造期拒同名参数）。
  各组的"能红"证据复现方式写在判据注释里：**隔离调用那一组函数**（扰动过大时整轮
  跑不到目标组）。
- 人工复核的三条不变量：① `_audit` 语义未动（`command_audit_denied` 在"authority 过得去、
  宿主 validator 拒键"时**仍是**正确形状）；② 未用这些声明的命令行为一字不变；
  ③ `output_schema.required` 的"必须非空"**未动**（与 `parameters.required` 刻意不同）。
