# 「读 / 写 / 读+遥测」三档**不进框架**（声明面在项目侧）

> **状态**：implemented
> **作者**：mecha v2
> **日期**：2026-09-26

## Problem

某项目（GP）的一处能力**声明 `kind="read"`、实际却写了一条痕**（遥测式追加）。
表面看像"**框架缺一档**"：既然有 `read` 与 `write`，似乎该补一个"读 + 遥测"。

**核过之后不是**：那个 `kind` **不在框架里**。
* 框架侧只有 `EntryKind`（Surface **注册项的角色**：`QUERY`/`HOOK`/`CUSTOM_TYPE`，`mecha/surface.py`），
  与"读/写/遥测"**不是同一个轴**；工具面 `ToolDefinition` **根本没有 `kind` 字段**。
* 那个 `kind="read"` 是**项目自己的注册器字段**（`@reg.tool(name=…, kind="read")`）；
  ML/EL 今天**连这个概念都没有**（它们只用 `EntryKind.QUERY`）。

## Decision

**不进框架。** 三条理由：

1. **声明面在项目侧**：`read`/`write`/`read_telemetry` 是**项目对外**的表达；
   框架侧的 `EntryKind` 管的是"注册项角色"，两者不是一回事（**合并会把两个不相干的轴混在一起**）。
2. ⚠ **框架看不到项目的工具体**：**即使框架加一个声明位，也管不住"它偷偷写了"** ——
   那个声明位**唯一的消费者就是项目侧判据** ⇒ 等于把项目的声明面搬进框架，**却换不来任何机械能力**，
   只会**再造一处"声明了没人喂"**（正是这几天在治的病）。
3. **R1：今天只有一家有这需求**（n=1）⇒ 不预建。

⇒ 取而代之：**给一条项目侧判据的可照抄形状**（写进《接入指南》），
它**不需要任何框架改动**，且能直接抓住那处病灶。

## Consequences

**换来**：框架不被一个"只有一家需要"的概念污染；项目的声明面留在项目里（**谁声明、谁对账**）。

**付出 / 放弃**：

- ⚠ **放弃了"框架提供读/写/遥测这一档"** ⇒ 代价是**每个项目要自己判、自己钉**
  （没有框架级的统一档位与统一判据）。
- ⚠ **放弃了"用声明位换取机械能力"这个念头**：这条路上**声明与行为之间没有可机械闭合的环**
  （框架读不到工具体内部），所以"加档"只会**增加一处声明**，不会增加一处**检查**。
- **放弃把它做成 `EntryKind` 的新值**（两个轴不同；改它 = 污染"注册项角色"的语义）。

## Alternatives considered

**（b）框架加一个声明位（如 `ToolDefinition.writes_telemetry: bool = False`）——否决。**
见理由 2：它换不来机械能力，且按"声明必须被消费"那套守卫，它**必须点名消费者与判据**，
而唯一消费者是项目侧判据 ⇒ **纯搬运**。

**（c）等三家都冒出同类（"声明 read 却写痕"）再做——记下条件。**
⚠ **重新考虑的条件写清**：**当第二家（n=2）出现同类需求时**，
才在框架侧加档位，**且必须与"项目侧对账判据"同批落地**——
否则就是"**造一个新名字来掩盖同一处病**"（本仓明令不许）。

## Required verification

- `python checks/run_all.py` **全绿**（22 项）。本 ADR **不含框架代码改动** ⇒ 判据侧无新增；
  它记录的是**一个"不做"的判断**与**一条项目侧形状**。
- 该判断的可复核依据（都能被独立核）：
  ① `EntryKind` 的成员与消费者（`mecha/surface.py`、`providers/skills.py:47/58`）；
  ② `ToolDefinition` 无 `kind` 字段（`mecha/tools.py` 里的 `kind=` 全是错误 kind）；
  ③ 三家用法（ML/EL = `EntryKind.QUERY`；GP 的 `kind="read"` 在**它自己的**注册器里）。
- **项目侧形状**（《接入指南》里那四步）自带**双向验法**（把 `kind` 换一档 ⇒ 判据必须红），
  所以它落地时**不是哑判据**——⚠ 但它**由项目自己跑**，框架不代跑。
