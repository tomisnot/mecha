# Gate/History 的事务提交序与库内锁

> **状态**：proposed
> **作者**：主代理（响应接管报告 P0-1/P0-2/P0-3）
> **日期**：2026-09-24

## Problem

可观察事实（接管报告深研核实，代码对照确认）：

1. **sink 失败 ⇒ 内存/磁盘分叉**。`Gate.set` 先改 `_snapshot` 再 `history.append`；
   `History.append` 先改内存（`_seq += 1`、`_events.append`）再 `sink.append`。
   sink 抛错（磁盘满、租约被夺）时内存快照已变、journal 无此事件——重启折叠后
   "真值"变了，违反"History 是域状态唯一账本"的不变量。
2. **set_batch 不原子**。两阶段：先逐条 validate，再逐条落地。落地阶段每条独立
   走 `set` 路径，并发写可插在两条之间——批次语义（要么全成要么不动）只在单线程成立。
3. **库内无锁，宿主锁堵不住所有门**。EL 的 GUI 写路径持 `V2Bridge._lock`，但
   MCP 工具线程（`tools.py` 的 `_set`/`_set_drive`）直接 `gate.set(channel, ...)`
   不走该锁——同一 Gate 上两条写轨并发，快照与事件序可以交错。

受影响者：任何多通道部署（GUI+AI 同进程是默认形态，不是边角）。

## Decision

**尚未落地，待委托方裁决后实施**。方案（若批准，按此做）：

- Gate 内部持一把 `threading.RLock`；`set` / `set_batch` / `undo` 全程持锁——
  **锁在库内，不依赖宿主自觉**（硬纪律 1"门在执行器上"的并发版）。
- 提交序改为 **sink-first**：`History.append` 先 `sink.append` 成功、再改内存
  （`_seq`/`_events`）。sink 失败 ⇒ 内存原样，异常上抛，Gate 快照不动。
  无 sink 的纯内存 History（判据装配）行为不变。
- `set_batch` 在锁内完成"validate 全部 → append 全部 → 改快照全部"，事件序连续，
  中途不释放锁——真原子（单进程内）。

## Consequences

- 换来：三条 P0 消除；多通道并发的写序有单一串行点；sink 失败不再产生
  "内存说写了、磁盘说没写"的分叉。
- 付出：单进程全局锁（写是低频操作，秒级演化才是热点，不碰此锁——性能代价可忽略）；
  sink-first 让"磁盘已写、内存未改"成为失败路径上的中间态——但 jsonl 追加失败
  即未写，写完即成功，无半态，可接受。
- 放弃：跨进程写协调（写租约已保证单写者，不重做）；分布式语义（不在框架射程）。

## Alternatives considered

- **维持宿主层锁（现状）**：否决——已被证伪。GUI 持锁、MCP 旁路，两轨并发是
  代码事实不是理论风险；宿主堵不住库内的门。
- **WAL/两阶段提交**：否决——为单进程 jsonl 账本上 WAL 是过度设计（n=1 纪律）；
  sink-first 顺序调换已消除分叉窗口。
- **不修，并入五边界迁移（提案 M0-M9 的 ExecutionLog/事务层重做）**：部分否决——
  迁移裁决未定且周期长；这三条是当下默认部署（GUI+AI 同进程）的真实缺陷，
  修复在"走迁移"与"维持现状"两种裁决下都不白做（迁移后锁与提交序不变量照样要）。
- **History 改事件溯源全重放**：否决——fold 已是纯函数重放，问题只在提交序与
  串行点，不在读路径；不借修 bug 之名做架构翻新。
