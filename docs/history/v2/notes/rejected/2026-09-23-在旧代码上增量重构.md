# 否决：在 v1 旧代码上增量重构，而非从零重写

> **状态**：rejected — 要动的 84% 里 ops/session/bus/server 互为因果，旧代码会锚定新形状
> **作者**：mecha v2
> **日期**：2026-09-23

## Problem

v2 是重写还是改造？改造省初始工量，但 v1 的形状会持续拉扯新架构。

## Decision

**禁止**在 v1 代码上改，**从零重写**。依据（总纲 §2.3）：要动的 84% 里 `ops`/`session`/`bus`/`server` 互为因果（改 session 快照语义连带 ops 产物、server 回执）；31 方法的 `EngineProtocol` 是沉积物，逐个瘦身反复撞"某个旧消费者"；新对话没有旧代码锚定，会按总纲长而非按 v1 长。

## Consequences

换来：架构不被旧形状绑架。付出：放弃 v1 已跑通的机制代码，重写工量前置。

**重新考虑条件**：若从零重写导致 Phase 1-4 任一阶段反复回归、且根因确认为"缺少 v1 的某个已验证边界处理"，可局部引入 v1 的**测试用例**（不是实现）作为判据来源。

## Alternatives considered

**否决：原地重构。** 见上，互为因果 + 锚定效应。
**否决：先冻结 v1 再并行写 v2 后切换。** 双份维护期会诱导"把 v1 的洞抄过来"，违背 §11"Phase 5 才允许打开 EL 项目"的顺序纪律。
