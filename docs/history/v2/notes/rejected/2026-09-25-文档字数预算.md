# 拒绝：文档字数预算与预算门禁

> **状态**：rejected — 那是给 266 包 monorepo 的规模控制，不适用于单包框架
> **作者**：mecha v2（M 提案，主代理裁决拒绝）
> **日期**：2026-09-25

## Problem

DSH 用一套**字数预算当门禁**治理文档规模：`scripts/doc-budgets.manifest.json` 给每份常备
文档设天花板，`pnpm run verify-doc-budgets` 对**超标或漏登记**都报错；红了的规定动作是
relocate → condense → raise（**顺序不可颠倒**），并附两条硬细则——"**ceiling 是护栏，不是
压缩目标**"（低于目标时留 ≥5% 余量）、"**天花板太低是预算 bug，不是文档超标**"。
（出处 `docs/AGENTS.md:48-58`；转述见 [`外部实践研究/DSH-对本轮悬案的答案.md`](../../外部实践研究/DSH-对本轮悬案的答案.md) §3.3。）

**诱因**：用户要求"框架代码要整洁，别堆屎山"，于是"把'别堆屎山'做成门禁"看起来像是同一句话的机械版。

## Decision

**不引入字数预算，也不引入预算门禁。**

## Consequences

**换来**：框架不必维护一份"哪份文档允许多少字"的 manifest；不必在每次正常扩写文档时先做一轮
relocate/condense 的仪式；不引入一个**只能测长度、测不出价值**的门禁。

**付出/放弃**：放弃"文档膨胀被机械拦住"这个**能力位**。**替代**是文档纪律 **D3 的 slop 清单当
人工审查表**（见 [`框架准入线.md`](../框架准入线.md) §6）——它抓的是"腐烂的具体形态"（重复的规则、
历史放错层、段墙、强调通胀），**不是行数**。**主动删掉该说的话**（例如为了压行数合并两条规则）
比超字数更坏，而门禁分不清这两者。

## Alternatives considered

**否决：照搬 DSH 的预算表与门禁。** 那套数字服务于 **266 个包的 monorepo**（每包一个 README、
总文档量以十万行计）。mecha 是**单包 + 三份主文档 + 一棵 ADR 树**，规模差两个数量级 ⇒ 这是
**为不存在的规模问题建机制**（违反 R1：没有具名消费者）。

**否决：只给根文档设软上限 + 人工复核（不做门禁）。** 比全盘照搬轻，但它仍然假定"**行数**是这里的
主要失效模式"——而本工程实测的文档失效模式**全是"内容撒谎"而不是"内容太长"**：手抄清单漏列
（`__all__`）、`spill` 删除后仍在 `README` 仓库地图里多躺一轮、接管报告给一份未裁决草案上位权威。
**守错了量。** 若将来真出现"某文档长到没人读"，那也该先有那件事的实例再立规则（R/D 系列都只收踩过的）。

**否决：把预算写成"建议值"放进文档。** 文档里的建议值没人执行，且会随文档增长**静默过期**（L8：文档不写会漂的数字）。

**重新考虑条件**：**出现"某份常备文档长到实际妨碍阅读或维护"的实例**（例如有人明确因长度而漏读
某一节并因此出错），**或本仓从单包变成多包**（出现第二个随包发布的包）时，重开此案；届时**先做
分层 relocate（D1）**，而不是引入字数门禁。
