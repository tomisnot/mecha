# 框架准入线：设计判断与适量验证

本文件是改动 mecha 时的工作指导。工程建议按当前风险使用，不自动产生文档、登记表或 check 的义务。
2026-10-13 起采用本版；过去的 R/D 编号可在 Git 历史中查到其案例，代码注释里的编号不构成额外门禁。

## 1. 先解决错误产生的结构

- 新机制需要真实用途；定义、实现和消费者的关系应能解释清楚（原 R1/R4）。审查用途不靠 grep import 代替。
- 优先单一状态所有者、单一事实来源、受控写入口、类型与构造期校验。
- 同一规则让多个项目复制时，先考虑共享实现或声明派生；不要先给每份副本加守卫。
- 迁移结束后删除重复路径、过渡测试和过期说明（原 R2）。历史 bug 不自动成为永久限制。
- 库的通用性由依赖方向和实际接入检验；同名命令、示例词汇或某个数字本身不证明领域耦合。

## 2. 选合适的判据

结构性判据验证关键架构性质，例如同一数据根的写者互斥、装配共用状态、人机写入口受同一治理。
它应允许等价实现；检查特定 import、文件名或源码字符串，通常只是实现痕迹。

结果性判据验证调用后的可观察承诺，例如失败仍是失败、重启能恢复、原始记录可归因、计算结果正确。
纯逻辑适合单元或性质测试，装配和跨进程边界适合集成测试；没有“所有测试都必须测装配”的规定。

一条测试应有可信的期望和确实到达目标路径的输入（原 R3/R8/R9/R10/R11/R12）。
正反输入有助于检验边界，但不要求每条测试额外建立突变体、红证脚本或“测试的测试”。
只在拒绝规则复杂、影响重大且普通案例不足时使用故障注入；失败要与目标缺陷有关。

新增、修改、删除测试都按它保住的承诺判断。没有价值的测试可以直接删除，不必另加守卫禁止其文件或符号回来（原 R13）。
删除机制后检查当前消费者与引用；按受影响范围搜索和验证，不把每次修改变成全仓扫描（原 R14）。

## 3. 按范围运行

`checks/run_all.py` 默认核心契约；集成、面板资产、真实项目与发布扫描分别选择。
运行方式见 [checks/README.md](../../checks/README.md)。本地迭代运行受影响项，跨层改动和交付前扩大范围。
缺环境要明确区分未验证与失败。SKIP 不冒充 PASS，也不要求无关改动准备所有外部仓库。

## 4. 文档按需要写

记录设计理由、公共用法和真实限制。简单模块不强制局限章节；文档不靠标题、措辞或计数黑名单衡量质量。
重大取舍可用 [ADR](ADR制度.md) 保存；一般修复与机械重构可以由提交说明交代。
文档与实现一起维护即可，不要求先写 ADR、补验证章节、再改代码。
生成的能力表可按需刷新；注册表是来源，文档新鲜度不阻塞无关开发。

## 5. 保留的契约注意事项

MCP 参数类型、缺省值与 null 的语义要在模型实际收到的协议上核对（原 R5/R6）。
API 声明与执行不能互相矛盾；可注入项应真的影响结果，不使用的选项应删除（原 R17）。
这些是接口设计要求，是否新增测试取决于风险与现有覆盖，不是固定的测试配额。
