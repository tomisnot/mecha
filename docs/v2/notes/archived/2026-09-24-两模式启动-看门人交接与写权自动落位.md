# 两模式启动：看门人交接 + 写权自动落位

> **状态**：implemented
> **作者**：mecha v2（兑现用户裁决 2026-09-24"写权别搞复杂，就 AI/GUI 两模式，像启动页那样"）
> **日期**：2026-09-24

## Problem

三态写权 UI（人接管 / 交给 AI / 全员禁写）+ 双入口（GUI 侧边栏控制卡 + :8767 网页控制台）
上线后，用户反馈**心智负担过重**："不要搞得像现在这么复杂，机制在内部存在，然后分两个模式，
AI 和 GUI，就像启动页面那样。"

具体症状（可观察）：
1. 用户分不清"启动模式（AI/GUI）"与"写权模式（HUMAN/AI/LOCKED）"是两维——UI 把两维
   揉成三个按钮摆在一起，每次都要解释。
2. AI 模式仍照起 GUI 窗口（`run_ai()` spawn `--gui`），"AI 在开、人在看"的界面语义模糊。
3. dsh 侧驾驶舱按钮随 v1 净化退役，AI 模式下人**没有顺手的地方看 AI 在干什么**（只能开
   GUI 侧边栏或 :8767 网页，两者都不是 AI 工作现场）。

## Decision

**用户面收两模式，写权自动落位；机制（三态 Authority + watch 缝）原样保留在库内。**

1. **两模式 = 两种进程编排**，由常驻**看门人**（EL `launcher.py`）唯一编排：
   - **GUI 模式**：纯本地软件（`app_entry --gui`，`start_services=False`）——不起 MCP 端点、
     不起监控端点，**AI 物理看不见这台软件**；写权恒 HUMAN。
   - **AI 模式**：headless 权威（`app_entry --authority`，不建 GUI 窗口）+ dsh 前台；写权
     自动落 AI；监控在 dsh 右侧栏面板。
2. **写权自动落位**：AI 模式权威装配出厂 HUMAN 后立即 `switch_mode(AI, actor='human')`。
   语义合法化：看门人**代理人的启动意图**开闸（人选了 AI 模式即授权 AI 写），**不是 AI 自解锁**
   ——护栏不变（AI 通道改不了 mode，靠 Authority 的 side 判定，见 `authority.py`）。
3. **切换经文件握手，进程交接归看门人**：任一进程写 `<EL根>/.mode-request`（内容 gui/ai），
   看门人轮询到 → `terminate` 当前进程组 → **等进程真退出**（journal 写租约随进程释放，否则
   新权威被 `writer_lease_held` 拒）→ 按新模式 spawn → 删请求文件。GUI 侧入口 = 文件菜单
   「切换至 AI 模式」；dsh 侧入口 = 「→ GUI」按钮经 `/re0-gui` command 让 host 写文件。
4. **监控端点降级为只读**：`:8767` 从"人工控制端点"（POST switch_mode/write + token）收缩为
   "只读监控面"（`GET /status` + `GET /activity?since_seq=`），供 dsh 面板轮询。控制权切换
   不再经它。加 CORS（浏览器 dsh 页跨源轮询，只读+回环，允许任意源不构成风险面）。

## Consequences

换来：用户面只剩"AI / GUI"一个选择，与启动弹窗同一心智；写权随模式自动落位，无"按了按钮
忘了切"的中间态；AI 模式下监控在 AI 工作现场（dsh 侧栏），人不用另开窗口。
付出：多一个常驻看门人进程（无窗口，日志进控制台）；进程交接引入 `.mode-request`/`.mode-state`
两个握手文件（.gitignore 已收）；GUI 模式与 AI 模式**互斥**（不能同时既要纯本地 GUI 又要 AI 在场
——这正是"完全断开"裁决的代价，换来 AI 看不见本地会话的干净保证）。
放弃：三态 UI 的"全员禁写"按钮（机制 Mode.LOCKED 保留，维护/排障经代码切，不再占用户面）；
:8767 网页控制台页面（`_CONTROL_HTML` 删，只留只读接口）；GUI 侧边栏 AI 监控面板
（`monitor_panel.py` 删——两模式下都没有它的存在场景：GUI 模式无 AI、AI 模式无 GUI）。

## Alternatives considered

**否决：保留三按钮，只把"全员禁写"藏进二级菜单。** 治标不治本——用户的核心抱怨是"启动模式"
与"写权模式"两维被揉在一起，减一个按钮仍是两维心智。收成一个选择（AI/GUI）才是对症。
**否决：GUI 模式留一条只读 AI 通道（AI 能看不能写）。** 切换更顺滑（不必重启交接），但违背
"GUI 模式 = 纯本地软件"的用户裁决，且"AI 物理看不见"这个干净保证值回那点顺滑——留通道就要
维护"只读 MCP 端点"的第三种装配态，复杂度回来了。
**否决：进程自接力（旧权威自己 spawn 新权威后退出，不建看门人）。** 少一个常驻件，但交接时序
（等租约释放再起新的）分散在两个会死的进程里，崩溃恢复路径翻倍；看门人把"等退出→再起"这个
最易翻车的时序集中到一处（launcher_selfcheck 的 D 组专测它）。
**否决：mode 落 History 让面板订阅史拿实时性。** 继承 `写权模式UI面-Authority通知缝` 的否决
理由——mode 是协调态非域状态，落史污染 fold 快照；面板实时性走 :8767 只读轮询（展示刷新，
非正确性依赖），仍不建"最后状态缓存"（那是第二个真值）。
