## 0. ⚠ 施工顺序的原则：先证伪，再铺开

这套架构有**两个可能致命的前提**，它们**必须先实测**。
若不成立，整个新架构要重新设计 ⇒ **先别让三家动代码**。

| # | 致命前提 | 不成立的后果 |
|---|---|---|
| **P1** | **软件进程能同时提供 MCP 服务与 PyQt 窗口**，且互不干扰 | 裁决 1（GUI 在进程内）**不成立** ⇒ 要退回"独立客户端" |
| **P2** | **写权切换"立刻生效"**：切到 HUMAN 后 **AI 的下一次写被拒**、人在同一进程里立刻能写 | 需求 4（可反复切）**做不到干净** |

⚠ P1 还带着**native×Qt 的雷** —— ⚠ **但每家不是同一条**（我早期把两家的混成一条，已更正）：

| 仓 | 那条雷 | 状态 |
|---|---|---|
| **EL** | **QThread 生命周期 / `0xc0000409`** | ⚠ 步骤 0 只覆盖 **offscreen + 单次演化** ⇒ **只对这一档量级成立**；真上长时/并行负载**要重测** |
| **ML** | **lightgbm 必须先于 PyQt5**，否则 OpenMP×Qt 冲突 ⇒ fit 时 access violation | ⚠ **未实测**（ML 还没做进程内开窗，见第 2.3 节） |

⇒ **步骤 0 = 只做 P1/P2 的实测**（EL 最合适：它已有 `for_shared`（人机同门装配）
与一个现成的 PyQt 主窗口）。**这一步不改功能代码**，只写一个验证脚本 + 判据。
✅ **已完成**（见 §0.0）。

| # | 判据 | 红证怎么造 | 状态 |

### ⚠⚠ 4.1 **删除类改动的收尾是「全仓搜残留」，不是「跑门禁」**（R14）
⚠ 框架准入线 **R14**（**踩过才写下的**）：
> 门禁只覆盖它**走到**的路径；漏改的引用可能躺在**没被判据走过的分支**里，**运行到才炸**。
> **实例**：删 `spill` 时漏了 `assembly.py` 的构造实参 `Software(..., spill=spill, ...)`
> ⇒ 会 `NameError`；**是"残引用 grep"抓到的，不是门禁** —— 当时 `run_all` **是绿的**。

⇒ **本次要搜的残留**（删 `manual` 是删除类改动）：

| 搜什么 | 为什么 |
|---|---|
| `manual`（框架 + 三家仓，**含 gitignore 的文件、不经 git**） | 三家声明已删，但**别处可能还有引用** |

| `Software(` / `software.py` | ⚠ **R14 的原始实例就是这个形状**（构造实参 `Software(...)`） |

⚠ 与 **R10** 是一对：**R10 讲"绿只覆盖走过的路径"，R14 讲"所以删除类改动不能拿绿当收尾"**。

⚠ **为什么两边都漏了**：

| 漏的原因 | 说明 |
|---|---|
| **只搜源码扩展名**（`.py/.ts/.tsx/.md`） | `lib/client.js` 是 **`.js`** ⇒ 不在搜索面里 |
| ⚠ **以为 `lib/` 是 gitignore 的产物 ⇒ 不重要** | ⛔ **错**：`dsh/.gitignore` 确实含 `lib/`（**不入库**），但 ⭐ **dsh 是 JS 进程，它运行时【真的读】 `client.js`** ⇒ 那句旧提示 **AI 实际会看到** |

⇒ ⭐ **规则**（R14 的补充）：**残留搜索必须覆盖"被 gitignore 的构建产物"**，
且**改了源码就要重建产物**（本仓：`dsh/` 下 `npm run bundle`）。
⚠ **判据就是"搜到 0 命中"**，不是"门禁绿了"。
⚠ 另：`python` 不读 JS ⇒ **用 python 写的搜索脚本看不到它**（我第一遍就是这么漏的）。
