# EL 消费配置的能力面取舍：undo / 存档 / gc 的决策与重新考虑条件

> **状态**：implemented
> **作者**：mecha v2（回应审查第三轮 §1.2③④ + 勘误 §4.1）
> **日期**：2026-09-23

## Problem

审查第三轮 §1.2 把"对外能力面缺口"分成四类，其中两类**缺 ADR 说明**：

- **③ 能力整体缺失、无 ADR**：v1 有 `list_archives`/`read_archive`（存档面）
  与 `gc`（数据回收），v2 顶层无 archives 模块、`gc_report` 是返回
  `{ok:false, note}` 的诚实 stub。"要不要保留这两面"这个决定本身没写下来。
- **④ 明确挂起、等 ADR**：`undo`（撤销）。EL `v2_bind.py` 自述"撤销要按反向
  set 记一条新事件实现，等接 GUI 撤销按钮时写 ADR"——但这是框架级能力、v1 有，
  挂起状态该有正式决策记录，不能只活在适配器注释里。

不写下来的后果：后人以为 v2"漏了"这些能力去补，或反过来以为"故意永不做"而无
从判断边界——两种都是 §9 反模式（沉默的决策最贵）。

## Decision

**三件各给一个明确处置，全部带可判定的重新考虑条件（硬纪律 9/10：推迟不许
沉默）：**

1. **存档面（`list_archives`/`read_archive`）：v2 不建独立 archives 模块——
   这是设计，不是遗漏。** 理由：v2 的 History 是 append-only JSONL journal，
   **它本身就是存档**（总纲 §5.2②：域状态史是软件自己的资产、可从盘续）。v1
   的 `archives` 是在 journal 之外又造一层"归档目录 + 检索"，与 `gc` 的
   `JOURNAL_ARCHIVE_DIR` 三处分散同病（D-9）。v2 要读历史 = 读 journal；要
   按时间点回看 = `History.since(seq)` 折叠。**再造一层 archives 是第二真值。**
   重新考虑条件：出现"journal 之外的异构存档"真实需求（如导出给第三方系统的
   不可变快照包），届时写 ADR 定义其格式与归属。

2. **`gc`（数据回收）：保留 stub 的诚实报错，实现推迟到 D-9（保留策略）。**
   v2 现状：`v2_bind.gc_report` 返回 `{ok:false, note:"未接 gc"}`，GUI 回收
   按钮显示"未接线"而非静默成功——**这点审查明确认可（诚实报错）**。真正缺的
   不是 gc 代码，是**保留策略**（哪些 journal/artifact 可删、删前归档到哪、
   保留多久）——那是 D-9，"等第二个项目"的 n=1 推迟。重新考虑条件：第二个
   项目接入且其保留策略与 EL 不同（n=2），或 EL 磁盘占用成为真实痛点。

3. **`undo`（撤销）：设计定为"反向 set 记一条新事件"，实现挂起至接 GUI 撤销
   按钮。** v2 History 是 append-only——撤销**不能**删事件（违反 L2），只能
   追加一条"把键改回前值"的新 set 事件。语义与 v1 的 `session.undo`（弹出式
   回滚）**不同**：v2 的"撤销"在史里看得见（谁在何时撤销了什么，可归因），
   这是 append-only 的必然推论，也是它比 v1 更强的地方。实现要回答"撤销哪一
   步"（按 seq？按 call_id？按键最近一次？）——这些是接 GUI 撤销按钮时的真实
   消费方逼出的问题，现在无调用方，不预建（§5.4 Require evidence）。重新考虑
   条件：GUI 撤销按钮接线（真实调用方出现），届时补 undo 的具体 API + 判据。

**工具面对等性随之澄清（勘误 §4.1）**：v2 暴露的工具清单以
`examples/energy_level/tools.py` 的注册为准（本轮补了
`submit_job`/`read_job`/`cancel_job`/`run_actions`），覆盖 v1 的对应功能
（`read_job` 有意折叠 v1 的 `job_status`+`list_jobs`——枚举是投影不是工具）。
真正未覆盖的正是本篇处置的 undo/archives/gc + 故意不建的 `get_activity`
（无订阅者）+ 改为固定工具的泛化 `query`（新查询经 `Surface.register` 暴露，
不新增工具）。

## Consequences

换来：§1.2 四类缺口的③④两类有了决策记录，后人能判断"这是设计还是遗漏"；
工具面对等性有准确数字（读出来的，不是数出来的——勘误 §6 教训）。付出：
undo 仍是"已决策未实现"，archives 的"不建"要在 EL 侧文档同步说明（否则 EL
用户找不到 v1 的存档按钮会困惑）。

## Alternatives considered

**否决：照 v1 补齐 archives + gc + undo 三个模块。** 违背 §5.4「Require
evidence for public choices」——undo 无调用方、archives 与 journal 重复、gc
缺保留策略输入；补齐 = 把 v1 的形状焊进 v2（正是总纲 §2.3"不在旧代码上改"
要避免的）。
**否决：把"不建 archives"写进总纲而非本篇。** 总纲是引导源、不记具体能力取舍
（那是 ADR 的活）；写进总纲会让它膨胀成能力清单（L8 同源问题）。
**否决：gc stub 直接删掉回收按钮。** 按钮是 GUI 已有能力入口，删它改变 UX；
保留 stub + 诚实报错是"能力在、实现待"的最小诚实态。
