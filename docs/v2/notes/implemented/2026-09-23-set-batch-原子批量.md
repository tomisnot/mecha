# 裁决：`set_batch` 原子批量（真实调用方 = GUI 存档恢复）

> **状态**：implemented
> **作者**：mecha v2
> **日期**：2026-09-23
> **取代**：`2026-09-23-set-many-裁决.md` 的"重新考虑条件"（本 note 兑现它，
> 继承其全部 rationale，不推翻其"零调用方就删"的裁决——那个裁决当时是对的）

## Problem

set-many-裁决说：删 `set_many`，等真实调用方接入再带证据重写。现在真实调用方
出现了——EL 的 GUI 存档恢复（`app_entry.load` 一次回填 34 个键）与 `push_all`
（同步一批面板值）。v1 的教训具体：20 份旧存档每份 34 键，`load` 在第一键抛就
一份都载不回，且**不留半加载中间态**——原子性在那个场景是救命的。

## Decision

新增 `Gate.set_batch(channel, items, reason, call_id)`，语义 = **先全校验，再
全落地**：

1. `authority.gate(actor)` 一次（整批同通道同写权）。
2. 阶段一：对每个 (key,value) 跑 validate，**不碰快照**；任一抛错 ⇒ 直接传播，
   快照与 History 一字节不动（不留半拉子）。
3. 阶段二：校验全过后，逐键落快照 + `History.append`，**整批共用一个 call_id**
   ⇒ History 里可识别"这一批本该一起"（set-many 审查方案 D 的内核，白捡）。

事件粒度不变：仍是逐键一条 `kind='set'`（不产生 `kind='set_batch'`——那是
D-27 教过的假 kind）。原子性是"要么全写要么全不写"，与"每键一条史"正交。

## Consequences

换来：存档恢复有原子口（v1 教训落地）；批量写可被 call_id 归成一批。付出：
validate 必须无副作用（当前契约如此，docstring 已声明）；两阶段循环比逐键 set
多一次遍历（批量小，可忽略）。

## Alternatives considered

**否决：逐键 set 拼一个 for 循环（不原子）。** 正是 set-many 审查批评的"半拉子
状态"；存档恢复场景会留下"34 键恢复了 12 个"的坏快照。
**否决：恢复旧名 `set_many` 且不原子。** 名字带"many"却无原子保证，会误导。
改名 `set_batch` + 原子语义，名字与保证一致。
**否决：加 `atomic=True/False` 旋钮（set-many 方案 C）。** 唯一真实调用方（存档
恢复）要的就是原子；无第二个要"不原子批量"的调用方 ⇒ 不建旋钮（§5.4 无据不建）。

**重新考虑条件**：出现"故意要逐键独立提交"的真实调用方（如流式导入，坏一条
跳一条继续），届时加显式非原子口并说明与 set_batch 的分工。
