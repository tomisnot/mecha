# 裁决：删除 `Gate.set_many`（零调用方，非原子性之争）

> **状态**：implemented
> **作者**：mecha v2（回应审查 P5-1 / proposed set-many-原子性）
> **日期**：2026-09-23

## Problem

审查提出 `set_many` 刻意不原子、与 v1 相反、且无 ADR，要求裁原子性（proposed
note 给了三问 + 四方案 A/B/C/D）。但裁决前必须先答 proposed 自己的**问 2**：
"谁需要原子性？列出真实调用方。**没有调用方就不抉择**（§5.4 Require evidence
for public choices）。"

实测：`grep set_many` 全仓**零调用方**（只有定义处 + 评审文档）。它和 v1 的
`result_meta`（D-19）是同一类——**签名存在、无人消费的公开口**。

## Decision

**删除 `Gate.set_many`。** 原子性之争是伪议题：一个没有调用方的批量口，讨论
它原子与否没有证据基础。按 ADR 保留死契约的裁决（rejected/保留死契约）执行。

逐条回答 proposed 的三问，作为删除的理由（不是回避）：

1. **不原子的收益？** 无。"每条 set 独立四步事务"是描述不是收益——proposed
   问 1 说得对。既然无收益也无调用方，删。
2. **谁需要原子性？** 当前无人。v1 的"20 份存档靠先全校验再全落地救过"是**真**
   需求，但那是**存档恢复**这个具体消费者——它尚未接入 v2。等它接入时带着真实
   调用方重写原子性 ADR（届时 v1 教训是现成的 evidence）。
3. **"合成单键值"成本推给谁？** 无人——因为没有调用方付这个成本。

**保留的不变式**：`set` 仍是唯一变更口（四步、门在执行器、validate 必填）。
批量语义将来若加，必须是"先全校验再逐键落地"的原子版（v1 教训），且带 batch_id
写进 History（proposed 方案 D 的合理内核）——但那是**接线时**的 ADR，不是现在。

## Consequences

换来：删一个无消费者的公开口，Surface/Gate 的公开面更诚实（每个口都有调用方）。
付出：若近期要接存档恢复，得重写一遍批量口（但那时才写得出有证据的原子性设计）。

## Alternatives considered

**否决 A（保持现状，逐键不原子）。** proposed 问 1 已指出"不原子的收益"答不出；
且现状的 docstring"需要原子性请合成单键值"把成本推给不存在的调用方。
**否决 B（恢复 v1 原子语义）。** 无调用方就实现原子 = 为假想需求建机制（§5.4
"Don't split preemptively"）；且 B 让 set_many 与 set 四步不同构，是新的复杂度。
**否决 C（atomic=True 旋钮）。** 默认值本身又要裁一次，且仍是无调用方的公开面。
**否决 D（batch_id 不救原子）。** 最小改动，但仍是给零调用方的口加特性。
四方案的共同盲区：都假设"set_many 该存在"。真正的裁决是先问有没有调用方——没有，就删。

**重新考虑条件**：存档恢复 / GUI 批量回填 / AI 一次多键写，任一真实调用方接入时，
带它重写原子性 ADR 并继承本 note + v1 的 20-存档教训。
