# 格式版本化与迁移制度（HISTORY_FORMAT_VERSION）

> **状态**：implemented
> **作者**：mecha v2（制度源自总纲 §6.4）
> **日期**：2026-09-23

## Problem

v1 把格式假设散落成字面量：`pickle protocol=4`、`'mecha-session-v1'` 串、`.mcp-port` 文件名、`MECHA_ROOT` 变量名（D-12），没有版本位、没有迁移边、没有"故意不支持什么"的清单。后果：格式一变，旧数据要么静默坏掉，要么报错点离病因很远。

## Decision

**必须**建立四件套制度，管辖一切持久化格式（History 日志、快照、归档、Provider 落盘）：

1. `HISTORY_FORMAT_VERSION`：每个持久格式带显式版本位；只有**结构性格式变化**才 bump 版本（抄 dsh 的语义，不抄它的事件集）。
2. **相邻边 Stage 迁移链**：迁移只声明 `vN → vN+1` 单步；读取时按构建时静态确定的相邻链组合，**旧版本既不隐含回退也不隐含降级支持**。
3. **released-format 政策**：已发布格式的磁盘产物**不许移动、覆盖、删除**；迁移在旁边排他发布新版本命名的后继。
4. **corpus 拒识清单**：按来源列出"故意不支持的历史转换 + 确切拒识原因"，作为判据语料。

本 note 立的是**制度**；机制接线随 Phase 1 History 实现落地，届时判据必须测装配（L6）。

## Consequences

换来：格式腐烂可归因、可迁移、拒识可测试。付出：每次格式变更多写一条迁移边 + 一条拒识登记。

## Alternatives considered

**否决：只加版本号、不建迁移链。** 版本号没有相邻边就是装饰品——旧数据照样读不出，只是报错更早。
**否决：直接抄 dsh 的 session envelope 与迁移实现。** 违反 §4.3"实现细节不当契约"与"session 存储只能观察"；我们抄制度形状，事件集是自己的。
**否决：等 Phase 1 有真实格式再立制度。** 制度先于格式，否则第一版格式会把偶然形状焊成"v1"。
