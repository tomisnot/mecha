# 通用命令面：命令是注册项，不是 Engine 的第 5 个必实现

> **状态**：implemented
> **作者**：mecha v2（响应第二宿主接入压力；衔接基调 §10.1「Command Surface 最高优先」）
> **日期**：2026-09-24

## Problem

**事实 1（现有结构塞不下多命令宿主，可观察）。** 今天的操作面只有两条分派路径：

- `Engine.run(spec, *, context, **opts)`：**一个**操作，吃一个不透明 `spec`、
  回一个不透明映射。它的回执契约只由 `schema()["run_output_required"]` 声明
  **一份**（`mecha/surface.py` 的 `Surface.run`）。
- `Surface.query(name, **args)`：只读动词分派，**不经写权门**（D-4 的解法）。

第一条路对一个"只有一种演化"的宿主够用；对"一次拟合 / 一次批量遍历 / 一次基准 /
一次调参 / 一次导出"，它只能靠**把命令名塞进 spec 字典**来复用：于是"哪个参数
必填""回执必含哪些键""这条命令有没有副作用"全部退回宿主散文与宿主判据——
使用者（AI 或 GUI）看不到逐命令契约。第二条路明确排除有副作用的命令。

**事实 2（把命令做成 Definition 会撞判据）。** `checks/phase2_surface_selfcheck.py`
钉死 `Engine.__abstractmethods__ ⊆ FRAMEWORK_CALLS`（`schema`/`run`/`summary`/
`estimate`）且**长度恰为 4**，理由写在 `surface.py` 的铁律里：*框架自己会调用的，
才配进 Definition；框架不调、只做分派目标的，必须是注册项*。命令是分派目标。
往 Definition 加 `register_command` / `invoke_command` 会被该判据当场判红，也会
重蹈 v1「13 必实现对没有运行的项目也全强制」的覆辙（消 D-13）与
`rejected/2026-09-23-具名-ABC-方法膨胀.md` 已否决的方向。

**事实 3（第二宿主的形状与第一宿主不同，这是压力而不是巧合）。** 现有真宿主只有
一条主操作；第二个真实宿主（多方法、多任务、含长跑与导出、含资源与审批语义的
工具箱）有几十个能力，且它们**不是同一个操作的参数变体**：只读清单、上下文写、
单次执行、批量、优化、导出，各自有不同输入、不同回执、不同副作用、不同审批需求。
硬塞进单操作 `spec` 的代价不是"不好看"，是**契约消失**：回执必填键无法逐命令声明，
只读与有副作用无法在机制上分开，审批与取消无处声明。

**受影响的是谁**：第二个宿主的 adapter 作者（要么复刻一套自己的分派+校验，要么
把领域形状写进 `Engine.run` 的 spec）；AI 操作者（看不到逐命令契约，只能试错）；
以及框架自己（"通用化"若靠反推第一宿主的工具表，得到的只是"第一宿主工具通用化"）。

## Decision

**新增 additve 的通用命令面 `mecha/commands.py`，只写机制、不写任何宿主的
命令名/状态键/指标名。** 具体决定：

1. **`CommandSpec`（frozen）= 命令声明契约**，字段恰为九项：`name`、
   `description`、`parameters`（JSON-schema 风格映射）、`output_schema`
   （**必须**含非空 `required`）、`side_effect: bool`、`scope: tuple[str, ...]`、
   `estimate_sec`（数或 callable）、`cancel_supported: bool`、
   `approval_required: bool`。**构造即校验**：坏名字、空描述、缺 `required`、
   非 bool 标志、坏估时一律当场拒（门在执行器上，同 `define_tool`）。
2. **`CommandRegistry`**：`register(spec, handler) → disposer`（可逆，同名重复
   注册拒），`invoke(name, args, *, context, gate=None, channel=None) → dict`
   （归一化回执：`is_error` / `value` / `error`，错误形状沿用 `MechaError` 并投影成
   `ToolFailure {message, info}`，与 `ToolRegistry.execute` 同构）。
   `specs()` 只出 frozen 声明，**handler 绝不外露**。
3. **接入点取最省的一处**：`Surface` 增一个 additive 的 `commands` 入口（与 QUERY
   注册项并列，共用装配点那张角色表），`assembly.Software` 增一个 `commands`
   字段且**就是 `surface.commands` 同一对象**（不是第二张注册表）。
   理由：Surface 已经持有注册项与角色表的唯一装配点，命令面是"另一条分派路径"
   而不是"另一个 seam"（分类留宿主）；`Software` 多一个取用入口让宿主只拿软件
   实例就能挂命令。**`Surface.run` / `query` / `schema` / `estimate` 语义一字未改，
   `Engine` 仍是 4 个必实现。**
4. **只读命令不得强制过 Gate**：`side_effect=False` 的 invoke 不碰 `gate` 参数
   （传了也不用、不写史）——D-4 同款，不存在"只读动词被判不可逆"。
5. **有副作用的命令经 Gate 写审计事件**：键 `command.<name>`，值只放操作语义
   （命令名 / ok / scope / 回执键 / 错误 kind），**不放结果体**（大对象归宿主的
   run store，History 只留引用）。副作用已发生但回执不合契约时**仍写审计并标
   `ok=False` + `error_kind`**（最该被审计的失败不许无痕）。声明了副作用却没注入
   gate ⇒ `missing_gate` fail loud（不允许无痕副作用）。
6. **参数契约默认严格**：缺必填键拒，多未声明键也拒（要放行须显式声明
   `additionalProperties: true`）；`reason` / `call_id` 是框架抽给 Gate 的调用
   元数据，默认不喂命令体。理由：静默吞参会把"拼错参数名"变成"命令悄悄少做一件事"。
7. **命名只守通用格式**：非空 snake_case、无项目前缀（`mecha_`）。**刻意不照搬**
   工具面的"动词_宾语、禁 `get_`/`list_`"那套——命令名不是模型可见工具名，
   单段名（`reset`）合法；更强的文体律属于 ToolHost 投影层，不属于核心。
8. **命令不自动投影成 AI 工具**：ToolHost 契约未定（衔接基调 §10.2），本轮只保证
   声明是 frozen、可投影的数据。

## Consequences

**换来**：多命令宿主有了归宿，且是**注册项**而非新的必实现——`phase2` 的 4 必实现
判据、`Engine.run` 语义、EL 侧行为全部原样；每条命令的参数/回执/副作用/审批/取消
成为**可机械校验的显式契约**（消 D-15 的隐式键，逐命令粒度）；命令的调用痕迹进
History 且可归因（actor + call_id + reason），进史事件只含操作语义；注册即投影、
dispose 即撤销（含 `command:<name>` 能力行，无幽灵条目）；`docs/capabilities.md`
多一行 `commands.registry`，`Software` 多一个字段且被完整性守卫自动覆盖。

**付出**：`Surface.__init__` 多构造一个注册表；`Software` 多一个字段（装配点唯一
具名组装处的纪律不变）；宿主 validator **必须接受 `command.` 前缀的审计键**，否则
有副作用命令的调用以 `command_audit_denied` fail loud——框架不替宿主放行，这是
刻意选的（宁可吵，不静默写未声明键）。审计键会进域快照的键空间（前缀隔离，不
与域键同名），需要"域快照纯净"的读面要按前缀过滤。

**放弃了什么**：放弃"用 `Engine.run` 的 spec 分派硬撑"（把契约推给宿主散文）；
放弃把命令面做成独立 seam（n=1 不预建分类，等 ToolHost/Command Map 真有第二个
消费压力）；放弃核心内置"哪些命令只读/危险"的判级表（那正是 D-4 治过的病）；
放弃命令名强制"动词_宾语"（那是工具面文体，不是通用格式）。

**接口缺口（与第二个宿主对接时要知道的）**：① 命令 → AI 工具的投影未实现
（ToolHost 契约未定）；② `scope` / `approval_required` / `cancel_supported` 目前
**只是声明**，Scope Authority 与 Job 契约落地前不参与分派——即"声明了审批需求
不会自动拦"。这两条是**诚实推迟**，触发事件分别是"ToolHost Provider 出现"与
"Scope Authority / Job 契约落地"。

## Alternatives considered

**否决：把命令做成 `Engine` 的新必实现（`register_command`/`invoke_command`）。**
撞 `phase2` 的"方法名 ⊆ 框架真会调的名单 + 长度恰为 4"判据，也撞
`rejected/2026-09-23-具名-ABC-方法膨胀.md` 与消 D-13 的裁决：命令是分派目标，
框架不主动调它。这条路的真实代价是**每个宿主被迫实现同一段注册骨架**，而骨架
形状已经稳定——正是"薄适配目标需要"（衔接基调条件 C）的反面教材。

**否决：沿用 `Engine.run`，命令名进 spec（`spec["command"] = ...`）。** 它保住了
零改动，但把三条契约降级成约定：逐命令参数必填、逐命令回执必填键、只读与有副作用
的区分。结果是机制层无法校验，只能靠宿主判据钉，而"使用者看不到契约"正是要治的病。
更糟的是它鼓励核心长出 `if command == ...` 的分支——把宿主形状写进核心。

**否决：只读命令也一律过 Gate（统一一条路）。** 这是 D-4 已经判过的病：写权门会
把只读动词判成不可逆操作，LOCKED 下连读都要开闸。判据里专门钉了"LOCKED 下只读
命令可调"这一条，反向证明该方案不可取。

**否决：框架内置命令分级表（哪些命令只读 / 危险 / 需审批）。** 领域分类不许进核心
（总纲 §5.4：分类内容 ❌ 不许定；"D-4：没有 op 名表判级"）。核心只提供
`side_effect` / `scope` / `approval_required` 这些**可由宿主填的槽**，不填内容。

**否决：让框架自动把命令投影成 AI 工具（`ToolRegistry` 里手抄一份命令名单）。**
手抄名单会漂（消 D-25 的教训）；且 ToolHost 是独立 seam（衔接基调 §10.2），
MCP/dsh 只是它的一个 Provider。从命令声明投影工具**是接缝处该做的事**，不是核心
自己长出来的——n=1 不建，触发事件写在上面的接口缺口里。

**否决：独立 `CommandSurface` seam（新 ABC + 新装配点）。** 命令面没有新的
Provider 种类，也没有新的生命周期；它就是一条分派路径。为它开 seam 会在
`build_roles` 与 capability map 里制造一个没有 provider 的空壳，且立刻要回答
"它和 Surface 谁先谁后"——过早拆包（衔接基调条件 A/B 都不满足）。
