# ToolHost 契约：工具定义与宿主传输分成两个 seam

> **状态**：implemented
> **作者**：ML×mecha 衔接（Lead）
> **日期**：2026-09-25

## Problem

`tools.py` 已经把"工具长什么形状"定得很死：命名律、`output.schema.required`
显式声明、`schemas()` 白名单投影、失败归一化成
`ToolFailure {message, info}`。但**定义**与**交付**是两件事，现状把两件事压在
同一个对象上，逼出三条可观察事实：

1. **宿主侧注册无处安放。** 总纲 §7 Phase 4 定"注册进 `ctx.tools`，不另起 MCP
   server"，`tools.py` 的 docstring 只能写"宿主注入时把 ToolDefinition 适配成
   defineTool 形状是 Phase 5 的接线工作"。于是每个宿主适配器（EL 的
   `build_tool_registry` / `to_mcp`、ML Toolbox 的工具面）都**各自手写一遍**
   "怎么把定义交出去、怎么把调用收回来"：交出去时抄哪些字段、收回来时怎么把
   宿主异常译成模型能读的失败。同一概念多个来源——v1 血统标签漂移的同款病。
2. **传输侧的失败没有归属。** `ToolRegistry.execute` 归一化的是**工具本体**
   的失败。可宿主句柄本身也会坏：MCP 回程丢字段、宿主 adapter 抛错、回执被
   中间层改成裸字符串。这些没有归属地，只能各自在适配器里裸抛——而裸抛正是
   "模型看见内部错误、拿不到可纠正信息"（L4 要消灭的那类失败）。
3. **"dsh 只是 Provider"目前是句承诺，不是结构。** 本包不 import dsh 已经有
   纪律背书（`__init__.py` docstring），但工具面没有可替换的传输 seam 时，
   "换宿主"实际等于"改适配器代码"，churn 会从 Provider 层漏回核心旁边
   （硬纪律 6 想要的是整层可替换）。

## Decision

新增 `mecha/toolhost.py`（additive，不动既有 Definition），把"宿主传输"定成
工具面旁边的一个 Provider seam：

1. **Definition**：`ToolHost` 只声明四个操作——
   `declare(schemas) -> None`、`call(name, args) -> Mapping`、
   `schemas() -> list[Mapping]`、`teardown() -> None`。定义是 Protocol
   （`runtime_checkable`），**不是 ABC**：宿主侧实现只需形状对齐，不需要继承
   我们任何基类。
2. **`declare` 的选择：拒收，不静默过滤。** 待声明的每一项必须是
   含 `name`/`description`/`parameters` 的映射，出现**白名单外字段**
   （`execute`/`output`/`render` 或任何别的东西）当场
   `MechaError(kind="bad_tool_declaration")`。理由见 Consequences 与
   Alternatives：安全上过滤与拒收等价（两者都不透传对象），差别在**事实是否
   被吞掉**——手工拼 schema 是"执行器/可调用对象差点泄进模型请求"的唯一来路，
   静默扔掉等于让这条路不留痕（L3：不要把可疑当正常）。
3. **`call` 归一化到底，不抛穿。** 未知工具 / 缺必填参数 / 回执缺必填键 /
   工具体意外异常沿用 `ToolRegistry.execute` 的既有投影；此外 ToolHost 自己
   兜三层：宿主句柄抛错 → `toolhost_error`；宿主回执不是映射 / `is_error`
   不是真布尔 / 错误支不是 `{message, info}` / 成功支缺 `value`/`content` →
   `bad_host_result`。**畸形结果绝不当成"值"透传**——那会把传输事故伪装成
   工具返回了一个奇怪的结果。
4. **`schemas()` 白名单是唯一名单来源。** 投影只出
   `name`/`description`/`parameters`（字段名与 `tools.MODEL_VISIBLE_FIELDS`
   同源，不手抄）。谁要工具名单，谁去取投影：注册表增删实时反映，核心**没有**
   第二份可漂的手抄清单（消 D-25）。
5. **`teardown()` 幂等可逆。** local 没有外部注册面可撤 ⇒ 空操作；dsh/MCP
   实现用它撤销 `declare` 建立的注册。幂等是契约的一部分（宿主关停/重装工具面
   时可能被调多次）。
6. **local 是出厂 Provider**：`LocalToolHost(registry)` —— `declare` 校验后
   无操作、`call` 委托 `registry.execute`、`schemas` 委托 `registry.schemas`、
   `teardown` 空操作；`name` 缺省 `local`（进教学 hint 用，派生实现可覆盖）。
   **dsh/MCP 是另一个 Provider**（未实现，见推迟项）：把定义注册进
   `ctx.tools`、把调用走宿主回程——它住适配器侧，本包一行都不 import 它。
7. **装配**：`Software.toolhost` 字段（与 `Software.tools` **同一对象**
   `registry`，不是第二张表）+ `declare_roles` 登记 `provider.toolhost`
   （DEFINITION）与 `provider.toolhost.local`（PROVIDER, `in-process`）；
   `provider.toolhost.local` 当前无内置消费者，按既有纪律进
   `capability_map_selfcheck.DEFERRED_PROVIDERS` 显式登记推迟。
8. **判据** `checks/phase9_toolhost_selfcheck.py` 进 `run_all`：白名单投影、
   合规调用、六类失败归一化（含宿主句柄抛错与五种畸形回执）、坏声明反例（九
   种）、teardown 幂等、装配路径 L7 对偶。
9. **机制层零领域词**：本模块不出现任何消费项目的命令名、状态键、指标名，也
   不 import dsh/领域实现；判据自己的工具名是中性值（`do_thing`/`set_value`
   与 `phase4_adapter_selfcheck` 同款）。

## Consequences

**换来**：宿主传输有了唯一定义——第二个宿主不再自己发明"怎么交定义、怎么收
调用、宿主坏了怎么报告"；换宿主 = 换 Provider 实现，核心与判据一行不改
（硬纪律 6 在工具面上从承诺变成结构）。工具名单只有 `schemas()` 一个来源，
模型可见字段的泄漏面收在 `declare` 的入口守卫上。失败词汇统一，模型在任一宿主
下看到同形状的可教学失败。

**付出**：多一层间接（`host.call` → `registry.execute`）与一次白名单再投影的
拷贝（工具数量级小，不构成新瓶颈）；`declare` 的拒收把"顺手多塞一个字段"从
静默降级变成当场报错——接第三方的 schema 源时可能更啰嗦，这是刻意的。

**放弃了什么**：放弃"宿主自己决定交哪些字段"的自由（白名单是契约，不是建议）；
放弃把宿主异常原样透传给模型（栈归宿主日志，模型只拿结构化失败）；放弃在
ToolHost 里做权限检查——可见性过滤归 `visibility.py`、写权归 Gate，
ToolHost 只搬运；在这里加第二道权限就是 v1"两套写权门"的复发。

**实现期发现（诚实记录）**：本判据首版把"回执缺必填键 / 工具体意外异常"两条
反例的调用参数写漏了，结果两条都归一化成 `missing_arguments`——判据自己把
"测错东西"暴露成红，而不是绿着通过。这正是"每条'能抓坏'必须断言**具体 kind**、
不能只断言 `is_error`"的实证：只查 `is_error is True` 的话，这两条反例连
`bad_tool_output` 与 `internal_error` 都没走到也会绿。

**推迟项（各绑可判定触发）**：

- **dsh/MCP 侧 Provider**（`declare` 注册进 `ctx.tools`、`call` 走宿主回程、
  `teardown` 撤销注册）。
  **触发**：出现可注入 `ctx.tools` 的真 dsh 宿主进程，且宿主需要工具面
  opt-in 接线（届时本包仍不 import dsh，实现住适配器侧）。
- **`declare` 的注册表身份核对**（确认交付的 schemas 就是本实例 registry 的
  产出，而非另一张表的拼装）。
  **触发**：出现两个工具注册表片交错的真实宿主。
- **传输层工具白名单/限流**（按宿主会话裁剪可见工具）。
  **触发**：出现"同一进程里两个操作者需要不同工具可见集"的真实部署——
  届时应做在 `visibility.py` 的 restriction 链上，而不是 ToolHost 里。

## Alternatives considered

**否决：不拆 seam，把宿主传输继续留在各适配器里（`build_tool_registry` +
`to_mcp` 各写一遍）。** 这是现状。它的问题不是"重复代码"，是**失败语义分叉**：
同一个宿主回程畸形，A 宿主翻译成 `internal_error`、B 宿主裸抛、C 宿主当成
工具返回值，模型在三个部署里学到三套行为（L4 的 ROI 直接归零）；且换宿主等于
改适配器源码，churn 越过 Provider 层（硬纪律 6 失守）。共用形状可以，共用一个
"谁来交、谁来收"的归属不行。

**否决：`declare` 对白名单外字段做静默过滤（只投影三个字段，其余丢弃）。**
安全上与拒收等价（两者都不透传 `execute` 对象），所以这不是安全权衡，是
**证据权衡**：能往 `declare` 里塞 `execute` 的代码，只可能是绕开
`registry.schemas()` 手工拼 schema 的地方——而那正是"模型请求里差点出现
可调用对象"的唯一来路。静默过滤会让这条路继续存在且不留痕（绿着上线），
拒收让它当场红。另一层是形状责任：`declare` 的入参契约如果是"随便什么映射，
我只挑三个"，那么"声明里漏了 description"这种真事故也会被静默补成空串，
到模型那里才变成"这个工具没法用"。**重新考虑条件**：出现一个真实宿主，
其 `ctx.tools` 注册面要求额外字段（如宿主自己的权限标签）必须随 schema 一起
交付——届时扩白名单字段（`_DECLARED_FIELDS`），仍不改成静默丢弃。

**否决：把 `ToolHost` 做成 ABC 并让 local/dsh 继承。** 宿主侧实现必须继承我们
的基类，等于把"我们包里的一个具体类"变成宿主必须拉的依赖——dsh 侧 Provider
会变成 `import mecha` 才能注册工具，与"核心不 import dsh、宿主不 import 核心
内部形状"的双向解耦冲突。Protocol 只约束形状，宿主侧不继承任何东西；判据实测
一个与 `LocalToolHost` 毫无血缘关系的替身同样被认作 `ToolHost`。

**否决：把 ToolHost 合并进 `ToolRegistry`（给注册表加 `declare`/`teardown`）。**
注册表是**定义面**的唯一来源（构造即校验、白名单投影、回执契约），它的正确性
可以完全脱离宿主单独成立；传输面会随宿主变（有的宿主有注册 API，有的只是
进程内一个 dict）。合并的后果是：每次换宿主都要动定义面那个被 phase4 判据逐字
钉住的对象，且"注册表的形状"与"宿主的形状"两个独立变化源焊在一起。共用形状
可以（回执同构），共用 seam 不行。

**否决：`call` 在失败时把宿主原始异常/回执原样透传给模型。** 透传看起来信息
更全，实际是把"我们的调用链内部长什么样"写进模型可见文本——总纲 §9 反模式
明列"把实现细节写进模型可见的文本"，且跨宿主的文本不可比、不可教。栈留给宿主
日志，模型只拿 `message` + `info{kind,hint,suggest}`。**重新考虑条件**：出现
"模型必须知道宿主特定失败码才能继续"的真实用例——届时在 `info` 里加**稳定
字段**（如宿主码），而不是透传异常对象。

**否决：让 ToolHost 承担工具可见性/权限裁剪。** 越界的双重代价：一是核心开始
理解"谁能用哪个工具"的宿主策略（领域/部署知识进机制层）；二是与
`visibility.py` 的 `ToolRestriction`（单调、取交集、拒未声明名）形成第二个真相
源——两处都能裁可见集，谁赢？这正是 v1"两套写权门"的机构版。ToolHost 只搬运，
裁剪归 restriction 链，写权归 Gate。

**否决：现在就把 dsh 侧 Provider 一并实现（把 dsh 的 `ctx.tools` 形状抄进来）。**
本仓没有可注入的 dsh 进程，抄来的 API 形状无消费方作证（总纲 §5.4：没有消费
方作证的选择要么显式要值、要么推迟）；且 dsh 特性层以天为单位重写，抄进核心
就是把 churn 请回来。**重新考虑条件**：真 dsh 宿主进程可注入 `ctx.tools` 且
需要工具面接线——实现仍住适配器侧。
