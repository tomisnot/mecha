# 两层传输上提：只读监控端点进核心、MCP 投影进 extra

> **状态**：implemented
> **作者**：mecha v2（框架实现方与接口冻结方；响应主代理「提取」阶段 1–3）
> **日期**：2026-09-25
> **落地**：`mecha/cockpit.py` + `mecha/portfile.py`（core，零依赖）与
> `mecha/providers/mcp.py`（extra `mcp`），判据 `checks/phase11_cockpit_selfcheck.py` /
> `checks/phase12_mcp_projection_selfcheck.py`；`python checks/run_all.py` 全绿。
> **状态语义**：`implemented` ≠ 冻结（ADR 制度 §1）。本 note 记的是**框架侧**已落地；
> 两个下游迁到它、以及收口轮的减法，都是后续动作。

## Problem

两个下游宿主各自手写了两层**逐字节同形**的传输，框架侧一份都没有：

1. **只读监控端点**。EL 的 `src/v2_bind.py` 的 `_MonitorHandler` /
   `start_monitor_endpoint` 与 ML 的 `ml_mecha/monitor_http.py` 实现了同一组路由
   与响应形状（ML 的模块 docstring 有一张逐条标注 EL 行号的契约表）。
   面板（从 EL `dsh/src/client/` 移植）不改渲染逻辑就能吃两家的数据，**正是因为
   两边逐字段对齐**——而这个"对齐"靠人手抄，不靠机制。
2. **MCP 投影**。EL 的 `mecha_v2/hub.py` 的 `to_mcp` / `_register` 与 ML 的
   `ml_mecha/mcp_host.py` 实现了同一套投影：工具来源是 `ToolRegistry.schemas()`、
   必填项从声明派生、覆写 SDK 私有面把声明写回、失败归一化为
   `CallToolResult(is_error=True)`、调用前设 `CURRENT_CALL_ID`。

不改会怎样（可观察，且已在发生）：

- **契约漂移无人拦，且"文档说的"与"代码做的"已经分叉**。ML 的 docstring 写的是
  两家的**交集**，代码却是**超集**（`/status` 多运行期键、`/config` 多
  `n_snapshot_keys`）。主代理据该 docstring 得出"两家字节级一致"，实测不成立——
  这正是要根治的那类漂移：没有机械判据时，善意差异与缺陷不可区分。
- **框架自述与实物不符**。总纲把 Monitor 列为与 Gate/History/Surface 并列的第一层
  正职（"侧边栏是第一交付物"），但**这一层在框架里没有传输**：库内 `monitor.py`
  只有 `read()`，能不能被人看见取决于宿主是否记得再写一个 HTTP 端点。ToolHost
  契约把"定义"与"传输"分开并声明 dsh/MCP 是它的另一个 Provider——该 Provider
  至今不存在（`toolhost.py` 的 Known Limitations 自认）。
- **同一批 SDK 私有面与安全规则被两处各垫一次**：`server._tool_manager` 覆写
  `Tool.parameters`、以及"启动前无条件清陈旧发现文件 / 收尾只删自己的"这条
  **带安全论证**的规则（Windows 强杀不跑 `finally`）。两处各写一次＝两处可各自漂移。
- **固定端口**：EL 侧把监控端口写死为默认值，且同一常量在 Python 默认值与面板
  TS 常量里各写一遍 ⇒ 换端口表现为"面板永久离线却不报错"（假绿）。

受影响的：两个下游（维护成本翻倍、行为已分叉）、框架（自述的面缺传输）、后续
接入的第三个项目（照抄哪一份？两份已不完全一样）。

## Decision

冻结两层传输的框架侧接口并实现。**「只增不改」只是本迁移窗口的战术**（唯一目的是
让回归可定位：迁完若坏，能一眼看出是哪一步引入的）——**不是**架构原则，窗口一关
必须做减法。窗口内对既有文件的改动限两类：①**接线级**（让新机制能接上，必须说清
"谁需要"）；②**表述级**（文档与实现不符时改文档）。其余一律不许（"更通用/更整洁/
将来方便"不是理由）。**每一条新增都必须有一个具名消费者——今天存在的调用方**；
"为了将来可能需要"与"两个下游之一想要"都不算。

### D1 · cockpit 进核心（`mecha/cockpit.py`，零依赖）

用 `http.server` + `json`，**不引入任何依赖**，不改 `dependencies = []`。理由：它
补的是框架**已经声明为正职**的监控面的传输，是"完成自己"而不是扩张；零依赖 ⇒
进 extra 会让框架自己的第一层面变成 opt-in，与"nothing ships enabled"用在自己
身上的初衷相反（那条纪律管的是**写权**默认收紧，不是把自己的正职藏起来）。

> **模块名**：EL 规格 §7.2 建议 `mecha/monitor_http.py`；本 ADR 定为
> `mecha/cockpit.py`（主代理给的第一节摘要取此名，取其"人看 AI 干了什么"的原义；
> `monitor_http` 把传输实现写进模块名，而该模块同时含投影纯函数与源适配）。
> **这是与规格书的一处命名分歧，行为面零差异**；若委托方要改回，只改文件名与
> 引用，不动契约。

**数据 seam**：不认 `Software`、不 import `assembly`（传输层不该依赖装配点，判据
也不必为此起整台软件）。只认 `MonitorSource` —— 五个成员：`events()` / `snapshot()` /
`mode()` / `schema_rows()` / `status_extra()`，**鸭子类型**（有这五个可调用成员即用，
不需要继承）。

- `MonitorSource.from_software(sw, *, schema_rows=None, status_extra=None)` 是给
  `Software` 形态的一行适配（只按成员名识别 `history` / `gate` / `authority`）。
- `MonitorEndpoint(source, …)` 的首参**同时接受两种形态**：五成员对象直接用；
  `Software` 形态自动适配（于是"把端点接到这台软件上"直传即可）。**第三种对象
  响亮报错**（`bad_monitor_source`，列出缺哪些成员并指路 `from_software`）——
  静默降级成空史/空快照会做出一个"永远健康但什么都没有"的面板，那是最坏的假绿。
- 已有五成员对象时再单独注入 `schema_rows` / `status_extra` ⇒ 报错（不静默忽略）。
- `activity_records` / `history_records` / `config_tree` / `monitor_summary_payload`
  同时是**模块级纯函数**（判据与将来的同源路由直接用；端点方法只是转调）。

**缺口与处置（`Software` 不够的两项，都用注入，不往 core 加概念）**：

| 项 | 谁提供 | 为什么不进 core |
|---|---|---|
| `schema_rows()` | 项目注入 | 行是不透明映射。EL 从引擎参数表来，ML **没有**这层、如实空表并走"无 schema"分支；给 `Engine` 加必实现会逼没有 schema 的项目**编造行**（"凭空造树把面板撑满"是它明文拒绝的），加可选字段等于把回退值藏进 Definition（D-17 的反面） |
| `status_extra()` | 项目注入 | 是**宿主生命周期事实**（pid / 端口 / uptime），端点自己不知道。默认空 ⇒ 默认响应与"只回 `{ok, mode}`"的宿主逐字节一致 |

**schema 行的可选键词表（迷你契约，必须写下来——不写就是下一次漂移的源头）**：

| 键 | 必需 | 缺省 | 语义 |
|---|---|---|---|
| `name` | ✅ 非空字符串 | — | 键全名；缺/非串 ⇒ `bad_schema_row` fail loud（不静默丢行） |
| `family` | ❌ | `"other"` | 族（`groups` 的第一级键）；空值同样归 `"other"` |
| `prefix` | ❌ | 由 `name` 派生 | **不读宿主值**：取 `name` 第一个 `.` 之前；不含 `.` ⇒ `""` |
| `unit` / `type` / `desc` | ❌ | `""` | 只做空值投影，**不解释语义**（领域分类归宿主） |

**路由契约（冻结，逐字段照两家现有实现）**：

| 路由 | 响应 |
|---|---|
| `OPTIONS *` | `204` + `ACAO: *` + `ACAM: GET, OPTIONS` + `ACAH: Content-Type`，**无 body、无 Content-Length** |
| `GET /status` | `{"ok": true, "mode": "<human\|ai\|locked>"}` + `status_extra` 的键 |
| `GET /activity[?since_seq=N]` | `{"ok": true, "events": [...], "mode": "..."}`；事件**恰好 6 键** `{kind, actor, target, value, seq, call_id}`，`kind` 恒 `"set"` |
| `GET /history[?since_seq=N]` | `{"ok": true, "events": [...], "mode": "..."}`；事件**恰好 9 键** `{seq, kind, actor, target, value, before, after, reason, call_id}`，`value == after` |
| `GET /config` | `{"ok": true, "has_schema":…, "groups":…, "orphans":…, "n_keys":…, "n_snapshot_keys":…}` |
| 未知路径 | `404` `{"ok": false, "error": "unknown endpoint"}` |
| 任意 `POST` | `404` `{"ok": false, "error": "read-only monitor endpoint"}` |

其余冻结项：**路径一律先取 `urlsplit(self.path).path` 再精确匹配**（查询串交给
`parse_qs`，做 URL 解码；`/historyfoo` 必须 404，`/config?t=1` 必须 200）；
`since_seq` 缺失 / 非纯数字 ⇒ `0`，语义 `seq >= N`（闭区间）；
`n_keys` = **schema 行数**、`n_snapshot_keys` = **快照键数且恒回**（两者之差正是
人最该看见的信号："schema 说这么多键，实际只设了这么几个"）；
`has_schema = n_keys > 0`；`orphans` 按 `name` 升序；`groups` 族与前缀字典序、
同前缀内保持宿主给的表序；行字段
`{name, short, prefix, value, unit, type, desc, set}`（`value` 取自**当前快照**、
`set` 取自**全史最后一次写**的 `{reason, actor, seq}`）；`orphans` 行
`{name, value, set}`；响应头 `Content-Type: application/json`（不带 charset）+
精确 `Content-Length` + **所有**响应（含 404 与 POST 404）带 `ACAO: *`；
序列化 `json.dumps(..., ensure_ascii=False, default=str)`；`log_message` 静音；
**绑回环、无鉴权**（只读 + 回环是全部安全模型；"AI 不能自授权"靠 `Authority` 的
side 判定，不靠端点鉴权）；服务端**不截断、不倒序、不缓存**，`since_seq` 是唯一裁剪。

**POST 必须先把请求体读干净再回 404**（`_drain_request_body`）：带 body 的 POST 若不
drain 就关连接，Windows 内核回 RST，客户端在读**状态行之前**就被打断
（`ConnectionAbortedError` / `WinError 10053`）——这是**既有缺陷**（迁移前的老实现
同病，EL 用 `git show` 取出旧实现做过决定性实验：同条件 6×30 轮命中 4/30），代价是
**两个项目的门禁偶发假红**（本仓实测未修时 40 轮里命中 0–13 次），不是用户可见故障
（真实面板只发 GET）。三分：合法 `Content-Length` 且在 1 MiB 内 ⇒ 读净丢弃、连接可
复用（**不加任何头**，wire 一字不变）；缺失 / 非法 / 超界 ⇒ **不硬读**，只加
`Connection: close`——**状态码与 body 一字不变**。判据在 `phase11` 的 H 组：决定性
判别子（公告的 body 未发完时服务端不得提前回响应——不修的实现**必然**在这里红）＋
压测（带 body POST 多轮零中断）＋三分单元规则 ＋ 契约不变的不许误报对偶。
**残余面（已登记、不建机制）**：`do_GET` / `do_OPTIONS` 带 body、以及
`BaseHTTPRequestHandler` 对未实现方法回的 501，同样"不 drain 就关"——今天没有消费者。
MCP extra 侧无此路径：它不碰裸 HTTP，全部由 ASGI 栈（uvicorn/starlette）处理。

⚠ **`before` 必须 fold 全史、不能只 fold 窗口**：它是"同键**上一条**事件的值"
（首写 `null`），不是快照旧值；fold 与过滤必须分离（先算 before / 更新 last，再判
seq）。写成"只 fold 窗口"会让增量轮询的 `before` 从 `null` 起，面板展开行显示
`∅ → 新值`——**静默错**，只有人肉看面板才会发现。**已配致死性判据**（构造"窗口内
无前值、全史有前值"的场景）＋"首写必须为 `null`"的不许误报对偶。

**项目扩展点（不 fork 加路由）**：`add_route(path, handler) -> disposer`，构造参数
`extra_routes: Mapping[str, handler]` 走同一道校验。

- `path` 必须是以 `/` 开头的绝对路径；与核心四条或已注册路由重名 ⇒
  `duplicate_route`（fail loud，不静默覆盖）；`handler` 不可调用 ⇒ `bad_route`。
- `handler(query: Mapping[str, list[str]]) -> Mapping`；返回体由本模块统一包成
  `{"ok": true, **返回体}`、`200`（项目不自己写 `ok`），走同一套序列化与响应头。
- 路由**只挂 `GET`**，`POST` 恒 404（只读红线不给扩展点开后门）；注册 / 撤销在
  运行中立即生效；`disposer` 可逆（与 `Surface.register` / `CommandRegistry.register`
  同纪律）。
- ⭐ **失败语义是"响亮失败"**：handler 抛异常 ⇒ `500` + 结构化错误体，
  **不返回如实空表**。"读不到数据"与"确实没有数据"必须可区分——在传输层把两者
  抹平成空表，正是本仓反复在防的假绿（"缺真依赖即红不假绿"）。错误体用
  `MechaError.to_failure()` 的 `{message, info:{kind, hint, suggest}}` 形状，
  与工具面 / 命令面同一份（**不新造第三种形状**；主代理裁决里的"message + kind"
  由该形状覆盖：`kind` 在 `info` 内）。返回非映射 ⇒ `500 bad_route_payload`；
  `status_extra` 抛错同理（500）。
- `monitor_summary_payload(view)` 把 `MonitorView` 投影成
  `{summary, disputed, dispute_reason}`，且把 `Claim` 转成 `{"value", "target"}`：
  直接丢进 `json.dumps` 会被 `default=str` 变成 `"Claim(value=…)"` 字符串，
  "它复述的是哪个原始键"就此丢失（**契约级要求**，已配判据）。

**生命周期**：`MonitorEndpoint(source, *, host="127.0.0.1", port=0, port_file=None,
runtime_writer=None, schema_rows=None, status_extra=None, extra_routes=None,
log=None)`；`start() -> int`（实际端口；`port=0` 由 OS 分配后回读）、
`stop(timeout=10.0)` 幂等、`port` / `url` 只读属性（未启动 ⇒ `url == ""`）、
`with` 上下文；便利函数 `start_monitor_endpoint(source, **kw) -> MonitorEndpoint`。

- **无固定端口默认值**（D-7 纪律：库内零端口字面量，含注释里的"建议端口"）。
  宿主若要有固定端口，是它的参数。
- **处理器类按实例派生**（不是类属性共享全局）：同进程起两个端点时类属性会互相
  覆盖——那是实测过的隐患（已配判据：两端点各自 `mode` 必须正确）。
- `start()` 顺序：清陈旧端口文件 → bind → 写端口文件 → 调 `runtime_writer`。
  `ThreadingHTTPServer` 构造即 bind+listen ⇒ **同步 bind**，无"起来了但还没 listen"
  的竞态。`stop()`：`shutdown` → `server_close` → `join` → 按"内容仍是自己写的
  端口"清文件 → 通知描述符。`stop` 幂等；重复 `start` ⇒ `monitor_already_started`。
- `start_monitor_endpoint` **返回端点是刻意的**（不是裸端口 int）：调用方需要
  `.port` / `.url`，也必须有人握着 `stop()`。EL 侧老签名（返回 int）与本签名不同，
  迁移时两处调用点（生产路径 + 判据）同批改——**属 EL 的改造单，不在本仓**。

**发现机制与边界**：

- `port_file`：裸端口文本，清理规则由 `mecha/portfile.py` 单一实现
  （`clear_port_file(path, expected=None)` = 启动前无条件清；`expected=<端口>` =
  收尾只在内容仍是自己写的端口时删）。**库不持有任何端口文件名字面量**——文件叫
  什么是宿主与其消费方的发现约定；`.mcp-port` 这类必须保持现名的约定归宿主。
- `runtime_writer: Callable[..., Mapping] | None`：可选的"描述符合并写"钩子。
  框架只负责**何时写**（`start` 成功后 `monitor_port=<实际端口>` 一次；`stop` 时
  `monitor_port=None` 一次），**文件名与字段表归项目**；钩子异常透传（不吞）。
- ⛔ **运行期描述符的 schema 不属本轮**：`mode` / `pid` / `authority_pid` /
  `dsh_port` / `started_at` 等字段表归宿主；`mecha[launcher]`（后续步骤）才拥有
  描述符 schema。本轮框架只提供 `port_file`（最小发现机制）+ `runtime_writer`
  （可选钩子）。**不把任何一家的 `.…-runtime.json` 字段表吸进核心。**

### D1b · `portfile` 进核心（`mecha/portfile.py`，零依赖）

`read_port` / `write_port_file` / `clear_port_file(path, expected=None)`。它不是
"三个碰巧写法相同的函数"，而是**一条带安全论证的规则**：

- Windows 下 `terminate()` / `taskkill /F` **不跑** Python 的 `finally`
  ⇒ "起时写、止时删"不能只靠收尾，必须在启动前也清一次陈旧文件。
- 启动前无条件清（`expected=None`）的安全性论证：调用方此时**已装配成功**（手握
  数据目录写租约）⇒ 同根不可能还有别的活宿主 ⇒ 该文件必属死进程。
- 收尾只删"内容仍是自己写的端口"的文件 ⇒ 不误删下一台权威刚写的新端口。

**安全论证重复两次＝两处可各自漂移**，故归框架；宿主只拥有"文件叫什么"。
落点不放 `data_layout.py`：后者管数据目录，端口文件在仓根，是两个关注点。

### D2 · MCP 进 extra（`mecha/providers/mcp.py`）

`pyproject.toml` 的 `[project.optional-dependencies]` 增
`mcp = ["mcp>=2.2,<3", "uvicorn>=0.30"]`。理由：`uvicorn` 被**直接 import**
（不是仅传递依赖）必须显式声明；`MCPServer` 与 `_tool_manager.get_tool` 是 **2.2
的形状**，`>=2` 太宽。它天然属于 `providers/` 的 **ToolHost 传输 seam**：
`toolhost.py` 已完成定义/传输分离，MCP 正是缺失的远程传输 Provider。
**核心不 import 本模块**（`import mecha` 零第三方依赖）。

**冻结接口**：`MCP_PATH` / `DEFAULT_MAX_INSTRUCTION_BYTES`；`RequiredSource`
（`required_for(name, tool) -> list[str] | None`，`None` = 回退）；`signature_required`
（出厂回退）；`resolve_required`；`tool_input_schema`；`synthesize_signature`；
`check_instructions`；`build_mcp_server(registry, *, server_name, instructions,
toolhost=None, required_source=None)`；`McpEndpoint`（`build_server()` 纯构造 /
`start(timeout=30.0) -> int` / `stop(timeout=10.0)` / `port` / `url` / `server`）。
**不提供"declare 即注册"的 `ToolHost` Provider**（曾拟 `McpToolHost`）：它今天没有
外部消费者，按准入线删掉并登记收口轮（见下，含升格触发条件）。

**三条不变式**：①工具唯一来源 `registry.schemas()`，不新增第二张工具表；
②调用唯一路径 `ToolHost.call`，**不**直调 `registry.execute`（远端边界归一化必须
留在路径上）；③必填项从权威声明派生、**不从包装函数签名推**（`**kwargs` 包装会推出
空集 ⇒ 必填在模型面静默消失）。

**必填来源优先级（本 ADR 的实现）**：注入的 `required_source` → `execute` 闭包签名。
命中注入来源时，若闭包签名**确实**暴露了命名必填项，两侧必须逐项相等，否则
`tool_declaration_drift`；签名推出空集是包装器下的预期状态，不比对。

**其余冻结项**：`properties` = 声明逐字（键序 = 声明序）；`required` **恒出现**
（空则 `[]`）；注册后把声明合成的 `inputSchema` **覆写回 SDK 注册项**（pydantic 派生
值会丢 `description` 与真实默认值、并加 `title`）；覆写与置空**只允许出现在一个
函数**里（`_override_declared_schema`），取不到注册项抛 `mcp_sdk_shape_changed`；
`defaulted` 的**唯一权威 = `parameters` 声明里的 `default` 键**，三分规则（缺一即
错）：声明 `default` **非 `None`** ⇒ 进集合，收到显式 `null` 时**丢弃该键**（让真默认
生效）；声明 `default` **为 `None`** ⇒ 不进集合（显式 `null` 原样传递——那是"清空"
语义的唯一表达方式）；声明**没有** `default` 键 ⇒ 视同真默认 `None`，同样不进集合。
⛔ **刻意不读 `tool_def.execute` 的签名**：写工具体常被 `def wrapped(**kwargs)` 包一层，
**内层闭包的真默认被包装遮死** ⇒ 签名侧恒为空集，对"包装宿主"必然漏，且漏得静默
（显式 `null` 以 `None` 到达工具体；今天无害只因各工具体用真值判断，改成
`is not None` 就立刻错）。权威收回声明——与本仓既有教条一致（**声明 → 机械投影**，
投影不靠实现细节反推）；`ctx` 经注解注入、不进模型可见参数；
`CURRENT_CALL_ID` 按 wire request id set/reset（`try/finally`）；失败恒为
`CallToolResult(is_error=True)` + 正文 `{"ok": false, "error": {message, info}}`
（不用 `raise ToolError`、不返回错误文本）；成功返回
`json.dumps(value, ensure_ascii=False, default=str)`；`/mcp` + `streamable_http_app`
+ `uvicorn.Server` 跑在权威进程后台 daemon 线程，等 `uvicorn.started` 后**回读真实
端口**；端口文件走 `portfile`；`server_name` / `instructions` 由宿主给（框架不设领域
默认值），说明体积在**构造期**校验。

⛔ **不声明 structured output（理由是"假契约"，不是"dsh 会拒绝"）**：SDK 会从 handler
的**合成签名返回注解**派生一个 output schema——`return_annotation=str`（两家下游现状）
会产出 `{"properties": {"result": …}, "required": ["result"], …}` 并**出现在
`tools/list` 的 wire 上**。它声称"这个工具返回 `{result: string}`"，而工具**实际返回
各自领域回执的 JSON** ⇒ **发给客户端的是错的契约**；更糟的是它由**实现痕迹**（合成
签名长什么样）派生，不是任何人的声明。这与"缺 `type` 被当成 `string`"是**同一类**
缺陷：实现细节泄漏成 wire 契约。故合成签名的**返回注解留空**（派生结果为空），并由
判据断言**协议层 `list_tools()` 的 wire dump 里没有 `outputSchema`**——防 SDK 漂移靠
判据，不靠再加一条冗余代码路径（同一保证不做两份实现）。
**两家下游现状都会在 wire 上带它 ⇒ 迁移后这一点会变**。
至于"它在 dsh 侧是否真的触发 `createOutput` 的 `content + structuredContent` 要求"：
**我未验证，主代理也未验证**（且 EL 的提交史里有多次真人实测会话，说明**当前带
`outputSchema` 也跑得通** ⇒ 那条因果链很可能是错的或是有条件的）。该问题**已路由 ML
子代理复核**；本 note 只按"假契约"立论，不把 dsh 当成已证动因。

### D3 · 明确不做的事

- **core 不 import `mcp`**：`mecha/__init__.py` 与全部脊椎模块保持零第三方依赖；
  只有 `providers/mcp.py` 顶层 import `mcp`，且 core 不 import 它。
- **不新增第二道权限门**：可见性归 `visibility`，写权归 `Gate`；两层传输都只搬运，
  MCP 面不新增审批/scope 判断，监控端点不加鉴权、不开写路由。
- **不替宿主决定端口、目录名、文件名、服务名、`instructions`、工具名、schema 行、
  描述符字段**。
- **不改 core 既有语义**：`Software` 字段与 `Gate` / `History` / `Surface` /
  `ToolRegistry` / `ToolHost` 签名一律不动（只增不改）。
- **两个下游不需要改核心才能接**：接入 = 删掉各自那份实现、改为传
  `MonitorSource` / `ToolRegistry` + `ToolHost`；扩展路由用 `add_route` 注册。

## 偏离裁决之处（逐条留痕，不做静默取舍）

纪律更正后新增的准入规则（"每一条新增都必须有一个具名消费者——今天存在的调用方"）
改变了三处实现决定，逐条报备；**三处均经主代理批准**（第 2、3 步裁决 §二逐条点名
"全部批准"）：

1. **不加 `ToolDefinition.declared_required` / `define_tool(declared_required=)`**。
   主代理裁决 4 的优先链是 `required_source()` → 工具上的 `declared_required` → 签名；
   中段那一项的**今天消费者为零**（ML 走注入路径，EL 走签名），而 `required_source`
   已能覆盖"宿主有自己的必填声明面"这唯一需求（EL 将来若包装 `execute`，传一个
   source 即可）。故本轮**不往 `tools.py` 加字段**，优先链落地为
   `required_source()` → 签名。**已批准**；将来要保留中段可在收口轮加（它不影响
   任一家的现状）。
2. **不做 `declaration_required(parameters)` 公开助手与 `validate_declared_tools`
   公开判据**：前者无独立消费者（注入来源覆盖同一需求），后者的两项漂移检查已在
   `resolve_required` / `tool_input_schema` 里**就地强制**（注册时即红），再包一层
   公开函数只是并行实现。
3. **不做 `check_server_name`**：服务名合法性是 dsh 侧约束（本 extra 不 import dsh），
   且无今天消费者。写在 Own Limitations 里作为宿主责任，不预建守卫。
   **若你要求**，收口轮按 `check_instructions` 同款补（它已被裁决要求，故保留）。
4. **`signature_required` / `tool_input_schema` / `synthesize_signature` 保持公开**：
   消费者是本模块自身的注册路径（不是"为将来预留"），且判据要直接断言 wire 形状。
   三者都在 ML 规格 §9.2 的冻结面里。

## 未验证（明确不宣称）

- ⛔ **不得假设 `MCPServer.call_tool()` 可在进程内直调**。根因（mcp 2.2 实测）：
  进程内 `call_tool` 造的 `Context` **没有 `request_context`**；读它会抛
  `ValueError("Context is not available outside of a request")`，而
  `Context.request_id` 正是读它 ⇒ handler 用 `getattr(ctx, "request_id", None)` 取
  call_id 时，**`getattr` 只吞 `AttributeError`，`ValueError` 会直接穿出**，被 SDK
  包成 `UnexpectedToolError`。⇒ **消费者必须走真实传输链路**（HTTP /
  streamable-http）；判据 / 测试不得依赖进程内直调。handler 里那个 `getattr` 容错
  写法**保留**（真链路上它是对的）；已裁定**不为此加分支持、不加判据**——今天零消费者，
  且"成功但 `call_id` 为空"的无归因写比响亮失败更坏。
- **`outputSchema` 在 dsh 侧的后果未验证**：我实测到"两家下游现状的 wire 上都会带
  `outputSchema`（由 `return_annotation=str` 派生）"，也实测到本实现能把它按住；但
  "dsh 收到它是否真的把回执判为 invalid"**我没有跑真 dsh**。若 ML 的活体 mount 判据
  一直绿，说明要么 dsh 容忍、要么那条判据没走到调用路径——**请路由给 ML 子代理复核**，
  这是本次发现里最值得追的一条。
- 未跑真 dsh 客户端往返（`mcp__<server>__<tool>` 公开名映射、`serverName` 约束、
  `maxInstructionBytes` 的真实拒绝行为都属宿主侧）。

## Consequences

**换来**：框架自述的"人类监控面"第一次有了自己的传输，ToolHost 的远程 Provider
从"声明存在"变成"可 opt-in"；两家的响应形状与投影规则**单一来源**，契约漂移从
"人手抄对齐"变成"可机械对拍"（两边成薄壳后同一份响应可直接 diff）；SDK 私有面
垫片与端口文件安全规则各只有一处；第三家接入照 seam 传参即可。

**付出**：core 多两个公开模块（`cockpit.py` / `portfile.py`）；`providers/mcp.py`
把 SDK 私有面垫片收进框架（SDK 升级只改一处，但框架要跟着 SDK 动）；
`pyproject.toml` 的 extra 段落从空注释变成真声明；capability map 多两行
（`monitor.transport` / `monitor.transport.local`），后者在迁移窗口内**显式登记为
诚实推迟**（当前无任何非判据代码 import 它），任一宿主迁完即移出该表。

**放弃了什么（均为可观察的行为变更，逐条留痕）**：

- **EL 获得一个附加键**：`/config` 多回 `n_snapshot_keys`（加法放宽，面板按键名读）。
- **EL 的畸形路径从 200 变 404**：`/historyXYZ`；**带查询串的 `/status`/`/config`
  从 404 变 200**（取纯路径 + 精确匹配是修正）。
- **EL 失去库内固定端口默认值**：固定端口降级为**宿主参数**（行为不变，EL 调用点
  要显式传）。
- **EL 的 `start_monitor_endpoint` 返回值从 int 变端点对象**、首参从 `V2Bridge`
  变 `MonitorSource`/`Software` ⇒ **EL 的两处调用点（生产路径 + 判据）同批改**，
  否则基线红；这是 EL 的改造单，不在本仓。
- **ML 的 `/runs` 失败语义从"如实空表"变 `500`** ⇒ ML 迁移时承接。
- **放弃把 `/summary` / `/runs` 做成核心内置路由**：它们是领域概括与领域存档，
  核心不认（`/summary` 只给 `monitor_summary_payload` 投影便利函数，`/runs` 完全
  不进核心）。
- **放弃"两个下游 `/status` 完全同形"**：附加键由 `status_extra` 注入，两家键集
  仍不同（面板只读 `mode`，相容）。抹平就要往核心塞运行期概念。

**已知后续候选（登记 + 升格触发条件，不许沉默推迟）**：`/status` 的运行期四字段
（`pid` / `uptime_s` / `mcp_port` / `monitor_port`）**本轮不进核心**，只留
`status_extra` 注入。区分原则：`n_snapshot_keys` 是**框架可派生**的，
这四个是**宿主生命周期事实**（端点不天然知道自己的 pid 与邻居端口）。
**升格触发**：出现第三个真实实例、或任一宿主明确要求框架统一提供
`{ok, mode, pid, uptime_s, monitor_port}` + `mcp_port` 注入时，写取代 note 再提升。

**还没配判据的（诚实声明）**：本节的行文纪律（"对齐"→"形状类比"）与 D2 的
`output_schema` 禁声明属 MCP 实现阶段，届时同批补判据；本 note 不宣称它们已落地。

## Alternatives considered

**否决：维持两家各一份，只在文档里写"必须同形"。** 已经证明不够——本次复核实测
ML 的 docstring 与其**自己的代码**都不同步（文档写交集、代码是超集），主代理据此
得出过错误结论。没有机械判据时，善意差异与缺陷不可区分；文档纪律正是 v1 血统标签
黄掉的方式（L5/L8 的教训）。

**否决：cockpit 也进 extra（`mecha[cockpit]`）。** 它零依赖，进 extra 的唯一效果是
让框架**自己声明为正职**的那一层在默认安装里缺席——"侧边栏是第一交付物"会变成
"要装才有"。

**否决：MCP 进 core。** `mcp` 是重第三方依赖（含 starlette/uvicorn 链），进 core
直接破 `dependencies = []`；且 dsh 的 churn 按硬纪律 6 必须关在 Provider 层。

**否决：让 cockpit 直接吃 `Software`（不做 seam）。** 传输层与装配点耦合后，判据测
这个端点就必须起整台软件（含引擎与写租约），而纯内存假源足够测；`MonitorSource`
让 seam 显式、让"缺哪一项"在类型与报错上都可见。**注意本 ADR 仍让首参接受
`Software` 直传**——便利性与 seam 显式性两件事可以并存（适配发生在入口，不在内部）。

**否决：给 `Engine` / `Software` 加配置 schema 方法，让 cockpit 一处取全。**
ML 没有这层 schema，加必实现会逼它编造行（它明文拒绝"凭空造树把面板撑满"）；
加可选字段等于把回退值藏进 Definition（D-17 的反面）。

**否决：把 `status_extra` 的四个运行期字段本轮就提升进核心。** 它们是宿主生命周期
事实，且核心一旦认了 `pid` / `mcp_port` 就等于承认"一台软件只有一个进程、只有一个
MCP 端点"——那是把某个部署形态焊进"通用"里（D-6/D-7 同族）。登记为后续候选并给
触发条件，比现在猜更符合"推迟不许沉默"。

**否决：附加路由失败返回"如实空表"（ML 现行）。** 空表与"确实没有数据"在 wire 上
不可区分 ⇒ 面板显示"没有运行记录"而真实原因是读盘失败，是典型假绿。框架不在传输层
重新引入这个反模式。

**否决：`before` 只 fold `since_seq` 窗口（更省事的写法）。** 增量轮询会把 `before`
渲染成 `∅ → 新值`，且**没有任何自动判据会红**——只有人肉看面板才可能发现。本 note
把它升级为"必须 fold 全史"并配致死性判据（构造窗口内无前值、全史有前值的场景）。

**否决：MCP 的 `required` 从 `execute` 签名派生（EL 现行）。** 写工具是 `**kwargs`
包装 ⇒ 派生空集 ⇒ 必填在模型面静默消失（P1-8 的同一类缺陷，已经实测过）。

**否决：失败用 `raise ToolError(json)` 或返回错误文本。** 前者正文被加
`Error executing tool …` 前缀（模型读到散文而非 `kind`）；后者 `is_error=False`，
成为"成功文本里写着错误"的假成功（D5 大忌）。

**否决：监控端点带鉴权 / 保留 `POST` 写与切模式路由。** 读的是操作流水，不是域
数据覆写面；加鉴权会把"AI 不能自授权"的护栏从 `Authority` 的 side 判定挪到一个
token 上（v1 的 `.human-token` 已退役一次）。写与切模式归看门人的进程交接，端点
保持只读才能让"只读"成为可机械验证的红线（`POST` 恒 404）。

**否决：把端口文件规则留在两个宿主里各一份。** 它带安全论证，两处各写一次＝两处
可各自漂移的安全论证。

**否决：本轮连实现一起做而不先冻结接口。** 接口冻结是主代理设的确认闸门；先冻结
再实现，避免实现形状反过来定义契约（ADR 制度 §3.5：与现实冲突时先改 note 再改码）。
