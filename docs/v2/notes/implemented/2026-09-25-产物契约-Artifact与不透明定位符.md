# 产物契约：宿主产物只以不透明 locator 进入核心

> **状态**：implemented
> **作者**：ML×mecha 衔接（Lead）
> **日期**：2026-09-25

## Problem

第二个真实宿主（ML Toolbox）的运行产物——一次长任务产生的模型文件、指标
序列、中间张量——**只活在宿主进程的内存里**。命令面同步返回的 `result_ref`
与 Job Contract 的 `result_ref` 都只能挂**引用**，可引用指向哪里？

现状逼出的三条可观察事实：

1. 宿主没有"把大对象交给框架、拿回一个引用"的通用入口。可选做法只剩两个：
   要么把产物内容塞进 `result_ref`（回执与 History 会被大对象撑爆，且
   append-only 日志不可接受这个体积），要么宿主自己造一套"产物表 + 自增
   id"，于是**第二个宿主各自发明一套引用机制**——正是 v1 血统标签漂移的同款
   病：同一概念多个来源。
2. 现有 `providers/spill.py` 的定位符**也是**不透明的 `$<id>`，形状上像，但
   它的判断依据是**体积阈值**（`should_spill`），载荷是 `str`，服务对象是
   "核心自己产生的回执/日志太大要截断落盘"。宿主产物不是核心产生的文本，
   没有阈值可言（一份 2KB 的检查点也必须原样保存），而且它是 `bytes`。
3. 若把"产物落盘"直接摊给宿主，宿主会顺手把**真实路径**写进 `result_ref`
   与 History：路径一旦进日志就固化进 append-only 史，目录搬迁、数据目录
   改名、换机器都会让历史引用变成死链，而 append-only 不许改写。核心则被迫
   在守卫里理解"哪个目录是合法的产物目录"——核心开始理解宿主布局。

## Decision

新增 `mecha/artifacts.py`（additive，不动既有 Definition），把"宿主产物托管"
定成 Provider 层的一个 seam：

1. **Definition**：`ArtifactStore` 只声明四个操作——
   `put(payload: bytes, *, kind="", name="") -> locator`、
   `retrieve(locator) -> bytes`、`describe(locator) -> Mapping`、
   `exists(locator) -> bool`。载荷是 `bytes`（逐字节往返，无隐式编解码），
   不是 `str`。
2. **local Provider**：`LocalArtifactStore(layout)` 写
   `<data_dir>/artifacts/artifact-<n>.bin` + 同名 `.json` 元数据
   （`locator`/`kind`/`name`/`size`/`sha256`/`created_at`）。locator 是
   `artifact-<n>` 的**不透明句柄**：核心只拿它做**格式**校验（拒路径、拒任意
   字符串），路径由进程内映射给出，**对外绝不暴露**。
3. **fail loud**：未知/畸形 locator、以及盘上文件被外部删掉的 locator，
   `retrieve`/`describe` 一律抛
   `MechaError(kind="bad_artifact_locator")` + 教学 hint。**禁止**静默返回
   空产物——那会把"引用丢了"伪装成"产物是空的"，是最坏的一类失败。
   `exists` 是唯一的例外：问存在不是问错，不可取回即 `False`。
4. **核心不解释 `kind`/`name`**：两者是不透明的宿主标签，核心原样保管、原样
   回读，不做校验、不做枚举、不据此分派。核心**禁止**知道任何宿主产物类型。
5. **不做删除 / GC**（明确决定，不是遗漏）：删除是宿主的保留策略。
6. 装配：`Software.artifacts` 字段 + `declare_roles` 登记
   `provider.artifacts`（DEFINITION）与 `provider.artifacts.local`
   （PROVIDER, `local-file`）；`provider.artifacts.local` 当前**无内置消费者**，
   按既有纪律进 `capability_map_selfcheck.DEFERRED_PROVIDERS` 显式登记推迟
   （不许沉默推迟）。
7. 判据 `checks/phase8_artifact_contract_selfcheck.py` 进 `run_all`：不透明、
   逐字节往返、元数据不撒谎、fail loud 且 kind 正确、≥1MiB 大载荷、多产物
   互不覆盖（含并发 put）、装配路径 L7 对偶。

## Consequences

**换来**：宿主有了通用产物入口，`result_ref` 与 History 里只出现不透明
locator；领域真值（产物内容 + 类型语义）**全部留在宿主自己的数据目录**，
核心的引用面与内容面解耦。第二个宿主不再自造引用机制，第三个宿主接入时同一
套四操作即可。产物落在宿主数据目录内，写租约与"域状态不出目录"的既有约束
自动覆盖。

**付出**：磁盘只增不减（无 GC，见下）；`_map` 是进程内的，进程重启后旧
locator 在新实例里不可用（元数据 sidecar 已含重建所需全部字段，但重建索引
未实现）；`put` 持一把进程内锁串行化 locator 分配与落盘（产物是大对象，
写入本身是主要成本，锁不构成新瓶颈）。

**放弃了什么**：放弃把产物内容或真实路径写进 History/`result_ref`；放弃让
核心校验 `kind`/`name` 的取值集合（那需要核心持有宿主类型表，直接违反
"核心不写领域词"）；放弃内置 GC 与保留策略；放弃"locator 跨实例稳定"的
承诺（不承诺，就不会有人依赖它去拼路径）。

**实现期发现（诚实记录）**：首版 `retrieve` 误读了元数据 sidecar 而不是
`.bin`，由本 ADR 配套判据的"逐字节往返"当场抓红（空载荷回 215 B）。这正是
"往返必须比字节、不能只比长度"的实证：只断言 `len(got) > 0` 会让它绿着上线。

**推迟项（各绑可判定触发）**：

- **跨重启找回 locator**（扫 `artifacts/` 按 id 重建索引）。
  **触发**：出现"进程重启后仍需用旧 locator 取回产物"的真实调用方。
- **dsh 侧 Provider**（把产物交给 dsh 的宿主句柄）。
  **触发**：有真 dsh 宿主进程可注入句柄、且宿主产物确实需要跨进程回程。
- **GC / 保留策略**。**触发**：出现第一个因产物堆积而真实耗尽磁盘的部署，
  或宿主明确提出保留窗口需求——届时也优先做在宿主侧策略里，而非核心。

## Alternatives considered

**否决：复用 Spill（把 `SpillStore.put` 扩成接 bytes、去掉阈值）。** 两者的
不透明定位符只是**形状**相同，语义正交：Spill 的输入是**核心自己产生的
文本**，其存在理由是"超过阈值就别塞进回执"；Artifact 的输入是**宿主的产物**，
核心不知道它是什么、多大、什么格式，任何阈值都是越界猜测（一份 2KB 的检查点
和一份 2GB 的权重同等重要）。合并的后果有两个且都不可接受：核心被迫理解
"哪些载荷该落盘"（宿主语义），以及 `should_spill` 这个回程投递概念污染宿主
产物契约。共用形状可以，共用 seam 不行。

**否决：让 locator 直接是相对路径（如 `artifacts/artifact-7.bin`）。**
路径进 `result_ref`/History 即固化进 append-only 史，目录搬迁或换机器后历史
引用集体变死链，且 append-only 不许改写——错误不可逆。更糟的是它把"数据目录
布局"升格成对外契约：宿主一旦按路径拼，核心就再也不能改布局。不透明句柄 +
"没有按路径取的入口"让这种依赖在结构上不可能（判据实测 locator 既不含路径
分隔符，也不是可打开的真实路径）。

**否决：核心解释 `kind`/`name`（做枚举校验或按 kind 分派）。** 那要求核心
持有宿主产物类型表，等于把领域词写进机制层——本仓硬约束与
`checks/vocabulary_selfcheck.py` 的存在理由。且每个新宿主类型都要改核心，
与"边界写机制不写分类"直接冲突。核心只保证"存进去的字节与标签原样回来"。

**否决：核心内置 GC（按大小/时间/引用计数清理）。** 删除的正确性依赖核心
不知道的信息：产物是否还被某条历史引用、宿主是否还在用、保留几个版本。
核心猜错就是**静默删掉用户真值**——比磁盘涨满严重得多。保留策略是宿主的
运维决策，核心只提供"取回"与"元数据（含 sha256）"两个只读事实，让宿主自己
判断该删什么。

**否决：把产物塞进 `result_ref` 本身（小产物内联）。** 内联会让回执与
append-only 日志的体积随产物增长，且"多大算小"又要一个阈值——阈值一旦进
核心，就又回到 Spill 的越界问题；且内联/引用两种形态会让消费者写两条分支。
统一走 locator，形态只有一种。
