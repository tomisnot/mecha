# 声明必须被消费：三态表 + L1/L2/L3 守卫

> **状态**：implemented
> **作者**：mecha v2（本会话抓到四处「声明与行为不一致」之后的收口）
> **日期**：2026-09-26

## Problem

本会话连抓四处「**声明与行为不一致**」，**四处都是人读代码发现的**：

| 声明 | 实际情况 |
|---|---|
| `CommandSpec.approval_required` | 没人拦（已修：真拦 + fail closed） |
| `CommandSpec.scope` | 框架**有**消费者（`scopes.py`），但**项目没绑** ⇒ 不生效 |
| `kind="read"` | 却在写账（项目侧，已修） |
| CodeAct 文档"动作集 = Surface 已注册项" | 代码只到四个内置 + 注册的 `query` 项 |

⇒ 共同形态：**声明存在，但没有任何一处代码/判据依赖它**。⇒ 能不能**机械可见**？

## Decision

在 `checks/capability_map_selfcheck.py`（**已有的"真实消费者"守卫所在的同一个文件**）
加一组 **`check_declarations_are_consumed`**，配一张**三态表**：

* `consumed`：有消费者（**符号 + 文件**）+ **点名一条判据**；
* `deferred`：今天没有消费者 ⇒ **必须给理由**（"推迟不许沉默"，与同文件既有的
  `DEFERRED_PROVIDERS` 同一纪律）；
* `undecided`：被消费了但**语义还没定**（如 `MonitorView.disputed` 的
  "概括器失败算不算存疑"）⇒ 进**待办清单**。

三层断言：

* **L1（枚举驱动，强）**：声明面**从活对象枚举**（`__dataclass_fields__` / `__members__`），
  每个名字都必须在表里有行 ⇒ **新声明没表态 ⇒ 红**。
* **L2（grep，强）**：`consumed` 行的消费者符号必须**仍在**点名文件里（非注释行）。
* **L3（存在性，中）**：`consumed` 行点名的判据必须**真的存在于 `checks/`**；**空栏即红**。

**枚举源（L1 的输入，逐个列出）**：`CommandSpec` / `ToolDefinition` / `Mode` /
`MonitorView` —— 全部经 `dataclasses.fields` 或 `Enum.__members__` 现取，
**不手抄**；`ENUM_SOURCES` 是唯一的"手抄位"，所以它自己也被 L7 对偶钉住。

## Consequences

**换来**：新声明必须表态；消费者被改名/删除会红；每条"有消费者"必须点名一条真实判据。

**付出 / 放弃**：

- **放弃了"引用即消费"的宽松**：新增一个声明字段要**多写一行表 + 点名判据**（成本 +2 行）。
- **放弃了用 AST / 类型检查做更深的证明**：成本高，且与 L1/L2 的收益重叠。
- **放弃了把 `undecided` 当红**：那会为"**还没决定**"制造假红 ⇒ 代价是待办可能被忽略
  ⇒ 用"**每次运行都打印待办清单**"缓解（不放行、也不红，但**一直看得见**）。

## ⚠ 覆盖边界（别当万能药）

1. ⚠ **"项目没绑"框架侧抓不到**：`scope` 的真身是"项目没注入 `ScopePolicy`"——
   在框架里那一行**完全合法**（有消费者、有判据）⇒ **红不了**。
   ⇒ **抓它的正路是项目侧判据**（框架看不到项目的装配）。
2. ⚠ **"有引用" ≠ "可达"**：`if False:` 里的调用、永不为真的分支，grep 看不见。
3. ⚠ **"文档声称 > 代码事实"**：表只覆盖**代码里存在的声明**；文档承诺得靠人工对账。
4. ⚠ **值级语义错**（字段在、也被消费，但语义与预期不符）⇒ 只有**行为判据**抓得到。
5. ⚠ **`undecided` 不是通过**：它只是"还没决定"的显式登记。

### 项目侧自查的形状（给"声明了却没绑"的项目，框架不代劳）

> **判据形状**：本项目注册的命令里**若有 `scope` 非空** ⇒ **断言装配时注入了 `ScopePolicy`**；
> **验法**：让一条声明了 `scope` 的命令经 **AI 侧**通道调用——
> **没绑时**它会**成功**（unused declaration 静默通过）⇒ **判据红**；
> **绑上且未授权时**它应拿 `scope_denied` ⇒ **判据绿**。
> ⇒ **双向**：没绑红、绑上绿（证明判据不是哑的）。
> ⚠ 这是**项目侧**判据：框架**看不到**项目在装配点绑了什么，只能在框架侧证明
> "字段有消费者"（本组 L2/L3 做的正是这一半）。

## Alternatives considered

**否决：只写文档、不上守卫。** D4 已定："手抄名单必须配守卫"——文档拦不住漂移。

**否决：把守卫放进一个新的判据文件。** "声明→消费者"与既有的 `DEFERRED_PROVIDERS` /
`CONSUMER_SYMBOLS` / `_real_consumer_files` 是**同一件事**（同一个守卫族）⇒ 分两处必然
出现两份真值（本仓 D 系列要治的病）。

**否决：引入 AST / mypy 级分析证明"字段真被读"。** 成本高一个量级，而收益与
"L2 + 一条具名行为判据"重叠；真要有保证，靠的是**每条字段一条行为判据**（A1 就是这么做的）。

## Required verification

- `python checks/run_all.py` **全绿**（22 项）。
- 本组四条断言：L1（23 个声明字段全部有行）、L2（20 条消费者符号都在）、
  L3（20 条都点名真实判据）、L7 对偶（未登记的名字会被抓 + 假符号 0 命中）。
- 红证（隔离调用，**自证扰动落上**，三条各一次）：
  ① 给 `CommandSpec` 临时加一个字段 ⇒ **L1 红**（`brand_new_flag` 没表态）；
  ② 把某行的消费者符号改成不存在的 ⇒ **L2 红**；
  ③ 把某行的判据名改成不存在的 ⇒ **L3 红**。
