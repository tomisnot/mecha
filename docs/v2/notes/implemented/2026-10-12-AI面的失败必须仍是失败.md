# AI 面的失败必须仍是失败（`is_error` 真名 + 聚合面抬升）

> **状态**：implemented
> **作者**：主代理（在 tutor 的**真链路**判据里抓到的两处恒假/降级）
> **日期**：2026-10-12

## Problem

**现象（tutor 真链路实测，2026-10-12）**：经聚合端点调一个**注定失败**的工具，AI 那一侧
拿到的是**成功**——失败正文被塞在 `value` 里。链路：

```
tutor 工具抛 MechaError → providers/mcp._error_result ⇒ CallToolResult(is_error=True)  ✅ 对的
   → mcp_client._normalize_result：getattr(res, "isError", False)  ⛔ 该位恒为假
   → aggregate._backend_tool.execute：把 {is_error, text} 当**值**返回  ⛔ 聚合面永不失败
   → AI 的宿主看到 isError=False（"调用成功"）
```

两处独立缺陷，**都违反本仓自己写下的契约**：

1. ⛔ **`mcp_client._normalize_result` 读错了字段名**。mcp 2.2 的 `CallToolResult`
   **真名是 ``is_error``**（驼峰只是**序列化别名**）⇒ `getattr(res,"isError",False)`
   **恒为假**。这正是 **R11**"观测量必须能变"写下的那一课（原话就是
   "字段真名是 `is_error`（`isError` 只是序列化别名）⇒ 该项恒为假"）——
   **本仓第三次栽同一个坑**（前两次：EL 判据、三层架构口径 3）。
   ⇒ 后端的域失败在聚合面上**全被读成成功**。
2. ⛔ **聚合面把后端的失败"降级成值"**。`_backend_tool` 直接返回后端回执 ⇒ 即使第 1 条修好，
   AI 的宿主看到的仍是 `isError=False`（要自己去 `value.is_error` 里找）。
   而 **AI 调用体验 §P0-3 的判据**明写："失败回执 `isError=True` 且正文可 JSON 解析出
   `info.kind`"——那正是本工程记过的最贵一类缺陷（"差点把参数崩了当成实验结论"）。

**为什么一直没被发现**（比缺陷本身更值得记）：失败透传**只用假 Backend 测过**——
替身直接返回普通 dict，**绕过** `_normalize_result` 这一层，于是那句错误代码
**从没被执行到**。这是"**判据不许用替身测真路**"（本工程最贵的一课）的又一实例。

## Decision

**两处一起修，都用真链路判据钉住**：

1. `mcp_client._normalize_result`：**先 snake（`is_error`）、再驼峰（`isError`）兜底**
   （与同文件 `_fetch_tools` 读 `input_schema`/`inputSchema` 同一写法、同一理由）。
2. `aggregate._backend_tool`：后端回执 `is_error` 为真 ⇒ **抛 `MechaError`**
   （新函数 `_raise_backend_failure` 把后端正文里的 `message` / `info.{kind,hint,suggest}`
   **原样抬到顶层**）。`ToolRegistry.execute` 再把它归一化回
   `{is_error: True, error: {message, info}}`——**与后端自己发的那个形状一致**，
   所以 AI 在两跳上看到**同一套词汇**。
   ⚠ 正文解析不出来也**照样失败**（用原文当消息）："看不懂的失败"仍然是失败。

## Consequences

- **换来**：AI 在聚合面上**第一次真的能看到**每个软件的域失败（含 `kind`/`hint`），
  与它直连单个软件时看到的是同一套；P0-3 的判据对**四个仓**同时成立。
- **付出**：聚合面的失败**不再是"成功 + 失败正文"** ⇒ 任何依赖旧形状（去 `value.is_error`
  里找）的消费者要改。⚠ 已核查：仓内无此消费者（`aggregate_selfcheck` 的 `_call` 一直
  把 `is_error` 当失败读，正是因为**它本来就是这个契约**）。
- **风险与对策**：抬升会**丢掉**后端回执的原始 `text`（只剩 `message`）。
  ⇒ `_raise_backend_failure` 把解析不出的正文**整段**放进 message（不截断丢信息）。
- **不做**：不做"两类失败混一起"——后端**域失败**（`is_error`）与**连不上/超时**
  （`BackendConnectError`/`BackendTimeoutError`）仍是**分开**的三档话术（那是 2026-10-10
  真机修过的，本次不动）。

## Alternatives considered

- **只修字段名（第 1 条），保留"失败塞进 value"**：否决——那只让 `value.is_error` 变真，
  AI 的宿主层看到的**仍是成功**；P0-3 的判据要求的是**回执位**，不是"值里有个字段"。
  实测证据：修字段名之前，`Backend.call` 返回 `{"is_error": false, "text": "{...ok:false...}"}`。
- **让聚合面把后端失败原样重发（当成自己的 `CallToolResult(is_error=True)`）**：
  否决——那要绕过 `ToolRegistry`/`ToolHost` 的归一化缝，"失败形状"就有了**第二处**实现；
  抛 `MechaError` 走既有缝，形状仍只有一处。
- **在 `Backend` 层就把失败抛出去**（不给调用方看回执）：否决——`Backend` 是**传输**层，
  它的回执形状是既有契约（`aggregate_selfcheck` 的假后端也在照它写）；改它等于动
  Provider 契约，收益与风险不成比例。
- **只在假 Backend 里加一条失败用例**：否决——那正是**原来漏掉**它的原因；
  ⭐ 本条的守卫必须在**真 MCP 链路**上（`Backend.connect` + `call`）。
