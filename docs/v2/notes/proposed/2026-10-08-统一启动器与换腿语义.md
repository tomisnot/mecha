# 统一启动器与换腿语义

> **状态**：proposed
> **作者**：总设计师（与用户共同裁决）
> **日期**：2026-10-08

## Problem

mecha 生态三个项目（ML Toolbox / Energy-Level / Get Paper）**各有各的启动方式**，
且各自都出现同类故障。可观察的事实（全部实测）：

- **黑框**：EL 与 ML 的 `launcher.py` 里**逐字相同**的一行
  `_FLAGS = getattr(subprocess, "CREATE_NEW_CONSOLE", 0)` ⇒
  **每个子进程一个新控制台窗口**（AI 模式 4 个）；普通用户"看着就晕"。
- **假绿**：EL 的就绪判据只要端口文件"存在且非空"。实测现场该文件是
  **264.5 小时前**的残留、**没有任何进程在听**，而它**会被判定为就绪**；
  超时后还**照常**启动 harness。
- **孤儿**：只 terminate 直系子进程 ⇒ harness 经 `cmd.exe` 派生的 `node`
  变成**仍持有端口的孤儿**，导致端口"莫名被占"、端口选择一路漂移。
- **状态自相矛盾**：运行时描述文件里写的 harness 端口是**预选值**，
  不是它实际绑定的端口。
- **用户被迫做无意义的选择**：从 mecha 启动时问"AI 模式还是 GUI 模式"，
  而"从 mecha 启动"本身就已经蕴含"带 AI"。
- **无法同时用多个项目**：每个项目各自拉起一个 harness 实例、各占一个端口，
  AI 无法在一个 harness 里使用多个软件的能力。
- **结构重复**：两个 `launcher.py` 的编排骨架**函数名几乎一一对应**
  （起进程组 / 选模式 / 等就绪 / 挑端口 / 起 harness / 收尾 / 意图文件读写）。

## Decision

1. **从 mecha 启动永远是 AI 组**。**禁止**实现"启动模式选择"
   （`choose_mode` / 意图文件 / 状态文件 / "两模式整组重启交接"协议一律不得存在）。
   需要纯人工操作的用户**不使用 mecha**，直接找项目自己的入口。

2. **进程编排归框架**：新增 supervisor，项目只提供**声明**
   （`mecha_site.py` 暴露 `SITE: Site`）。项目侧不再保留任何编排代码。

3. **对 harness 只挂一个稳定的聚合端点**。开/关软件 = 该端点改变自己的工具表
   并发出工具表变更通知（harness 支持热同步）。**禁止**要求 harness 在运行中
   更换 MCP 服务器配置。

4. **同一数据根同一时刻只允许一条腿在跑**。
   `Supervisor.switch_leg(stop_id, start)` 必须**先停、等真退出、再起**；
   **顺序不得颠倒**（颠倒必然因写租约被占而失败）。

5. **"切手动"的语义是"交出写权 + 换一条腿"，不是"两条腿同时活"**。
   状态连续的判据是**账不断**（账只追加，当前状态是它的折叠），
   **不是**两个进程共享内存。

6. **就绪必须是真探活**：spawn 前记端口文件快照，要求"文件消失过或内容/修改时间变了"，
   再做真实的 HTTP 或 TCP 探测；超时**响亮失败**。**禁止**以"文件存在且非空"判就绪。

7. **零黑框，且日志必须留**：子进程一律不开新窗口，标准输出与错误
   **重定向到 `runtime/logs/<id>.log`**（带滚动上限）。**禁止**丢弃（不得指向空设备）。

8. **实际端口必须回读**。声明里的端口只表达**偏好**；状态里的端口一律是绑定结果。

9. **状态只有一个真值来源**，且"读不到"与"确实没有"必须用不同措辞。

10. **业务核心不得改动**：门 / 账 / 监控面 / 能力面 / 投影**一行都不改**。
    启动编排是独立于业务的一层。

## Consequences

**换来**：
- 三家入口统一为一个可双击文件；**黑框归零**（从 2–4 个到 0）；
- 假绿与孤儿端口在**结构上**不可能再出现（判据钉死）；
- 一个 harness 同时使用多个软件的能力；**运行中**可开关软件；
- 项目侧的编排代码被声明取代（其中一家 834 行的编排文件整体作废）；
- 用户不再面对无意义的选择，改为"勾要接入哪些项目"。

**付出**：
- 框架新增进程监督这一面（此前框架**完全不碰进程**），并因此新增一个
  常驻的聚合端点进程；
- 每家的测试与文档都要跟着改（其中一家有两个测试硬编码旧入口名）；
- ⚠ **"换腿"不是零成本**：切换期间那一组进程**真的会停一次**，
  人看到的连续来自"账不断"，**不来自进程不重启**；
- ⚠ 聚合端点必须自己处理"后端已关闭"的调用（**响亮失败**，
  而工具表在通知到达前仍有陈旧窗口）。

**放弃了什么**：
- 放弃"两条腿同时活"（被框架的写租约硬约束否决，见 Alternatives）；
- 放弃"启动时选模式"（被"从 mecha 启动即带 AI"否决）；
- 放弃跨软件共享状态（用户裁决）；
- 放弃给 AI 启停进程的权力（进程生死归 supervisor，AI 只能请求开/关软件）。

## Alternatives considered

1. **两条腿同时活**（AI 与 GUI 进程同时持有同一条脊椎，切换只换渲染）。
   否决理由：框架的写租约是**操作系统级独占文件锁**，抢不到即响亮失败 ⇒
   同一数据根**只能一个写宿主**。且一家的 GUI 需要其桥对象的二十余个方法，
   要让它变成网络客户端就得**先补齐一大片能力面**（那不是"接线"）。
   正解改为"换腿 + 账不断"。

2. **保留启动模式选择，只是把它做成图形化**。
   否决理由：与"从 mecha 启动即带 AI"重复；用户要纯人工操作时根本不该走这条路。
   保留它只会继续制造"这个模式到底锁了什么"的困惑。

3. **每家保留自己的启动器，只抽取公共函数成库**（不引入 supervisor 进程）。
   否决理由：跨项目的聚合端点需要**统一知道谁在跑、谁是实际端口**；
   没有单一监督者时，工具表与状态必然出现第二份真值（违反 Decision 9）。
   且"关掉软件"必须能落到进程操作上，那需要一个共同控制面。

4. **让某个软件兼做聚合端点**（谁先起谁当）。
   否决理由：软件之间会形成主从关系，且该软件死掉时整站能力面塌掉。

5. **不做聚合端点，直接让 harness 挂多个 MCP 服务器**。
   否决理由：harness 的服务器配置**在会话创建时固定**，
   不支持运行中更换 ⇒ **无法在存活期间开关软件**，而这是本需求的硬要求。

6. **为不支持动态工具表的客户端提供代理兜底工具**（某成熟聚合器的做法）。
   否决理由：已核实本 harness **支持**工具表热同步，
   兜底工具会白白增加一层间接与一个工具位。

7. **保留 `pick_dsh_port` 的"先绑定试探再释放"**。
   否决理由：存在检查与使用之间的竞态窗口。改为绑定后把结果交给子进程，
   或让子进程自选后回报。

## Required verification

1. **接口冻结件**：`mecha/supervise.py` / `mecha/site.py` / `mecha/launch.py` /
   `mecha/providers/status_page.py` 的公开签名与本文 Decision 第 1–9 条逐条对齐
   （评审：读签名，不必跑代码）。

2. **机械判据** `checks/launch_selfcheck.py`（用 mock 子进程），其中
   **以下三条必须先看到红、再变绿**，并把红的输出留证：
   - 预置"内容非空但没人听"的端口文件 ⇒ 必须超时报错，**绝不判就绪**（对应 Decision 6）；
   - mock 派生孙进程 ⇒ `stop()` 后孙进程也死，端口文件无残留（对应 Decision 7 与铁律 3）；
   - 同一数据根的 child **不许同时运行**；`switch_leg` 顺序颠倒必须
     以写租约失败**响亮**报错（对应 Decision 4/5）。

3. **黑框归零**：跑真子进程后断言无新控制台窗口，且标准输出出现在
   `runtime/logs/<id>.log`（对应 Decision 7）。

4. **端口真实性**：mock 绑定随机端口后，状态里的端口等于其绑定结果
   （对应 Decision 8）。

5. **端到端**：`python -m mecha.launch --dry-run` 打印的启动计划中，
   顺序为"各软件 → 聚合端点 → harness"（对应 Decision 3 与启动顺序）。

6. **三家回归**：三个项目各自的判据在删掉本项目启动器后全绿；
   ⚠ 特别检查两处易静默丢失的承接（UTF-8 输出编码注入、数据根白名单）
   在删除前后行为一致。

7. **文档一致性**：三家里描述"启动模式"的章节被删除或改正，
   不得留下仍声称"启动时可选 AI/GUI 模式"的文字。
