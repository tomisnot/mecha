## 0. ⚠ 施工顺序的原则：先证伪，再铺开

这套架构有**两个可能致命的前提**，它们**必须先实测**。
若不成立，整个新架构要重新设计 ⇒ **先别让三家动代码**。

| # | 致命前提 | 不成立的后果 |
|---|---|---|
| **P1** | **软件进程能同时提供 MCP 服务与 PyQt 窗口**，且互不干扰 | 裁决 1（GUI 在进程内）**不成立** ⇒ 要退回"独立客户端" |
| **P2** | **写权切换"立刻生效"**：切到 HUMAN 后 **AI 的下一次写被拒**、人在同一进程里立刻能写 | 需求 4（可反复切）**做不到干净** |

⚠ P1 还带着一条**具体的历史雷**：项目里记着
*"lightgbm 必须先于 PyQt5，否则其 OpenMP 与 Qt 冲突 ⇒ fit 时 access violation"*。
新形态要求在**跑业务逻辑的进程里启动 Qt** ⇒ **这条必须实测**。

⇒ **步骤 0 = 只做 P1/P2 的实测**（EL 最合适：它已有 `for_shared`（人机同门装配）
与一个现成的 PyQt 主窗口）。**这一步不改功能代码**，只写一个验证脚本 + 判据。

## 1. 步骤 1 · 框架：撤掉"换腿"，补"重启"，声明改形

### 1.1 `supervise.py`

| 动作 | 内容 |
|---|---|
| ➖ **撤** | `switch_leg`（"停一条腿→起一条腿"）的**定位**——它现在是"换操作者"，而新架构里**操作者不换进程** |
| ➕ **补** | `restart(child_id)` 的正规语义（**已有基础**：`start()` 对已停/已退出 id 会重启，判据 ⑦ 已钉） |
| ⚠ **保留** | 写租约互斥（它是**软件自己**的锁；同一 `data_root` 两个软件仍必须互斥） |

⚠ **撤 `switch_leg` 时不许顺手撤掉判据**：那些断言里"停→等真退出→起"的**时序**仍对
"**重启**"有用（重启也要先停干净、等租约释放）。⇒ **改的是名字与用途，不是机制**。

### 1.2 `software.py`（新）/ `site.py`（改）

```python
@dataclass(frozen=True)
class Software:
    id: str
    brief: str
    argv: tuple[str, ...]          # 起【软件自己】—— 状态 + 能力面 +（可选）GUI 窗口
    cwd: Path
    data_root: Path
    ready: ReadySpec
    initial_mode: Mode = Mode.LOCKED
    has_gui: bool = False          # ⭐ 决定面板显不显示"切到手动"
    env: Mapping[str, str] = field(default_factory=dict)
```

| 动作 | 内容 |
|---|---|
| ➖ **删** | `Service.manual: ChildSpec`（人那条腿**不是** child） |
| ➖ **删** | `Service` 里由 `manual` 带来的互斥校验（`manual_root_mismatch` 等） |
| ➕ **加** | `has_gui`（面板据此决定显示哪个控件） |

### 1.3 `launch.py`

| 动作 | 内容 |
|---|---|
| ➖ **删** | `AggregateRuntime` 里围绕"开/关另一条腿"的那套（若有） |
| ➕ **加** | 把 `initial_mode` 传给软件（**由启动者声明** —— 人是启动者，故合法） |
| ✅ **保留** | `prepare_hooks`（dsh 的 overlay 要等聚合端点端口出来）· 聚合端点接线 · 状态页接管 |

### 1.4 判据

| # | 判据 | 红证怎么造 |
|---|---|---|
| 1 | `start()` 对已停 id **重启**；对在跑 id **仍拒绝** | 去掉"已停可重启"那段 |
| 2 | 面板能列出**全部声明项目**，且 `has_gui=false` 的**不显示**"切到手动" | 把 `has_gui` 判断删掉 |
| 3 | 撤掉 `switch_leg` 后，**重启路径的时序**（停→等真退出→起）仍被钉住 | 把"等真退出"改成"立刻起" |

## 2. 步骤 2 · 项目：软件进程内加 GUI 窗口

### 2.1 EL（**最先做**：它已有全部素材）

| 素材 | 现状 |
|---|---|
| 人机同门装配 | ✅ `V2Bridge.for_shared`（GUI 与 MCP 服务器共享一个 Gate），且**是它判据在验的默认部署路径** |
| PyQt 主窗口 | ✅ `app_entry.py` 里现成的 `MainWindow` |
| 写权 | ✅ `bridge.switch_mode`（已有） |

| 动作 | 内容 |
|---|---|
| ➕ | `--mcp` 模式加一个**可选**的"同时开本机窗口"（例如 `--with-gui`，或由声明里的字段控制） |
| ⚠ **实测 P1** | 窗口开着时：**MCP 工具调用仍可往返**、**训练仍能跑**（那条 OpenMP/Qt 雷） |
| ⚠ **钉纪律** | **GUI 的写也过 `Gate`、也记账**（不许直接改内部状态）—— 加判据 |
| ➕ | 提供"切写权"的按钮（**调同一个 `switch_mode`**） |

### 2.2 GP

它已经是"**单进程一条脊椎**"（`build_stack` + `make_host`），Web 界面与 MCP 挂同一个 stack
⇒ **它最接近新架构**。要做的是：把"开一个本机窗口"接上（或确认它的 Web 面就算"GUI 腿"）。

### 2.3 ML（**最难，可能最后**）

⚠ ML 今天**没有门**：它的 GUI（PyQt）**从不经 mecha**，直接调 `runner.run_one`。
⇒ 新架构要求它"软件进程门化" ⇒ 那是**一次实质改造**：
把 GUI 的写路径接到门/账上（**它的 `api.Session` 是个现成的收敛点**，值得复用）。

⚠ 如实说清代价：ML 目前"谁都能直接调 `runner`"；门化后它**第一次拥有写权概念**。
⇒ 这不是"补一个声明"，而是**给 ML 补一层**（设计文档 §5.3 已记为"缺一层"）。
