## 1. 量东西时

| 症状 | 怎么认出 | 正确做法 |
|---|---|---|
| **行数/体积被系统性低估** | 同一文件量出**互相矛盾**的三个数（本仓 ADR 实测过 `459 / 537 / 638`），且漏算幅度约 20–27%；只在**中文**文件上出现 | 别用 `Get-Content \| Measure-Object -Line`。用**字节级** `\n` 计数（`open(p,'rb').read().count(b'\n')`）或 `(Get-Content -Encoding UTF8).Count`；记录数字时注明口径 |
| **中文文件读成乱码，并据此误判** | 输出里成片 `锟斤拷` 类乱码；随后得出"这文件是 GBK"之类结论（曾据此误判 `.gitignore`） | PowerShell 显式 `-Encoding UTF8`；**优先用 `read` / `grep` 工具**（它们按 UTF-8 解析，不经 shell 代码页）。乱码是**读数问题**，不是文件问题 |
| **相对路径静默指向别的仓** | 命令"成功"了，但结果对不上——因为 cwd 不是你以为的那个仓 | 一律**绝对路径**；跨仓操作（本仓夹在 `mecha` / EL / ML 三个并排仓之间）连"我在哪个仓"都要显式确认 |
| **清点会被 junction / 链接骗过，而且不报错** | 枚举结果与 `Test-Path` **互相矛盾**（实测：`Get-ChildItem -Recurse -File -Force` 清点 `SKILL.md` 得 **3** 份，真相 **4** 份——漏掉的那份在 junction 深处）；命令**不报错、不退非零** ⇒ "少了一份"看不出来 | 清点**必须交叉验证**：枚举 ⇄ 逐个 `Test-Path` ⇄ `Get-Item … \| Select LinkType,Target` / `fsutil reparsepoint query`。Windows 的**目录 junction 会被枚举漏掉**——EL 的 `.dsh/skills/energy-level` 正是一个 junction（指向 `skills/energy-level`）⇒ 两条路径读的是**同一个文件**，于是"镜像与权威逐字节相同"这类断言退化成**同一律**（R8 / R11 那一类：观测量恒定、不携带信息） |
| **`glob` 返回 0 个被当成「没有」** | 搜索「找不到东西」，而**你没先排除「找的地方是错的」**。实测：核验脚本从一个由 **PowerShell 5.1 `Out-File -Encoding UTF8`** 写的小文件里读目录路径——那个文件**带 BOM** ⇒ 读出来首位是 `\ufeff` ⇒ `glob` **静默返回 0**（报「0 个 wheel」） | 「没找到」必须先排除「基准/目标错了」（与 **T2 存在性检查的基准**同族）：① 优先**按内容搜索**而不是按路径 glob；② 打印**实际搜索的目标**（路径/模式）作为自证——**探针必须自证「它真的看到了它以为看到的东西」**（**R16 同族**：那管扰动真的落上了，这管真的看对了地方） |
| **验证脚本报「没命中预期」，而现象其实发生了** | 你的匹配对象是**你以为会打印的文本**，而输出里那一行只有**名字**。实测：红证探针拿**断言文本**去匹配 `node --test` 的 `✖` 行——而 `✖` 行**只有用例名** ⇒ **确实红了**，却被探针报成"没命中预期"（差一点把**成立的红证**判成无效，进而误判"守卫抓不住"） | **匹配稳定的标识**（用例名 / ID / 退出码），**不要匹配易变的呈现文本**（断言消息、措辞、格式）；并**把实际读到的原文打印出来**作为自证——这样"没命中"才能立刻区分为「**真没发生**」还是「**我读错了地方**」。⚠ 与 R16 方向相反：**R16 管「扰动真的落上了吗」，这条管「我看对了证据吗」**；共同点是**都要自证"我确证的对象真的存在"** |

## 2. 取证时

| 症状 | 怎么认出 | 正确做法 |
|---|---|---|
| **照文档下结论，结论是错的** | 你引用的那句话，**没人**在活代码/协议层验证过 | 关键论断**读活代码 / 探协议层 / 跑真链路**。本仓最贵的三次翻车都源于只读源码：`outputSchema` 源码 grep 零命中而 wire 上有；"两家端点字节级一致"实为多处分歧；"run_all 并行计时失真的同款"在本仓其实**不存在**（本仓是串行、且不打印计时）。**规则见 R3**，这里只提醒：**docstring 是全工程最不可靠的一层**，包括本仓自己的 |
| **"源码里没有"被当成"不存在"** | 结论的证据层级没写明 | 跨层结论**跨层取证**：源码 ≠ wire ≠ 面板渲染 ≠ 模型可见面。写明每条结论**取证到哪一层**（R3） |
| **容错写法吞不住异常** | `try` 里明明写了 `getattr(x, "y", None)` 或类似"安全取值"，却仍然炸 | `getattr(obj, name, default)` **只吞 `AttributeError`**；属性 getter 抛 `ValueError`/其它异常会**直接穿出**（本仓 `providers/mcp.py` 的 `request_id` 就是这种：进程内直调时 `Context.request_context` 抛的是 `ValueError`）。要真容错就显式 `try/except`，并**在注释里写明"这里为什么故意不修"**，防后人"顺手修好" |
| **「在某作用域内搜不到」被当成「不存在」** | 你的证据确实来自一次真扫描（「**仓内** 0 命中」），但写出来的结论是「**不存在**」——**作用域在推论里丢了**。有**外部资产**的项目尤其容易踩。 | 报告「不存在」之前，先**把作用域写进结论本身**：「**仓内** 0 命中」「**在 3 个候选路径里**都没有」。本仓实例：ML 的 `UI design/SKILL.md` 被报成「悬空指针」，实测**文件真实存在**于 `D:\desktop\UI design\`（**仓外**）——仓内检索是对的，**推论越界了**。真正的缺陷是**引用写法有歧义**（漏了 `D:\desktop\`，按仓根解析必为空）。**规则见 R3 的作用域强化** |
| **存在性检查的基准没说清** | 用 `Test-Path <相对路径>` 判断「仓内到底有没有这个文件」，而它其实是**相对 CWD** 的——命令成功、结论却可能被基准左右 | 判断「**仓内**有没有」用 `git ls-files`（以**索引**为准），不要用相对路径的 `Test-Path`；判断「**磁盘上**有没有」用**绝对路径**。**基准不同的检查不能互相印证，也不能互相否定** |
| **改了源码没重建：跑的是旧包，而且没人告诉你** | 改了 client 半的源码，**行为没变**；或者判据对着**旧产物**跑，得出"已修复/没变化"的结论。⚠ 实测证据：删掉某个导出后**旧包里还有它**、重建后**0 次** | **`lib/` 是 gitignore 的构建产物**，而 dsh 的 **client 半【永远】读 `lib/client.js`**（开发期的 `cordis.source.patch.yml` 只让 **host 半**读 `src/`）⇒ `git status` **看不见它陈旧**，而**判据读的是 `src/`** ⇒ **两边根本不是同一个东西**。正确做法：**改 client 源码后必须重建**（`npm run bundle`）；**判据若断言产物行为，先重建再跑**；更稳的做法是**把"产物是否比 `src/` 新"做成一条守卫**（那才是"我验的就是跑的那个"） |
| **把「当前恒真的真守卫」当成装饰删掉** | 你在清理「不可能失败的断言」（R11），把一条**当前**恒真的断言当装饰删掉——但它其实是**真守卫**。**两种要分清**：<br>① **结构上不可能失败**（装饰）：断言一个它**结构上不可能等于**的值。实例：`assert _text_sha256(<配置文件>) not in REFERENCE_SHA256.values()` —— 前者是配置、后者是代码/单测的哈希 ⇒ **恒真**；<br>② **在当前配置下为真、但换到它守的场景就红**（真守卫）。实例：`assert wrong_root != cli.PROJECT_ROOT` —— **当前**恒真（`parents[2]` vs `parents[3]`），但**有人把 `PROJECT_ROOT` 改回少一层时两者相等 ⇒ 红** | **判据不是「它今天会不会红」，而是「它守的那个缺陷被重新引入时它会不会红」**。做法：把**它声称守的缺陷人为重引入**（**R7/R16：并自证扰动真的落上了**），看它红不红——**红则留，不红则删**。⚠ 天真地套 R11 **会把回归守卫删掉**，而那**比留着装饰更坏**（装饰无害；删掉守卫有害）。⚠ 与 **R11** 配套：R11 要求观测对象**能**变化，这里补的是**变化发生在它守的场景里**，不是**每一刻**都在变 |

## 3. 验收与收尾时

| 症状 | 怎么认出 | 正确做法 |
|---|---|---|
| **gitignore 的文件逃出验证** | 你以 `git diff` / `git status` 为准宣布"已同步"，而**被 gitignore 的那份**（往往正是 AI/人真正加载的那份）仍写着旧值。<br>⚠ **它还会骗到验收动作本身**：`pip wheel` 会在**仓内**留下 `build/`，而 `.gitignore:11` 正是 `build/` ⇒ **按 `git status` 判「仓内无残留」就是假绿**（2026-09-26 实测；**这已是第三次被 gitignore 骗**——前两次是 EL 的 SKILL 副本与 junction，**这一次发生在我们自己的验收动作里**） | 验收**另跑一次不经 git 的全仓按内容扫描**（`Get-ChildItem -Recurse -File -Force` + 按内容匹配）。**AI 可见面**（SKILL / 提示词 / 面板文案 / 模型可见 description）**优先扫**——漂移代价最高 |
| **"全仓搜残留"扫漏了仓根文件** | 删除类改动的收尾 grep **只扫了 `mecha/` + `checks/` 与 `docs/`**，于是 `README.md` 的仓库地图里那行旧清单多躺了一整轮（A3 删 `spill` 时的真实实例：代码与 `docs/` 都改了，README 漏了） | R14 的"全仓"= **含仓根文件**（`README.md`、`pyproject.toml`、`.gitignore` 自身）**与隐藏文件**。做法：从**仓根**递归按内容扫（`-Force`），不要按"我以为文档都在 `docs/`"划范围；扫完**列文件清单**复核，别只看命中总数 |
| **对外声明的名单在撒谎，而没人拦** | 模块导入正常、门禁全绿，但 `from … import *` 抛 `AttributeError`，或"按名单枚举公开面"的工具列出一个**不存在的名字**（ML 实例：`monitor_http.__all__` 里列着已删的 `CORE_ROUTES`） | 任何**手抄的对外名单**（`__all__`、能力表、工具清单）都属这一类。两条出路：**(a) 删掉名单**，让单一来源（文件系统/注册表）说话——本仓 `mecha/__init__.py` 就是这么做并写明了理由；**(b) 非要留名单就配一条便宜且确定的守卫**（如 `set(__all__) <= set(dir(module))`）。**声明可以撒谎而无人拦**，这是"假绿"的一整类（规则见 R1 / R13） |
| **把红归给环境，其实是自己写的概率性断言** | 判据**偶发**红，而且 ⭐ **每次红的是不同的」包裹「测试**（**这是「同一底层用例概率性红」的指纹**）；单跑又绿。实测：`assert.ok(!/\d{2,5}/.test(body.error))` —— 而**错误文案本来就含出错文件的路径**，临时目录名**偶尔**带数字（`…panel-G05d6O` 含 `05`）⇒ **守卫靠概率** | **先把红归给自己，再考虑环境**。做法：① **别用「数字 / 字符类」去判一个可能含路径或随机后缀的文本** —— 改按**语义形状**判（如「不许出现 `127.0.0.1` / `http(s)://`」）；② **用指纹认它**：**偶发 + 每次红的包裹测试不同 = 底层有一条概率性用例**；③ **连跑 N 次 + 全量复验**才下结论。⚠ **这正是 R7 的反面（守卫靠概率）**。⚠ 同步盘的 `ReplaceFileW EIO` **确实存在**，但它咬的是**编辑动作** —— **别让它替你的概率性断言背锅**（本条是一次真实误归因的更正） |
