## 1. 我们在做什么，最终愿景是什么

### 1.1 三个东西的关系

```
Energy Level（EL）     一个 Rb-87 里德堡原子仿真软件（Qt GUI + Python 计算内核）
mecha（旧/v1）         把 AI 接进 EL 的框架：自带日志/任务/体积闸/写权门
mecha v2（要写的）     同一个职责，但重新定位——见 §5
DeepSeek Harness（dsh）一个成熟的 agent harness，AI 的宿主环境。我们**不是**它的作者
```

### 1.2 最终愿景（委托方原话，不可删改）

> **AI 在 dsh 里自然地调用各种工具，有原生的，有接入项目的，调用方便，仿佛是自己的手脚；
> 我们自己做的侧边栏之类的用于让人类监控 AI 在我们的软件里干了什么
> （有自己写的概括，有真实改不了的数据）；
> 软件也在运行，没那么依附于 dsh，只是操作者从人类变成了调用形式不太一样的硅基生命。**

这段话定了三件架构事实：

1. **dsh 和 AI 不是这套系统的架构，它们是这台软件的一个新操作者。** 软件有自己的门、状态、历史；人类从 GUI 进，硅基生命从工具进，**过同一道门**。
2. **侧边栏是第一交付物**（人类监控硅基操作者的主界面），不是附属。且它有两层信任：**自己写的概括**（派生，可能错）+ **真实改不了的数据**（权威）。
3. **软件不依附 dsh。** dsh 消失时，软件、数据、账、侧边栏全部照常，只少一个操作者。

### 1.3 由此推出的核心定位（v2 的全部出发点）

> **mecha 是「人机同门」：写入门、账、能力面、人类监控面。**
> **AI 适配器只是它的一个操作者适配器，和 GUI 平级——不是主子关系。**

⚠️ **这是 v1 犯的根本错误**：v1 把自己定位成"一台自给自足的 AI 框架"（自带 journal/jobs/spill/gate/archive），
以 dsh 为主语。结果是在 dsh 部署里出现**两套写权门**和**第二份真值**——见 §9 的两条洞。

## 2. 为什么从零重写，而不是改

### 2.1 审计结论（对 v1 全部模块做的定量判定）

| 命运 | 行数 | 占比 | 含义 |
|---|---|---|---|
| 换成 dsh 成熟件（删自研） | 708 | 15.7% | 纯重复造轮子：`jobs.py`/`codeact.py`/`autonomy.py`/`archives.py` |
| 保留但瘦身 | 2099 | 46.7% | 实现里混了 EL 特有约束：`ops.prepare/execute` 拆分只因 EL 的 SQLite 认线程 |
| 保留（dsh 无更好对应） | 719 | 16.0% | `registry.py`/`errors.py`/`hooks.py`/`cockpit/backend.py` |
| EL 派生，标血统等第二项目 | 971 | 21.6% | GUI 三件、gc 阈值、interlock、subscribe |

### 2.2 一个反直觉但关键的发现

**v1 的"模块级原创"是 0。** 它的原创全在**纪律**里，不在代码里：

- 「假绿比红更危险」——dsh 全文**没有**对应的成本不对称价值判断（它只有对称的 `fails loud`）
- 领域凝练 / 血统——dsh **没有**等价纪律（它的 `docs/config-catalog.md` 有 2973 行领域值）
- 可教学错误的「教学」取向——dsh 有更机械的版本，但不含这个价值判断

⇒ **重写不会丢原创。** 该丢的是 84% 的机制，该留的是 3 条纪律。这是"敢从零写"的前提。

### 2.3 为什么不在旧代码上改

- 要动的 84% 里，`ops`/`session`/`bus`/`server` **互为因果**（改 session 的快照语义会连带 ops 的产物、server 的回执）
- 31 个方法的 `EngineProtocol` 是历史的沉积物，逐个瘦身会反复碰到"某个旧消费者"
- **新对话没有旧代码的锚定效应**——它会按这份文档长，而不是按 v1 的形状长

## 3. 从 v1 保留什么（纪律清单，逐条带"为什么"）

**这些是设计与工程经验。设计不变量保留，工程方法按当前风险选择，不自动成为新增 check 的义务。**

| # | 纪律 | 为什么必须留 | dsh 有对应吗 |
|---|---|---|---|
| **L1** | **操作者无关的一道写入门**（人机同一路径） | 操作者会继续增加（人→AI→脚本→…），门只能有一道 | 结构上成立但**未成文**。我们的成文 + v2 的结构证据 |
| **L2** | **域状态史只能追加、快照可从它折叠出来** | 这是软件自己的历史，人操作时也写。可追溯、可撤销、可回放 | dsh 的 session log 同思路，但它是**操作者**行为史，我们的**域状态史**是另一份资产（见 §5.2 互引） |
| **L3** | **假绿比红更危险**（D4） | ⭐ **我们的原创。** 永远返绿的守卫比没有守卫更坏 | ❌ 没有。dsh 只有"一律报错"的对称规则 |
| **L4** | **可教学错误的教学取向**（错误消息是 LLM 的 UI） | AI 接入的 ROI 全在这里：一条能教它对的消息 ≈ 零试错成本 | 部分（"从模型视角写 + 逐字钉住"）——**互补，不是替代** |
| **L5** | **领域凝练 / 血统标注** | ⭐ **我们的原创。** 库是从一个项目抽出来的，不凝练就把那个项目的形状焊死在"通用"里 | ❌ 没有。dsh 从第一天就是框架，没这个原罪 |
| **L6** | **验证落在合适层级：纯逻辑、装配与协议各有用途** | v1 因此抓到三次"机制建好但装配没接"（`journal_files`/`_reject`/authority 接线） | ✅ dsh 有同款且更强：`REAL-composition test`（不许手搭 ctx） |
| **L7** | **测试使用可信期望与有效输入；复杂拒绝规则按需要加正反案例** | 只测"能抓坏"不够，还要证明它不是永远返绿的哑守卫 | ✅ dsh 有（snapshot corpus + 拒识清单） |
| **L8** | **减少手抄的重复事实；可生成的资料按需生成，散文计数不设门禁** | v1 为计数漂移付过两次账（18→16、16→17，每次五处手抄数字全红） | ✅ dsh 全部目录**生成**，禁止手写清单 |
| **L9** | **一件一提交；只提交自己路径；提交前看整个暂存区** | 多人共仓的纪律，v1 因此误卷过同事文件两次 | ✅ dsh 有 PR 纪律 |

**L3/L4/L5 是我们的原创，L6/L7/L8/L9 是被 dsh 印证的。全部保留。**

## 5. 新架构

### 5.1 四层 + 操作者适配 + Provider 层

```
┌────────── 软件自己的（不因操作者而存在）──────────────────┐
│                                                              │
│   Gate      写入门：谁能改、改之前验什么、改之后记什么         │
│   History   账：append-only、可折叠出快照、与人/AI 无关  │
│   Surface   能力面：这台软件能做什么（查询 / 变更 / 运行）    │
│   Monitor   人类监控面：概括层 + 原始层，可对账               │
│                                                              │
└──────────────────────────────────────────────────────────────┘
                            ▲
          ┌─────────────────┴─────────────────┐
          │                                   │
┌─────────▼────────┐             ┌───────────▼──────────┐
│ human adapter    │             │ ai adapter           │
│ → GUI (Qt)       │             │ → dsh ctx.tools      │
│                  │             │   + skill            │
│                  │             │   + systemPrompt     │
└──────────────────┘             └──────────────────────┘
                                            │
                          ┌─────────────────┘
                          ▼
┌─────────── Provider 层（dsh 的 churn 全落这里，可整层替换）──────────┐
│  Log      → dsh session event   /  local JSONL                   │
│  Jobs     → dsh ctx.jobs        /  local thread                  │
│  Approval → dsh ctx.approval    /  local Authority               │
│  （Spill 行已于 2026-09-25 收口轮删除：零消费者且无发起方；        │
│    「落盘 + 不透明定位符」由核心的 Artifacts 承担）               │
└──────────────────────────────────────────────────────────────────┘
```

### 5.2 五条 Definition（每条都是我们自己的稳定件）

**① Gate（写入门）**
- 唯一变更口是 `set(key, value, actor, reason)` 四步，**顺序不可换**：
  `authority.gate(actor)` → `validate(key, value)` → **落到执行器** → `History.append(...)`
- ⭐ **门必须在落地执行器上，不是包装层**（dsh `packages/AGENTS.md:14`：
  "Enforce a decision in the operation that makes it. Schema omission、门面、包装层、监听器顺序
  都不是强制——当直接或替代调用方能绕过时；必须经执行器测拒绝"）
- `actor` 由**通道**决定，不由请求内容决定。⇒ AI 无法传 `actor='human'` 伪造人类归因，也无法因此拿到写权
- 报错时**快照一个字节都没动**（validate 在落地之前）

**② History（账）**
- append-only：只追加、永不改写；seq 单调递增；可从盘上续
- **它是软件自己的资产，与操作者无关**——人操作时也写。**它不是 dsh session log 的第二真值**
- 与 dsh 的**操作者行为史**是两份不同资产，关系是**互引**（每次 `set` 带当次操作的 call-id/seq）
  ⇒ "AI 做了什么" ↔ "域变成了什么" 可双向走查
- **必须能在 dsh 消失后独立工作**（这是"软件不依附 dsh"最具体的一条）
- 折叠函数 `fold(events) → snapshot` 是纯函数；启动时按日志重建

**③ Surface（能力面）**
- 一个 `Engine` seam：**Definition（我们拥有）+ Provider（项目提供）+ Consumer（ops/tools 管道）**
- **Definition 允许是具体 registry 服务，绝不是 interface**（dsh `docs/glossary.zh.md:9`）
  ⇒ `queries`/`mcp_tools`/`hooks`/`custom_types` 是**一等 Service**，不是 ABC 上的方法
- **必实现只有 4 个**：`schema()` / `run(spec, **opts)` / `summary()` / `estimate()`
  （`schema` 合一 v1 的五个视图；`run` 合一 build+check+evolve；`summary` 合一两个摘要；
  `estimate` 留必实现 = D7 契约先行，框架真会调）
- **其余全部是注册项**：`register(entry) → disposer`（dsh `AGENTS.md:106`）
- ⭐ **铁律**：*框架自己会调用的，才配进 Definition；框架不调、只做分派目标的，必须是注册项。*
  （dsh 更锐利的版本：`packages/AGENTS.md:10` **Inverse smell——只有一个内部调用者的公开方法 = 坏味道，
  应降级为闭包**）
- ⚠️ **禁止"可选 ABC 方法"这种形态**。v1 的 31 个方法里约 7 个是"框架从不调、只是 getattr 分派目标"，
  这是 31 方法膨胀的直接原因

**④ Monitor（人类监控面）**
- **与 Gate/History/Surface 并列的第一层**，不是附属
- 两层信任：
  - **概括层**（derived）：我们写的、给人看的、可能出错 ⇒ **必须标明是派生的**
  - **原始层**（authoritative）：History 本身，append-only，软件自己的资产，**不随 dsh 生死**
- 唯一硬纪律：**概括必须能从原始推出；两者不一致时原始赢，且概括必须显示为存疑**
- 只读：无任何写回路径（v1 的 `cockpit/backend.py` 方向正确，补"可对账"这条）

**⑤ Provider 层（四个 seam，dsh 的 churn 全关在这里）**

| Seam | Definition（我们稳定） | dsh Provider | local Provider |
|---|---|---|---|
| **Log** | 事件形状 + `append`/`since`/`last_seq` **三原语** + **一个可选能力** `precheck`（经 `getattr` 发现，缺失即无预检；**`subscribe` 不在契约里**） | 发 host session/event | 写 `.mecha/journal.jsonl` |
| **Jobs** | 「一次长计算是一个 job」+ 可轮询/可取消/断线可找回 | 注册到 `ctx.jobs` | 本地线程 |
| ~~**Spill**~~ | ~~「大载荷落盘 + 回一个不透明定位符 + 取回指引」~~ **已撤销**（2026-09-25 收口轮：零消费者且无发起方 ⇒ 整机制删除；该语义由核心 Artifacts 承担，唯一条目见 `artifacts.py`） | ~~`ctx.spillStore`~~ | ~~本地 `$pointer`~~ |
| **Approval** | 「此刻这个 actor 能做这个操作吗」 | `ctx.approval` one-shot | 本地 `Authority` |

**⚠️ Approval 的一条硬约束（v1 曾误判）**：dsh 的 approval **刻意窄**——one-shot only，
**无 allow-always / 无规则记忆 / 无撤销 / 无 grant store**，fail closed。
⇒ **"human 模式持续一段时间的写权互斥"必须我们自己管 mode 状态。** `Authority` 的模式机不该删，该瘦成
"mode 状态机自留 + one-shot 授权委托给 Approval Provider"。

### 5.3 出厂策略：`nothing ships enabled` 用在自己身上

**local Provider 是出厂默认（独立部署开箱即用）；dsh Provider 是显式 opt-in。**

这不是权衡，是**遵守我们自己的纪律**（§3 L8 + dsh `packages/AGENTS.md:7` "Keep opt-ins out of shipped defaults"）。

### 5.4 ⭐ 边界的处置方式：写机制，不写分类

**这是本总纲最容易被执行错的一节，单独列出。**

我们对"什么归框架、什么归项目"争了几个月不得解。dsh 给出的不是答案，是**一种让这个问题不必辩论的机制**。
抄它的时候必须分清两类东西，混为一谈就会重犯 v1 的错：

| | 内容 | 该不该在 v2 里定 |
|---|---|---|
| **机制** | 每个 seam **声明自己的角色**；一张**从代码生成**的 capability map + 守卫；"新能力只能落在已声明扩展点上" | ✅ **要定**。它小、零成本，且**没有它我们就会退回手写标签然后漂移**（v1 的血统标签正是这么黄的） |
| **分类内容** | 哪些能力是 core / seam / bundle；`queries` 算不算 seam；哪些该拆包 | ❌ **不许定**。只有一个消费方（EL）+ 一个部署（dsh）时，任何分类都是"1 个项目的形状"。定了就是又次先验划界 |
| **汇总装置** | 保证第 2、3 个项目接入时，它们的能力声明**能被机械汇总** | ✅ **要定**。否则"等多几个项目再定型"到时候拿不出证据，还是得靠人议 |

**dsh 的原话依据（四条，前两条我亲自读过原文）**：

1. `docs/capability-seams.zh.md` 末行（**我核过**）：
   > 维护模式：混合模式。服务**从 Cordis 声明中发现**；接口、实现和消费方角色**在 `scripts/gen-doc-graphs.ts` 中分类**，并设有完整性守卫。

   ⇒ **分类是生成的，不是手写的。** 这是 v1 血统标签黄掉的直接解药。
2. `packages/AGENTS.md:11-12`（**我核过**）：
   > **Require a current owner and need.** 把每个抽象、状态机、选项、防御性拷贝、兼容路径系到一个**当前的**契约或生产消费方。
   > **Require evidence for public choices.** 可配置性不构成无据默认值/公开操作集/格式/引入的外部概念的理由。要当前消费方作证或相关先例；**否则要求一个显式值，或推迟这个选择**。

   ⇒ **没有消费方作证的选择，要么显式要值，要么推迟。**
3. `2026-06-13-capability-seams.md`（子代理读，**待核**）："**Don't split preemptively** —— 只有一个可设想 provider 和一个 Consumer 的能力，保持一个包，直到第二个出现。"
4. `docs/cookbook/extension-cookbook.zh.md:104`（子代理读，**待核**）："每个产品功能都映射到一个文档化扩展点上的监听器——**微内核声明由此可验证**……没有任何一行修改循环本身。"

**角色声明与能力表的用途**：运行时注册项可以声明定义、实现与消费者关系；
`docs/capabilities.md` 是从声明生成的阅读视图，可按需要刷新或并表。
真实消费者是否需要某个抽象是设计审查，不能靠字段名字、import 或第二份三态表机械判定。
角色注册和装配由行为测试验证，文档新鲜度不是无关开发的门禁。

**⚠️ 明确允许"现在不决定"的事**（写成 ADR 记录"推迟 + 重新考虑的条件"，不许沉默推迟）：
- 哪些 seam 该从单包拆出去
- `queries`/`mcp_tools`/`hooks` 是否算独立 seam（v2 先按"Surface 的注册项"实现，等第二个项目出现同类需求再升格）
- History/Artifacts/Approval 三家各自该不该有第三个 provider

**重新考虑的统一条件：出现第二个有据的消费方（n=2），或第一个明确说"我不要这个"的项目。**

### 5.5 ⭐ 三层与两条腿（运行时的当前口径）

**为什么是"三层"**：三种关切各自会变，混在一起就互相绑架。

| 层 | 归谁 | 一句话 |
|---|---|---|
| **软件**（状态 + 能力面 + 闸门 + 账） | **项目自己** | 门和账只有一个；状态所有者是软件（公理 A1） |
| **交互**（谁在跟它说话） | 框架 | 一次启动 = **一个 launcher 管 N 个站点**；dsh 是**全生态一个**，由站点共同贡献 |
| **写权**（此刻谁能写） | **启动者声明**，软件执行 | 四档：`locked` / `human` / `ai` / **`open`（AI 与人共用）** |

**两条腿都是客户端**（A2）——这条推翻了早期"两条腿不能同时活"的说法：
写租约是**软件自己的**（同一数据根只有一个写宿主），而**写权互斥**是另一件事。

| 腿 | 走哪条面 | 谁用 |
|---|---|---|
| **AI 腿** | 框架的**聚合端点**（`mcp__<聚合名>__<软件>_<工具>`）＋ 框架元工具 | AI |
| **人手腿** | **常驻控制台**（启停/写权）＋ **软件自己的人面** | 人 |

⛔ **一条不许破的纪律**：控制操作（切写权、开人面）**绝不进 AI 那条腿** ——
AI 不许给自己解锁，哪怕本机可信（裁决 2 放宽的是防护，不是这条意图）。

⭐ **共用档（`open`）= 该项目没有写权切换的需求**（用户裁决）：
两侧都能写时，"切到手动 / 交还给 AI"这两个标签**描述不了任何真实差别**
⇒ 控制台**不画那个假按钮**（入口留给项目自己）。这条取代了早期"从 mecha 启动永远是 AI 组"的口径。

### 5.6 ⭐ 三个生命周期（互相正交，别互相绑）

**这一节是把散在几份文档里的"生存域"收拢到一处**——三条命各有各的存亡，谁也别替谁决定：

| 生命周期 | 活多久 | 谁决定 |
|---|---|---|
| **软件进程** | 由 supervisor 起停（热更新 = 停了再起） | 框架的 `supervisor`（唯一进程控制面） |
| **交互会话** | 比软件进程长（软件重启，会话不死） | dsh / 面板；**不受**软件重启影响 |
| **写权** | **正交于上面两条**：切写权**不动进程、不动连接、不动状态** | 启动者声明初始档，之后由人侧切 |

**人面（窗口 / 网页）跟软件同生共死**，不跟会话走：
- 进程内窗口（EL / ML）：**按需开**，软件一重启就没了（这正是选"开在软件进程内"的代价，也是它的理由）；
- 浏览器页（GP 的 Web 工作台）：随服务进程在；
- 只读 web 侧车（ML 的面板服务、TensorBoard）：**由软件自己的启动方起、收尾收掉**。

### 5.7 ⭐ 启动功能：一个 launcher 把这三层架起来

**边界**：`python -m mecha`（`--all` 管全部站点）。它**不装系统服务、不设自启**——
是个前台编排器 + 一张常驻控制台；退出即收尾（先礼后兵、等真退出、整组死）。

**一次启动发生什么**（顺序即依赖）：载入并校验 N 个站点的声明 → 清陈旧残留 →
**生成 dsh 的第三层 overlay（地址按回读端口写）** → spawn 各软件 → **真探活的就绪判据** →
把起来的软件 attach 到**聚合端点**（工具表随之变）→ 起 dsh（一个）→ 起常驻控制台 → 收尾。

**三条纪律（每条都有根因，别绕过）**：
1. **就绪 = 真探活**（不许拿"端口文件存在"当就绪 —— 文件是发现辅助，不是真值）；
2. **端口 = 回读**（不许把预选值写上，那会和真实 bind 分叉）；
3. **状态只有一个真值来源**（面板不自己记账，一律问 supervisor）。

外加一条**措辞纪律**：**"消失了"与"读不到"必须长得不一样**（前者是事实，后者是我们没看到）。

⚠ **启动是"机制"，形态是"声明"**：软件怎么起（argv / 就绪判据 / 数据根 / 初始写权 /
有没有人面 / 监控面在哪）全在项目的 `mecha_site.py` 里，框架**不写死任何项目词**。

## 6. 决策、限制与兼容性

重要架构取舍可以用 ADR 保存理由，简单改动由提交说明交代。限制写在对使用者有帮助的位置，
不强制每个模块写固定标题或为“没有已知限制”编一段散文。历史否决可保留，但不自动成为永久禁令。

磁盘格式版本与迁移规则属于真实兼容性契约，应保留相应结果验证；ADR 标题、日期、章节不属于软件契约。
当前改动方法见 [框架准入线](框架准入线.md)，记录方式见 [ADR 制度](ADR制度.md)。

## 8. 硬纪律（不可协商）

1. **门只能在执行器上**，不许在包装层
2. **History append-only**，且 dsh 消失后必须独立可用
3. **Definition 只放框架真会调的**；分派目标一律是注册项
4. **`actor` 由通道决定**，请求内容永远不能改它
5. **概括层必须能被原始层证伪**，不一致时原始赢
6. **dsh 的 churn 不许越过 Provider 层**
7. **在合适层级验证关键承诺**：纯逻辑可测单元，接线测装配，协议测真实边界
8. **减少重复事实**；文档按用途维护，不设置散文格式或计数门禁
9. **重要决策交代理由**，记录形式按改动规模选择
10. **边界问题写机制不写分类**（§5.4）：角色声明、生成式 capability map、汇总就绪——这三件现在建；
    分类内容等第二个有据消费方（n=2）再定，**推迟也要写 ADR 并给重新考虑的条件**

## 9. 反模式（v1 踩过的，不许重踩）

| 反模式 | 代价 |
|---|---|
| 给单个功能加具名 ABC 方法 | v1 因此长出 31 个方法，其中 7 个框架从不调 |
| 把实现细节写进模型可见的文本 | AI 学到的不是任务，是我们的内部结构 |
| 判据自己造一份生产路径造不出来的输入 | **假绿**。v1 的 `static_pair` 因此绿了整月而经 MCP 恒报 R=0 |
| 为了让守卫绿而改小守卫 | 假绿比红更危险（L3） |
| 在库里写死某个项目的目录名/端口/键名/示例值 | v1 的 `save_state`/`8767`/`出光`…教错所有后来者 |
| 用自建算术替代被测系统 | v1 连着三次探针给出假答案（空集当结论、少传参当异常、注释当断言） |
| 一处机制改完不补判据 | 下一次回归没人拦 |
