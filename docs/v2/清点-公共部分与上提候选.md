## 1. 规模基线（本次清点的分母）

### 1.1 各仓 Python 规模

| 仓 | py 文件 | 总行数 | 其中：接入/胶水层 |
|---|---|---|---|

| **EL** | 246 | 51208 | `mecha_v2/` 5 文件 **1676** + `src/v2_bind.py` **193** + `src/ui/_mecha_bind.py` **365** = **2234** |

| **GP** | 91 | 21118 | `mecha_adapter/` 7 文件 **1945** |

### 1.2 ⭐ 基线结论（本节最值得先看的一条）

> **三个项目为了"接上 mecha"，一共写了约 8506 行**（EL 2234 + ML 4327 + GP 1945），
> 而框架本体只有 **5481 行**。
>
> ⇒ **接入层的代码量是框架本体的 1.55 倍。** 这就是"新项目接入成本"的现状。
> ⇒ 所以本次清点的真正问题不是"框架还能加什么功能"，而是
> **"这 8506 行里，有多少行是任何项目都得重写一遍的机械接线？"**

### 1.3 ⚠ 但那 8506 行里，真正的"机械接线"只有一小块（**本清点最反直觉的结论**）

把胶水层按文件拆开看（实测行数，`ReadAllLines` 口径）：

| 文件族 | ML | EL | GP | 性质 |
|---|---|---|---|---|
| `engine.py` | **1302** | 304→（校正后见注） | 157 | 项目领域：`Engine` 领域实现 |
| `tools.py` | **620** | ~544 | ~645 | 项目领域：工具声明与工具体 |
| `validator.py` | **562** | （并在 engine） | （并在 engine） | 项目领域：状态键与参数校验 |
| `capabilities.py` | **490** | — | — | 项目领域：能力图（ML 独有） |
| `assembly.py` / `bridge.py` | **418** | 455 | （并在 hub） | **半机械**：装配接线 + 领域摘要器 |
| `summarizer.py` | 179 | （并在 bridge） | — | 项目领域：人类可读摘要 |
| `monitor_http.py` / `monitor.py` | **194** | — | 79 | **合法适配**（见 §4.4） |
| `mcp_host.py` / `hub.py` 的 MCP 段 | **157** | ~45 | ~44 | ⭐ **机械**（见 §4.2） |
| `launcher.py` | **668** | **245** | ？（GP 走 CLI 形态） | ⭐ **机械**（见 §4.1） |

> ⚠ **注**：本表 ML 列与 `launcher` 行是校正后口径（含空行）；EL/GP 若干格沿用旧口径，
> 由上标"约/~"标出，**不许当精确值用**。逐格校正留待 §3 汇总时统一。

**⇒ 结论**：三个项目**最大的几个文件永远是 `engine.py` / `tools.py` / `validator.py`
—— 那正是框架 L5 明令禁止进框架的东西（领域知识）。**

真正"任何项目都得重写一遍"的机械件，每仓只有约 **250–350 行**：

```
每仓机械件 ≈ MCP 壳(~45) + launcher 状态机(~150-300) + 请求文件/端口就绪(~20-30)
其中已被框架收走的 = portfile 的 清/读/写 一件（87 行）
```

⇒ **上提的天花板约 500 行（跨两仓）+ 未来每仓约 215 行**，
**剩下 88%–94% 的胶水是项目领域内容，上提它就是违反 L5。**

> ### ⚠⚠ 但这只算了 Python —— **§2.8 推翻了本节结论**
>
> 本节的分母**只覆盖三仓的 Python 胶水层**。**`dsh/` 的宿主半（TypeScript）没算进来**，
> 而**最大的那处真重复正好在那里**：EL 与 GP 各握着一份 **≈500 行的同源
> "自愈 MCP 客户端桥"**（GP 自述"移植自 Energy Level"），且已开始分叉。
>
> ⇒ **正确结论**：
> - 在**Python 胶水层**里确实没有大块可省的代码（本节成立）；
> - 但**跨全仓**看，**最大的可省项在 `dsh/` 宿主半**，量级 ≈500 行/项目，
>   形状与既有的 `dsh-panel/` 共享资产**完全同构**。
> ⇒ **"没有大块可省"是错的；"Python 胶水层里没有大块可省"才是对的。**

## 2. 统筹者实测：四个候选簇（第一手证据）

> 以下每一簇都是**统筹者亲自读代码 + 实测行数**得出的，不依赖任何子代理的转述。

### 2.1 ⭐⭐ 候选 1：launcher 状态机（最强，但框架文档把话说粗了）

**跨仓事实**：

| 函数 | EL（`launcher.py` 206 行） | ML（`launcher.py` 572 行） | 逐字节相同 |
|---|---|---|---|
| `_spawn` | 5 行 | 5 行 | ✘ |
| `_write_state` / `write_state` | 9 行 | 7 行 | ✘ |
| `start_group` | 12 行 | 20 行 | ✘ |
| `_spawn_dsh` | 24 行 | 30 行 | ✘ |
| `_choose_mode` / `choose_mode` | 26 行 | 30 行 | ✘ |
| `_log` | 6 行 | 22 行 | ✘ |

- **同形的证据**：EL 的 13 个函数里，**10 个在 ML 里同名存在**
  （`_log` / `_spawn` / `start_group` / `_spawn_dsh` / `_terminate_group` / `await_exit` /
  `read_request` / `clear_request` / `write_state` / `choose_mode` / `main`）⇒ **状态机确实是一份**。
- ⚠ **但框架文档说的"13+ 同名机制、逐行同一"是错的**（`docs/接入指南.md` §5）。
  实测**无一函数逐字节相同**，差异是**装饰性的**：
  - `_spawn`：EL `cwd=HERE` vs ML `cwd=str(HERE)` + 多一个 `env=None` 形参
  - `write_state`：EL `open(MODE_STATE,"w")` vs ML `MODE_STATE_FILE.write_text(...)`
  ⇒ **抽取前必须先做"逻辑级并排清点"再定边界**（这正是框架自己写在 C1-5 里的前置条件）。
  **直接当同一份合并会出错。**
- **框架侧现状**：`mecha/` 内**没有任何** `subprocess` / `Popen` / `creationflags` / `taskkill` 代码；
  唯一的管理知识是 `mecha/portfile.py:6` 的一句 docstring。
- **ML 多出来的**（EL 无）：dsh patch、面板打包、`_kill_tree`、单例锁、控制台监听。

**裁定**：**候选成立，但边界待"逻辑级并排清点"后定**。见 §4.1。

### 2.2 ⭐⭐ 候选 2：MCP 薄壳（最干净，且框架已做过一次同类上提）

**三家写的是同一个壳**：

| | EL `mecha_v2/hub.py` | ML `ml_mecha/mcp_host.py`（157 行） | GP `mecha_adapter/hub.py` |
|---|---|---|---|
| `build_mcp_server` | 9 行 | 8 行 | 5 行 |
| `McpHost` 壳 | — | 50 行 | **46 行** |
| **真正项目专有** | 服务名 + 说明 | + 必填来源 | + 必填来源 |

- GP 的 `McpHost` 与 ML 的**结构上逐行一致**：
  `port` / `url` / `server` / `build_server` / `start(timeout=30.0)` / `stop(timeout=10.0)` /
  `__enter__` / `__exit__`，连默认超时值都一样。
- **根因（实测）**：框架 `providers/mcp.py` 的 `McpEndpoint.__init__`（`:539-544`）要 **8 个 kwarg**
  （`registry, server_name, instructions, toolhost, host, port, port_file, required_source, log`）。
  每个项目都想给 `server_name` / `instructions` /（`required_source`）**项目默认值**
  ⇒ **只能各写一个转发壳**。
- **已有先例**：ML 的 `mcp_host.py` **已经上提过一次** —— 445 行 → 157 行，并有契约文档
  `_mecha-extraction/mcp-contract.md`（本文件 docstring `:9-15` 记着）。
  它明确写了留在 ML 侧的三样：**服务名、服务说明、必填来源**。
  ⇒ **这次只是把同一件事再往前推一步**：给"项目的这几个值"一个正式的承载物。

**裁定**：**最该上提的一项**。见 §4.2。

### 2.3 候选 3：monitor 薄壳 —— ⚠ **实测结论是"不该上提"**

- 三家都接了框架的 `mecha.monitor`（`Monitor` / `Claim` / `Summarizer`）与 `mecha.cockpit`
  （`MonitorEndpoint` + `monitor_summary_payload` + 三个投影函数）。
- ML `monitor_http.py` 里的 `history_records` / `activity_records` / `config_tree` / `summary_view`
  都是**一行转发**到框架函数（`:52-83`），存在的理由是**适配 ML 自己的对象形状**（`_source(ml)`）。
- `MonitorEndpoint` 壳与 MCP 壳同形，但**更长的是项目自己的摘要器**：
  ML `summarizer.py` 151 行、EL `bridge.py` 383 行。

**裁定**：**不上提**。这是**合法适配**，不是重复实现 —— 顺手记进 §4.4 的负面清单，防后人重提。

### 2.4 候选 4：请求文件协议 —— 一个**已许诺但不存在**的机制

- `docs/接入指南.md:151` 的"该由谁提供"表**已经许诺**：框架给
  「**读 / 写 / 清一个请求文件**（路径显式）」，项目只给**文件名**（`.mode-request` / `gui` / `ai`）。
- ⚠ **实测：mecha 里没有这个机制。** 全仓 `request` 命中全是 HTTP 请求体（`cockpit.py`）
  与审批调用（`providers/approval.py`），**没有模式请求文件的读/写/清**。
- 而 **EL 和 ML 各写了一份**（`_read_request` / `_clear_request`、`read_request` / `clear_request`）。

**裁定**：**候选成立，且它同时是一条"文档许诺了机制、机制不存在"的账**。
按原则 1 的不变量（**露出来的必须真通电、没通电的必须响亮、不存在的必须不存在**），
它要么补机制、要么把文档改成真话 —— 两者都不许继续挂着。见 §4.3。

### 2.5 框架侧的正确样板：`portfile.py`（87 行）

上提**可以**做对，样板就在本仓：`portfile.py` 只给**规则**（含"启动前清陈旧"的安全论证），
**不持任何文件名默认值**，且 `OSError` 静默是**有书面理由的**
（"端口文件是发现辅助，不是真值"）。⇒ 凡上提，按这个形状：**库拥有规则，宿主拥有名字**。

### 2.6 ⭐⭐ 候选 5：概括层（`summarizer`）—— **框架强制要求，自己却不消费**（新，第一手实测）

**这是本次清点里唯一直接打到「需求 2 · 可靠监控」和原则 4.4 的一项。**

**实测链条**：

| 环节 | 事实 | 证据 |
|---|---|---|
| 框架**强制**要 | `assemble(*, …, summarizer: Summarizer, …)` —— **无默认值的必填 kw** | `mecha/assembly.py:156`（传给 `Monitor`：`:176`） |
| 框架**提供了**读面 | `monitor_summary_payload(view)` → `{summary, summary_error, disputed, …}` | `mecha/cockpit.py:232-256` |
| 框架**自己的路由不用它** | `CORE_ROUTES = ("/status","/activity","/history","/config")` —— 四条**都不含**概括层 | `mecha/cockpit.py:107`、`:589-599` |
| 框架**自己的面板不渲染它** | 面板只 fetch `BASIC_ROUTES`（同四条），只从 `/history`+`/config` 渲染 | `mecha/dsh-panel/routes.ts:36`、`panel-data.ts:47-48` |

**⇒ 三家的处境（实测）**：

- **EL：账上一个字都没有。** `hub.py:98` 把 `el_summarizer` 传进 `assemble()`，
  但 **EL 从不注册 `/summary`**（全仓 `add_route` 零命中）⇒ **EL 的概括层从生到死不可见**。
- **ML：自己补了两件。** `monitor_http.py:132` 注册 `/summary`，并**如实写下**
  "共享面板的通用读面**不渲染** `/summary` 的信封（`disputed` 那句没有标准渲染位）"（`:75-77`），
  只好把 `recent_runs` 摆成 `rows` 去迁就附加页的表格契约；再在 `dsh/src/client/extraPages.ts:80-92`
  声明 `EXTRA_PAGES` 让面板真的渲染它。
  ⇒ **ML 自建了"路由 + 附加页"两件，才让框架强制它提供的东西被人看见。**
- **GP：** `monitor.py:43-72` 写了 summarizer + `/summary`（`:91`）。

**⇒ 问题陈述（供裁决）**：
框架把概括层定为**必填**（原则 4.4："概括层（派生）：给人看的、可能出错 ⇒ **必须标明是派生的**"、
两层信任"必须能从原始推出、不一致时原始赢且概括必须显示为存疑"），
**却不在自己的读面或面板里消费它一次**。后果：
1. 每家**必须**写一个同形函数（强制成本），
2. 而"**必须标明是派生的**""**存疑必须显示**"这两条硬纪律，
   **在框架自己的面板上无处落地** —— 要不要让人看见，成了各项目的自觉。
   EL 的实测结果就是：**派生层对人不存在的**。

**裁定**：**候选成立，且优先级高于 launcher 与 MCP 壳** —— 它不是"省行数"，是
**一条已被写进原则的纪律在实现里没有出口**（近 R1"只占一格不叫接缝"，且方向相反：
这次是**框架占了两格（定义 + 强制消费者）、却在人面前缺了出口**）。

### 2.7 ⭐ 候选 6：`bind_scope_policy` 不注入 ⇒ 过滤**静默跳过**（新，第一手实测）

- `mecha/commands.py:310/312/318`：`_scope_policy` 默认 `None`，靠 `bind_scope_policy` 注入。
- `:430-433`：`if self._scope_policy is not None and spec.scope:` ⇒ **未注入就直接跳过过滤**。
- ⇒ **命令声明里的 `scope` 会变成"声明了没人用"**：声明在、过滤不在，且**不报错**。
- GP 实测踩到（`hub.py:104-109` 的注释记着）：不绑 policy ⇒ `add_topic` 经 AI 工具面**静默成功**，
  而**框架自己的判据全绿**。

**裁定**：这是一条**验收缺口**（L3 假绿同族）。正解不是"项目记得绑"，而是
**"声明了 scope 却没绑 policy"应在装配期响亮失败**（R13 的行为级判据形状）。
⚠ 但**这是框架侧改动，有风险**，须单独立 ADR —— 本轮只登记。

### 2.8 ⭐⭐⭐ 候选 8：dsh 自愈 MCP 客户端桥 —— **本次最大的一处真重复（新，推翻了 §1.3 的初步结论）**

> **这一项是 EL 仓负责人报出来的，位置在 `dsh/` 的宿主半 —— 此前统筹者的清点里没有它。**

**实测（四仓文件与 sha256）**：

| 文件 | EL | GP | ML | 判定 |
|---|---|---|---|---|
| `host/mcp-bridge.ts` | **277 行** | **283 行** | **无** | 83% 文本重合（48 条 diff） |
| `host/register-tools.ts` | **97 行** | **97 行** | **无** | **仅 10 条 diff，全是类名与日志串** |
| `host/mcp-session-http.ts` | 84 | 76 | 无 | — |
| `host/config.ts` | 51 | 49 | 无 | — |
| `host/mode-request.ts` | 24 | — | 无 | EL 专有 |
| **合计** | **≈533 行** | **≈505 行** | **0** | — |

**⭐ 决定性证据（不是"看着像"，是明写的）**：

1. **GP 的 `mcp-bridge.ts` 头部自述**：
   > "背景（**移植自 Energy Level re0-mecha-dsh**，见其 `docs/DSH-MCP现状-给开发者的参考资料.md §2.3`）"
   ⇒ **GP 是从 EL 复制过去的**，且连参考资料都指着 EL 的文档。
2. **`register-tools.ts` 97 行 vs 97 行，10 条 diff 全是**：`MechaMcpBridge` ↔ `PaperPilotMcpBridge`、
   `[re0-mecha]` ↔ `[paperpilot]`、一句"Hub 离线" ↔ "服务离线"。
   ⇒ **这是逐字副本 + 改名**，正与 `dsh-panel/` 的"参数块之外逐字"同形。
3. **两家替换的是同一个上游缺陷**：dsh 的 `dsh-mcp-client` 只在 `transport.onclose` 触发时重连，
   而 streamable-http 的 POST 失败（服务重启后旧 `Mcp-Session-Id` → 404）**只抛错、不触发 onclose**
   ⇒ 客户端永久卡死，只能重启 dsh Host。
   ⇒ **两个项目各自为同一个上游 bug 写了一次同样的 workaround。**

**⇒ 为什么这条推翻了 §1.3 的初步结论**：
§1.3 说"没有大块可省"，那是**只看了 Python 胶水层**得出的。
把 `dsh/` 的宿主半算进来后，**EL+GP 各握着一份 ≈500 行的同源代码**，
**且已经开始分叉**（83% 重合 = 已漂 17%）。

**裁定**：**该上提**，形状**照 `dsh-panel/` 的既有先例** ——
框架随包发一份 TS 共享资产（逐字副本 + 指纹 + 唯一参数块），项目只填自己的名字与日志串。
⇒ **每接入一个项目省 ≈500 行**，且把"替上游擦屁股"的知识收进一处。

⚠ **两条必须先裁的前置问题**（不是技术问题，是框架定位问题）：
1. **`register-tools.ts` import 了 dsh 的类型**（`@deepseek-ai/cordis` / `@deepseek-ai/dsh-tools`）
   ⇒ 框架多一类"面向宿主 TS 的共享资产"。**先例已有**（`dsh-panel/` 也是宿主资产），
   但 `dsh-panel` 是**监控面**，这件是**工具接入面**，性质不同，须明确写进边界。
2. ⚠ **与框架的硬纪律"dsh 的 churn 不许越过 Provider 层"（总纲 §8.6）冲突**：
   这件资产**恰恰是缠着 dsh 内部缺陷生长的**（402/404 语义、`onclose` 行为）。
   要么承认它是"宿主资产"（同 dsh-panel，独立于 Provider 层），**要么就必须先答**：

## 6. 方法说明（为什么这些数可信）

### ⚠ 6.1 一次**方法更正**（必须留档，否则本文件的数会继续骗人）

- **错法**：`Get-Content … | Measure-Object -Line` —— **不数空行**。
- **正法**：`[System.IO.File]::ReadAllLines(...).Count` —— 数全部行。
- **差多少**（实测）：EL `launcher.py` 206 → **245**；ML `launcher.py` 572 → **668**；
  `ml_mecha/mcp_host.py` 121 → **157**；`ml_mecha/assembly.py` 349 → **418**；
  `ML app_entry.py` 135 → **158**。**普遍低估 15%–20%。**
- **谁发现的**：ML 仓负责人（自报"实测 launcher 502 vs 真值 668，别用旧数"）。
  ⇒ 这正是本工程要的"**验证落在消费者那一层**"（R3）：统筹者的工具口径错了，
  被下游代理用另一套工具抓出来。
- ⚠ **教训（与本工程既有纪律同族）**：**"量"也是一种结论，量错等于结论错**；
  报行数必须写明**口径**（含不含空行、含不含注释），否则两个"实测"可以差 20%。

### 6.2 其它口径

- 规模统计：递归 `*.py`，排除 `.venv` / `venv` / `node_modules` / `build` / `__pycache__` / `.git` / `site-packages` / `lib`。
- 函数体比对：按缩进切出函数体，`\r\n` 归一后**逐字节**比较；配对用**归一化名字**（去前导 `_`、转小写）。
- 哈希比对：文件按 UTF-8 读取、`\r\n` → `\n` 归一后取 sha256（与四仓面板判据同一口径）。
- ⚠ **作用域声明**（R3）：以上结论的作用域是**源码层 + 磁盘副本层**。
  统筹者**未执行**任何判据、构建或服务 ⇒ "门禁是否绿""运行期行为"**均未验**。

### 6.3 三方独立算同一个数（本次的一个方法论收获）

候选 2 的净收益被**两条独立路径**算过（统筹者按 ÷3 家、mecha 负责人按 ÷2 家 + 判据翻倍），
结论都是"**低于噪声**"。⇒ **凡"上提"类决策，净收益必须至少两方独立算一遍**，
因为分母（分摊家数）与判据成本最容易被各算各的。
