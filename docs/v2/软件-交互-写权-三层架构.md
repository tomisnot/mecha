## 0. 三条公理（其余全部由此推出）

| # | 公理 | 直接推论 |
|---|---|---|
| **A1** | **软件自己是状态所有者**：状态住在**软件进程自己的线程**里；软件是它的**唯一写宿主** | 交互面**永远不是**宿主 ⇒ 写租约**天然**满足（它防的"两个宿主"根本不出现） |
| **A2** | **交互面只是客户端**：AI 与人都是**同一层的客户端**，都通过面**读**与**影响**状态 | 两者**可同时挂**；它们之间**没有存活性互斥** |
| **A3** | **写权是软件进程内的硬闸门**，与"软件存活 / 客户端连接"**三权分立** | 切写权 ⇒ **不动进程、不动连接、不动状态** |

⭐ **A3 是这套架构的核心**：它把"**谁能影响**"从"**谁在跑**"里彻底摘了出来。
这正是用户反复强调的那句：*"状态在软件线程内，AI 和 GUI 都只是读取和影响它"*。

## 1. 三个生命周期，正交

```
① 软件存活      起 / 停 / 探活 / 重启          ← 面板的【存活滑块】
② 客户端连接    AI 腿（dsh）/ 人手腿（GUI）    ← 挂 / 摘，与①无关
③ 写权          LOCKED / HUMAN / AI / OPEN     ← 面板的【写权开关】，与①②无关
                （软件进程内）
```

| 操作 | 动 ① | 动 ② | 动 ③ |
|---|---|---|---|
| 关掉一个项目（存活滑块 off） | ✓ | 腿失联 | —— |
| **切写权给手动**（面板按钮 / GUI 按钮） | ✗ **不动** | ✗ **不动**（dsh 与面板**待命，不关闭**） | ✓ |
| AI 工作流收尾（提前结束对话） | ✗ | ✗ | ✗ ⚠ **与写权无关** |
| 热更新（改了软件代码） | ✓ 重启软件 | 腿自动重连 | ✗ |

⚠ **"切到手动之后 dsh 与面板不关闭、只是待命"** 是需求，不是妥协 ——
它们的**写**会被闸门拒，**读**照常，所以它们**本来就是"待命"这个语义**。

## 2. 连接拓扑

```
              ┌──────────────────────────────────────────────┐
              │  软件进程（项目自己的线程/事件循环）           │
              │                                              │
              │  ├─ 状态（StateModel）—— 唯一所有者            │
              │  ├─ 账（Journal）—— 唯一写宿主，持写租约        │
              │  ├─ 写权闸门（Mode）                          │
              │  ├─ 能力面（Capability Surface）───┐          │
              │  │    ├─ 读 / 检视                 │ 给 AI 腿  │
              │  │    ├─ 写（影响状态；过闸门）     │（聚合端点）│
              │  │    └─ 订阅（增量流）             │          │
              │  ├─ ⭐ 控制面（Control Surface）───┼──┐       │
              │  │    └─ 切写权 / 开窗             │  │ 给人手腿│
              │  │      ⚠ **独立端点**（§7.1.1）    │  │（框架/  │
              │  │      ⇒ **不给 AI 看**            │  │ 面板）  │
              │  └─ ★ GUI 窗口（PyQt，就在这个进程里）│        │
              └───────────────┬──────────────────┴────────┘
                              │ 能力面
                     ┌────────▼────────┐
                     │  AI 腿           │
                     │  dsh ─ 聚合端点  │
                     └─────────────────┘
```

⚠ **两处容易看漏，务必注意**：
1. **GUI 窗口在软件进程内**（裁决 1）⇒ 它读状态是**直接读**、改状态是**直接调**，
   ⚠ **但仍必须过写权闸门**（见 §4）；
2. ⭐ **控制面是另一条端点**（§7.1.1 定案）—— **它不挂在给 AI 的那条路上**。
   本图早期版本把"控制（切写权）"画在能力面里，⚠ **那与 §7.1.1 矛盾**（已改）。

## 3. ⭐ 两个用户裁决（**连同理由与代价，一起记档**）

### 裁决 1 · **GUI 窗口开在软件进程内**（不是独立客户端）

**理由（用户给的，很关键）**：
> *"当我要频繁热更新时，通常是 AI 模式下，GUI 根本不开。"*

⇒ 这句话**消掉了"独立客户端"唯一的大好处**：
独立客户端的主要优势是"软件重启时窗口不死"；
而**热更新发生在 AI 模式、GUI 根本没开** ⇒ 那个场景**不会发生**。

**换来的好处**（都是真的）：

| | |
|---|---|
| 窗口与状态**同进程** ⇒ 读状态是内存读取、改状态是函数调用，**没有通信层要设计** | |
| **不需要为 GUI 单独设计一套"怎么探活/怎么握手"** —— 它随软件就绪 | |
| ⭐ 与公理 A1 **字面一致**："状态在软件线程内" | |

**代价（如实记）**：
- 软件重启（热更新）时窗口会**跟着一起死** —— ⚠ 但**这正是裁决 1 之所以成立的前提**：
  热更新通常发生在 **AI 模式、GUI 根本没开** ⇒ 那个代价**不落在真实场景上**
  （⚠ 所以 §7.1 **禁止"AI 模式下也一直开窗"**，否则这个前提就没了）；
- 要在**跑业务逻辑的进程里启动 Qt** ⇒ ⚠ **每家各有自己的 native×Qt 雷，
  而且它们不是同一条**（我早期把两家的混成过一条，这里更正）：

  | 仓 | 那条雷 | 状态 |
  |---|---|---|
  | **EL** | **QThread 生命周期 / `0xc0000409`**（`energy-level/docs/GUI界面-专家手册.md:233-234`） | ⚠ **未充分实测**（步骤 0 只覆盖 offscreen + 单次演化，见 §11 口径 2） |
  | **ML** | **lightgbm（经 methods 顶层导入）必须先于任何 PyQt5 模块**，否则其 OpenMP 与 Qt 冲突 ⇒ fit 时 access violation | ⚠ **未实测**（ML 还没做进程内开窗） |

- ⚠ **"两条腿同门"要靠纪律守**：窗口**能**直接调内部函数而不走闸门 ⇒
  **必须有一条判据**钉住"GUI 的写也过闸门"（不许长后门）——
  ✅ EL 已落（`checks/inprocess_gui_selfcheck.py` 组 ③：GUI 的写**账里有它**且带 `actor=gui`）。

### 裁决 2 · **写权依靠"本机可信"，不专门做防护机制**

**用户原话**：
> *"写权不用专门写机制防着，默认 AI 会配合，这不是安全问题只是工作需要，依靠'本机可信'即可。"*

**⇒ 因此**：切写权的通道**不做凭证**、不做"人侧/侧"鉴权，**本机发起的请求即可切**。

⚠ **如实记下这让渡了什么**：
框架原有的硬规则是 **"只有 human 侧能切模式；AI 不能给自己解锁"**
（`authority.py::switch_mode` 的 `side != "human"` 判定，注释写着 *"护栏仍在：AI 面改不了 mode"*）。
**本裁决显式放开它** —— 理由是本生态是**单用户开发环境**，
**默认 AI 配合**，这是**协作问题不是对抗问题**。

⚠ **但不许把它记成"我们忘了做安全"**：
- 这条是**显式裁决**，有理由（单用户、协作、默认配合）；
- ⚠ **触发条件**：将来若某项目要跑**不受信的内容**（多用户 / 联网服务 / 第三方插件），
  **必须重新裁决**这条，而不是沿用它；
- ⇒ 实现上**保留那个参数**（`switch_mode` 的 side 判定**别删**），
  只是**本生态默认不启用**它 —— 这样将来要收紧，**是一行开关的事，不是重写**。

## 4. 能力面：**门和账只有一个，形状可以多**

> ⭐ **先说清这一节最容易读错的地方。**
>
> ⚠ **早期版本这里写的是"两条腿共用同一个面"** —— 那句**过头了**，与 §7.1.1 冲突。
> 按框架的**核心原则 2**（`使用模式与核心原则.md`），原文是：
>
> > **"一条路"不是说"所有功能长一个样"。形状可以多……该长什么样就长什么样；
> > 门和账只有一个 —— 不管什么形状、谁在调，都过同一道门、落同一本账。
> > ⇒ 同一套治理 ≠ 同一个形状。**
>
> ⇒ **正确的说法**：

| | |
|---|---|
| **门 / 账 / 监控面 / 能力面这四件** | ⭐ 是**软件自己的**，**不因操作者而存在**；人和 AI 是它的**两条腿**，**它不归任何一条腿** |
| **形状（谁能调什么、面怎么分）** | ⭐ **可以多** —— ⚠ **控制操作就是另一种形状**（走独立端点，§7.1.1），**这不违反原则 2** |

### 4.1 形状一：能力面（给 AI 腿的那一条）

| 类 | 例子 | 谁能调 |
|---|---|---|
| **读 / 检视** | `read_state` · `inspect(page)` · `query_runs` | AI 腿 + 人侧读 |
| **写（影响状态）** | `set_param` · `run` · `cancel` | ⚠ **过写权闸门**（谁都一样） |
| **订阅（增量流）** | `subscribe(since)` → 事件流 | AI 腿 + GUI |

### 4.2 形状二：控制面（给人手腿的那一条）

| 操作 | 例子 | 谁能调 |
|---|---|---|
| **控制** | `set_write_authority(mode)` · `open_manual_surface()` | ⭐ **只有框架 / 面板 / 人手腿** |

⚠ **为什么它必须是另一种形状（独立端点）**：见 §7.1.1 ——
"**AI 看不见切写权那个操作**"要靠**端点的存在性**保证，**不能靠记得加过滤**。

### 4.3 ⚠ 一条不许破的纪律（即使不做安全）

**GUI 的写必须与 AI 的写走同一道门、记同一本账**（"人机同门"）。
理由不是安全，是**可追溯**：人改了什么、AI 改了什么，**在同一本账上分得清**
（`Channel.actor` 区分 `gui` / `mcp`，`side` 记录写权归属）。
⇒ **要有判据**：GUI 的写**必须**在账里出现，且**带它的 actor**。

⚠ **同一纪律也管控制操作**：`set_write_authority` / `open_manual_surface`
**也必须落账**（§7.1.1 的契约里已写）。否则"**谁在什么时候把写权切走了**"查不到 ——
那正是**原则 2 说的"绕过去的路"**（`使用模式与核心原则.md` §3 原则 2）。

## 5. 写权的语义（在裁决 2 下的最终形态）

```
出厂：LOCKED（nothing ships enabled —— 保留）
初始化：由【启动者】在 spawn 时声明（人是启动者 ⇒ "我起它就是要用"）
运行中：任何本机客户端都可请求切（裁决 2）
        ⇒ 切完【立刻生效】（下一次 gate 判定就用新值）
```

⚠ **"立刻生效"是可判的**，应写进判据：
切到 `HUMAN` 之后，**AI 的下一次写必须被拒**（`authority_mode_mismatch`），
而**人在同一条腿上立刻能写**。不许有"等一拍"的模糊语义。
✅ **已实测成立**（§11 的 P2：同一条 MCP 会话不重连，当场被拒）。

### 5.1 ⭐ `initial_mode` 用什么通道交给软件 ⇒ **环境变量**（定案）

| 变量 | 含义 | 谁读 |
|---|---|---|
| `MECHA_SOFTWARE_ROOT` | 这份软件的数据根（≈ `Service.data_root`） | 软件进程 |
| `MECHA_INITIAL_MODE` | 启动者声明的初始写权（`locked`/`human`/`ai`/`open`） | 软件进程 |

**为什么是 env 而不是 argv**（三条，缺一不可）：

1. ⭐ **与各项目的参数风格无关** —— 三家的 CLI 风格完全不同（`argparse` / `typer` / …），
   env 是**唯一**对三家都一样的通道；
2. 它**不占**软件的参数面（不会与项目自己的 `--mode` 之类打架，也不用改各自的解析器）；
3. 符合语义：写权是**运行环境给的**，不是用户敲的命令行参数。

**框架侧责任**：`spawn` 软件时注入这两个，走**已统一的注入点**
（与 `PYTHONIOENCODING` 同一处 ⇒ 天然带"**空串 = 显式取消该变量**"的语义）。

**软件侧责任**（步骤 2 的项目活）：**读** `MECHA_INITIAL_MODE`，装配闸门时**应用**它。

⚠ **框架只声明 `initial_mode`、不 spawn 软件进程内的闸门** ——
闸门在**软件进程内**（公理 A3）⇒ **送到**软件是双方约定，**应用**它是软件的事。

## 6. 项目声明（`mecha_site.py` 的形态）

⚠ ⭐ **先更正一处文档与实物的偏差**（D1"一个事实一个家"、D3"正文里写实现状态"）：

| | |
|---|---|
| 本文早期写的 | 新类 `Software`（还设想过新模块 `software.py`） |
| ⭐ **实际落地的** | **就是 `site.py` 里现有的 `Service`**（就地改形：删 `manual`、加 `has_gui`/`initial_mode`） |

⇒ ⭐ **以实际实现为准，本文不再提 `Software`/`software.py`** ——
理由：① 就地改形**更省**；② 更重要的是**避免两个模型并存**
（一个叫 `Service` 在跑、一个叫 `Software` 在文档里，那正是最容易分叉的形态）。

```python
# mecha/site.py（实际形态）
@dataclass(frozen=True)
class Service:
    id: str
    brief: str
    #: 怎么起【软件自己】—— 它自带状态、自带写租约、自带能力面、（可选）自带 GUI 窗口
    argv: tuple[str, ...]
    cwd: Path
    #: 怎么探"软件起来了"：端口文件**新鲜度** + 真探活
    ready: ReadySpec
    #: 数据根（写租约的互斥面：同一 root 不许两个**软件**）
    data_root: Path | None
    #: ⭐ 开始时用什么写权（由启动者声明 —— 人是启动者，故合法）
    initial_mode: Mode = Mode.LOCKED
    #: ⭐ 这个项目**有没有人操作的那个面**（决定面板显不显示"切到手动"）
    has_gui: bool = False
    #: 项目自己的环境变量；⚠ 框架注入的两个用 setdefault ⇒ **项目显式给的优先**
    env: Mapping[str, str] = field(default_factory=dict)
    # ⚠ 曾经有 `manual: ChildSpec`（人那条腿建成"要 spawn 的进程"）—— **已删**。
    #   按 A1/A2 它是错的（人那条腿在软件进程内，不是另一个子进程）。
    #   传它会当场 TypeError（判据 ⑬ 主动钉住这个"响亮失败"）。
```

⇒ **项目侧的义务**（新架构下每家要交的东西）：

| # | 义务 | 为什么 |
|---|---|---|
| **1** | **一个进程**同时提供：状态 + 能力面 +（可选）GUI 窗口 | A1 + 裁决 1 |
| **2** | 能力面**接受多个客户端** | A2 |
| **3** | **写权闸门**（`Mode`）在软件进程内，切完**立刻生效** | A3 |
| **4** | **GUI 的写也过闸门、也记账**（不许长后门） | §4.3 的纪律 |
| **5** | 提供**读 / 检视**与**订阅**，让"看"不依赖内部对象 | 让 AI 腿也能看同一份事实 |
| **6** | ⭐ **读框架注入的 `MECHA_SOFTWARE_ROOT` / `MECHA_INITIAL_MODE`**（§5.1） | 否则"框架声明的"与"软件实际用的"是两份值 |

## 7. 面板（常驻控制台）的定稿形态

```
┌────────────────────────────────────────────────────────────┐
│  AI 机甲 · 控制台                                          │
├────────────────────────────────────────────────────────────┤
│  ☑ Machine Learning   [●───] 存活   写权：AI  [切到手动]     │
│      传统机器学习 / 神经网络 / 自动调参                       │
│  ☑ Energy Level       [●───] 存活   写权：AI  [切到手动]     │
│  ☐ Get Paper          [───○] 已停   写权：—                 │
├────────────────────────────────────────────────────────────┤
│  dsh  [●───] 存活（它只是 AI 那条腿的载体）                   │
└────────────────────────────────────────────────────────────┘
```

| 控件 | 动什么 | 效果 |
|---|---|---|
| **存活滑块** | ① | 起/停软件（关掉 ⇒ 它的工具从 AI 面前消失） |
| **「切到手动」按钮** | ③ | ⭐ **只切写权**；**面板与 dsh 都不关闭，只是待命**（写被拒、读照常） |
| （dsh 滑块） | ① | 起/停 harness 本身 |

⚠ **按钮只在 `has_gui: true` 的项目上显示**（没有 GUI 的项目没有"手动"这一档）。

---

## 7.1 ⭐ 窗口**按需开**，不是启动就开（**被识破的矛盾**）

裁决 1 选"窗口开在软件进程内"的**唯一理由**是用户那句：

> *"当我要频繁热更新时，通常是 AI 模式下，**GUI 根本不开**。"*

⇒ ⚠ 所以 **"AI 模式下窗口也必须一直开着"是自相矛盾的** ——
那样热更新时窗口会**总是**跟着重启，等于把当初要避开的代价请了回来。

⇒ **定论**：

| | |
|---|---|
| **默认** | 软件进程 **headless**（不开窗）—— 这才是"AI 组"的常态 |
| ⭐ **开窗的时机** | **切到手动时**（与"写权切到 HUMAN"**同一个按钮**触发的两件事） |
| 机制 | ⭐ **软件暴露一个控制操作**（人侧调用）⇒ **软件在它自己的进程内开窗**（复用已装配的那份桥） |
| ⚠ 为什么"开在软件进程内" | 公理 A1（状态所有者是软件）⇒ 窗口拿到的必须是**那一份**状态，不是另建一份 |

⚠ **它需要一个"控制通道"（框架 → 软件），而那个通道今天还没有** ⇒ 如实登记为**下一轮的阻塞项**。
⚠ **不许做半成品**：半成的控制通道比没有更坏（会让人以为"切手动已经能开窗了"）。

### 7.1.1 为什么控制操作不该混进 AI 看到的那条腿

⚠ 控制操作（切写权 / 开窗）**不是给 AI 用的**。若把它们塞进**聚合端点导出的工具表**，
AI 就会看见并可能调用它们 —— 这**违背"AI 不许给自己解锁"的意图**（哪怕本生态裁决 2
放宽了"本机可信"，也**不该主动递给它**）。

⇒ **两条腿各自的可见面应当分开**：

| 腿 | 看见什么 |
|---|---|
| **AI 腿**（经聚合端点） | 能力面里**该给它**的部分（读 / 写 / 订阅） |
| **人手腿**（框架 / 面板 / GUI 窗口） | 能力面 **+ 控制操作**（切写权 / 开窗） |

⚠ 但它们**必须走同一道门、记同一本账**（§4 的纪律：可追溯，不是安全）。

#### ⭐ 落地方式：**两条端点**（已核查，不是"加个过滤"就行）

我核过框架现有的可见性机制，结论是"**用 scope 过滤**"**做不到**：

| 事实 | 出处 |
|---|---|
| `ToolDefinition` **有** `scope` 字段，注释说它是"投影期按 `ScopePolicy` 过滤的依据" | `mecha/tools.py` |
| `projection.py:89` 确实按 `policy.allows(side, s)` 过滤 —— ⚠ **但那只作用于命令投影** | `mecha/projection.py` |
| ⚠ `build_mcp_server(...)` **吃整个 `registry`**（`for schema in registry.schemas()`） | `mecha/providers/mcp.py:523` |
| ⚠ 所以**一条端点等于一个面**，无法在同一个 registry 上按 side 给出两套可见面 | （同一处） |

⇒ **定案：软件**可以**额外暴露一条**控制端点**（人侧专用）**：

| 端点 | 谁连 | 暴露什么 |
|---|---|---|
| 能力面端点（已有，端口文件 `.mcp-port`） | AI 腿（经聚合端点）+ 人侧读 | 该给 AI 的那部分 |
| ⭐ **控制端点**（新增，**独立端口文件**，例如 `.control-port`） | **只有框架/面板**（人侧） | `set_write_authority` · `open_manual_surface` … |

⚠ **"独立"是本质**：控制端点**不导出给 AI** ⇒ AI **看不见**切写权那个操作
（可见性由**端点的存在性**保证，不靠记得加过滤）；
⚠ 但**两条端点共用同一份 `Gate`/`Authority` 与同一本账**（§4 的纪律仍然成立）。

⚠ **替代方案（为什么不选）**：把控制操作放进能力面、再让聚合端点**不投影**它们 ——
那要给 `Aggregator` 加一层"按名字/标记过滤"，而这层过滤**只在这一处**有效，
**别的消费者**（任何直连 `:mcp-port` 的人）**仍然看得见**
⇒ "**忘了过滤**"会**静默**发生，而两条端点是**结构性**的。

#### ⭐ 控制通道的契约（定案，两端按此实现，**别各写一套**）

| 项 | 约定 |
|---|---|
| **端口文件** | `<svc_root>/.control-port`（⚠ **与 `.mcp-port` 并列、同名族**；写在软件根，与别的端口文件同源习惯） |
| **传输** | MCP over streamable-http（⭐ **复用已有那一套**，不发明第二种协议） |
| **谁连** | **只有框架 / 面板 / 人手腿** —— ⚠ **不导出给 AI**（AI 拿不到这个地址，也不经聚合端点） |
| **操作名** | `set_write_authority(mode)` · `open_manual_surface()` |
| **`set_write_authority` 的入参** | `mode`：`locked` / `human` / `ai` / `open`（⚠ **裸值**，见 §5.1 那条 `.value` 的坑） |
| **记账** | ⚠ 两个操作**都必须走同一道门、记同一本账**（§4 的纪律）—— 与 AI 的写**同一本** |
| **失败** | 未知 mode / 没有 manual 面 ⇒ **响亮失败**（不许静默）；⚠ 不存在的软件由**框架侧**在调用前判 |

⚠ **"只有框架连"这件事由什么保证**：由**地址的传递**保证 ——
`.control-port` 只被框架读（它在软件的启动环境里、由框架 spawn 时确定），
**AI 腿拿到的只有聚合端点的地址**。⚠ 本生态裁决 2 不做口令（"本机可信"），
但**不许因此把 `:control-port` 写进任何给 AI 的文本/工具输出**。

#### ⭐ 端到端的样子（三种操作各走哪条路，方便施工方对齐）

```
① 存活（起/停软件）     面板 → supervisor.start/stop            （框架内，已有）
② 切写权               面板 → .control-port → 软件内 ModeController（★ 本轮要做）
③ 按需开窗             面板[切到手动] → ②之后 → .control-port
                                    → 软件在本进程内开窗（复用已装配的桥）  （★ 与②同一个按钮触发）
```

#### ⚠ 控制端点**不按 `has_gui` 门控**（定案，回答施工方 EL 的未决）

施工方 EL 提了一条：*"控制端点现在每个 `--mcp` 进程都起（含 headless）——
若要'仅 `has_gui` 才起'，一行即可。"*

**定论：不门控，所有 `--mcp` 进程都起控制端点。** 理由：

| | |
|---|---|
| ⭐ **写权与"有没有窗口"是正交的**（§1 的三个生命周期） | 门控会把它们**耦合**起来 —— 正是 A3 要拆开的那件事 |
| ⚠ 而且**会造出一个盲区** | `has_gui=false` 的项目**再也切不了写权**；而人可能仍想"先把写权收回" |
| **没有 manual 面时怎么办** | ⭐ `open_manual_surface()` **响亮失败**（`no_manual_surface`）—— ✅ 已落；**不靠"端点不存在"来表达** |
| 代价 | 多一条**空闲**的 loopback 端点 + 一个端口文件；⚠ 与本架构换来的东西相比**可忽略** |

⚠ **与"AI 看不见"不冲突**：门控与否，控制端点的地址**都只给框架**（本文的"地址传递"保证）。

#### ⚠ 记账为什么**不能**走 `Gate.set`（施工方 EL 实测发现，**很重要**）

EL 实现时踩到并解决了一个**会自锁**的形状：

> `set_write_authority` **不能**过普通的写权门（`Gate.set`）——
> ⚠ **切写权本身就是它要改的那个东西**。
> 若它过门：切到 `ai` 之后，**人侧再也记不了账、也切不回来** ⇒ **死锁**。

⇒ **正确做法**：走 `Gate.record`（**只记史、不过写权门**）——
⭐ **仍然是同一本账**（§4.3 的纪律满足：查得到"谁在什么时候把写权切走了"），
但**不受被切的那个闸门约束**。⇒ 框架侧实现控制客户端时**别改成过门**。

#### ⚠ 两条实测踩到的坑（施工方 EL 记下的，**给下一位**）

| # | 坑 | 现象 |
|---|---|---|
| **1** | 在 **MCP 服务器线程**上直接建 Qt 窗口 | ⚠ **挂死**（Qt 要求 GUI 对象属于创建 `QApplication` 的那条线程）⇒ 必须**递队列回主线程** |
| **2** | 子进程用 `stdout=PIPE` 而判据正阻塞在 MCP 调用上 | 子进程日志把管**写满** ⇒ **卡在 write**；⚠ **现象像"开窗挂死"**（误诊风险）⇒ 输出**必须落文件** |

## 11. ✅ 步骤 0 证伪实验的结论（2026-10-08 实测，**两个前提都成立**）

先证伪再铺开的两个前提，**都成立**（脚本：EL 仓 `checks/three_layer_premises_selfcheck.py`，
7 组 / 19 子条件 全绿）：

| 前提 | 结果 |
|---|---|
| **P1** 软件进程能**同时**提供 MCP 服务与 PyQt 窗口 | ✅ 同一进程里 `for_shared` + `serve_mcp` + 真 Qt 窗口（matplotlib/pyqtgraph 已加载）并存；⭐ **窗口活着时**后台线程跑一次**真算**（numba 内核）而主线程泵 Qt 事件 ⇒ **跑完无崩溃**；真 MCP 客户端**往返通** |
| **P2** 写权切换**立刻生效** | ✅ **同一条 MCP 会话不重连**：切 `human` 后 AI 侧下一次写**当场**被拒（`authority_mode_mismatch`），人侧同一拍可写；切回 `ai` 反向同理 ⇒ **无"等一拍"** |

### ⭐ A4：新架构的**必改点**（本实验最重要的产出）

**同进程里再装配一次 `MainWindow` ⇒ 它自建一份桥 ⇒ `writer_lease_held`。**

⇒ **"GUI 窗口开在软件进程内"的前提是：窗口必须复用已有的 bridge，不能各建一份。**
（第一版因为两条桥落在了不同子目录而"竟然成功"，改正后才复现出这条 ——
⚠ 这也说明**"实验环境不对"能把致命问题藏起来**。）

⇒ 写进 §6 的项目义务：**窗口必须复用软件进程已有的那份桥/门**。

### ⚠ 三条**口径与更正**（不写下来就会被后人重踩）

| # | 内容 |
|---|---|
| **1** | ⚠ **native×Qt 的雷，EL 与 ML 不是同一条**：EL 的是 **QThread 生命周期 / `0xc0000409`**（`docs/GUI界面-专家手册.md:233-234`）；**lightgbm 必须先于 PyQt5** 那条是 **ML 的**。⚠ **别把两家的雷混成一条**（我在派工时就混过一次） |
