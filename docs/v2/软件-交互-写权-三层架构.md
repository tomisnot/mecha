## 0. 三条公理（其余全部由此推出）

| # | 公理 | 直接推论 |
|---|---|---|
| **A1** | **软件自己是状态所有者**：状态住在**软件进程自己的线程**里；软件是它的**唯一写宿主** | 交互面**永远不是**宿主 ⇒ 写租约**天然**满足（它防的"两个宿主"根本不出现） |
| **A2** | **交互面只是客户端**：AI 与人都是**同一层的客户端**，都通过面**读**与**影响**状态 | 两者**可同时挂**；它们之间**没有存活性互斥** |
| **A3** | **写权是软件进程内的硬闸门**，与"软件存活 / 客户端连接"**三权分立** | 切写权 ⇒ **不动进程、不动连接、不动状态** |

⭐ **A3 是这套架构的核心**：它把"**谁能影响**"从"**谁在跑**"里彻底摘了出来。
这正是用户反复强调的那句：*"状态在软件线程内，AI 和 GUI 都只是读取和影响它"*。

## 1. 三个生命周期，正交

```
① 软件存活      起 / 停 / 探活 / 重启          ← 面板的【存活滑块】
② 客户端连接    AI 腿（dsh）/ 人手腿（GUI）    ← 挂 / 摘，与①无关
③ 写权          LOCKED / HUMAN / AI / OPEN     ← 面板的【写权开关】，与①②无关
                （软件进程内）
```

| 操作 | 动 ① | 动 ② | 动 ③ |
|---|---|---|---|
| 关掉一个项目（存活滑块 off） | ✓ | 腿失联 | —— |
| **切写权给手动**（面板按钮 / GUI 按钮） | ✗ **不动** | ✗ **不动**（dsh 与面板**待命，不关闭**） | ✓ |
| AI 工作流收尾（提前结束对话） | ✗ | ✗ | ✗ ⚠ **与写权无关** |
| 热更新（改了软件代码） | ✓ 重启软件 | 腿自动重连 | ✗ |

⚠ **"切到手动之后 dsh 与面板不关闭、只是待命"** 是需求，不是妥协 ——
它们的**写**会被闸门拒，**读**照常，所以它们**本来就是"待命"这个语义**。

## 1.1 ⭐ 一次编排 **N 个站点**（多项目的地基 —— 原文漏了，实现因此只用 `sites[0]`）

⚠ **这一节是补写的**：`load_sites()` 从第一天就会找出**全部**站点声明
（还专门查站点名重复），但编排处处只取 `sites[0]` ⇒
⭐ **"多项目 + 一个 dsh"在实现上不存在**（面板只列第一个项目）。
根因是**本文没定义"多个站点该怎么编排"** ⇒ 实现就按"只有一个"写了。现补上。

### 定义

| 词 | 含义 |
|---|---|
| **站点**（`Site`） | **一个项目仓**的一份声明（`mecha_site.py` 的模块级 `SITE`） |
| **服务**（`Service`） | 站点里的**一个软件进程**（一个仓可以有多个） |

### 契约（**一次启动 = 一个 launcher，管 N 个站点**）

```
python -m mecha            ⇒  1 个 launcher 进程
                              1 个 runtime 目录（_mecha_runtime/）
                              1 个聚合端点     ← ⭐ AI 只连这一个
                              1 个 dsh         ← ⭐ 全生态只有一个
                              N 个站点、M 个服务（平铺进同一个 supervisor）
```

| # | 规则 | 为什么 |
|---|---|---|
| **1** | **服务平铺**：所有站点的 `services` 全部进**同一个** supervisor 的子进程表 | 一个 dsh 要能操作**全部**开着的软件 |
| **2** | ⭐ **服务 id 全局唯一**（跨站点也要唯一） | 它是**工具前缀**（`<svc_id>_<tool>`）⇒ 撞名 = AI 面前的工具名冲突。⚠ 现在只查了**站点名**重复，**没查服务 id** ⇒ 必须补，且**响亮失败** |
| **3** | **runtime 目录不取决于任何站点**：`Path.cwd() / "_mecha_runtime"`（**去掉** `_runtime_root(sites[0])` 那个入参） | 一次启动只有一个 runtime；挂在某个站点上会随"谁排在第一个"漂 |
| **4** | **启动顺序**：所有服务先起（站点之间**没有**依赖声明 ⇒ 用**稳定顺序**：按站点出现顺序、站点内按声明顺序）⇒ ⭐ **dsh 永远最后** | `build_children` 现在是"服务的拓扑序 + dsh 最后"，多站点只是把服务列表拉长 |
| **5** | **聚合端点覆盖全部站点的全部服务**（`AggregateRuntime(services=…)` 收平铺后的全集） | §7.1.1 的"一个聚合工具"要能报**所有**软件 |
| **6** | **面板列全部**：站点名 + 该站点的全部服务（**始终不变**） | §7 的"已注册项目清单始终不变" |
| **7** | ⚠ **站点名重复 ⇒ 响亮失败**（已有）；⚠ **服务 id 重复 ⇒ 响亮失败**（本轮补） | 两者都会让"工具前缀/状态归属"产生歧义 |

⚠ **不引入的新概念**：多站点**不需要**"生态声明文件"、不需要站点之间的依赖图、
不需要"站点组" —— ⭐ **站点之间互不知道对方存在**，只是同一个 launcher 把它们一起管了。
（这条是有意的：项目仓要能独立存在、独立声明，**不因为"被谁一起起"而改自己的写法**。）

### 1.1.1 ⭐ dsh 是**全生态一个**，由站点们**共同贡献**（原文漏了，实现踩到才补）

⚠ §1.1 只说了"1 个 dsh"，**没说"谁声明它、多家的 dsh 插件怎么办"**。
初次实现时施工方按"**只准一个站点声明 dsh**"写 ⇒ 而 `site.py` 里 `dsh` 是**必填**、
三家真项目**各声明一个** ⇒ ⭐ **多站点必然报错**（实测：`有 2 个站点声明了 dsh`）。
⇒ 契约写清如下：

| 项 | 规则 | 为什么 |
|---|---|---|
| **身份**（`command` / 端口偏好 / 超时 / `ready`） | 各站点**若都给了，必须一致**；不一致 ⇒ ⭐ **响亮失败** | "一个 dsh"意味着**只有一个身份**；静默取一家 = 我以为起的是我那种 |
| **`cwd`** | 取**第一个**声明了 dsh 的站点（站点顺序**稳定** ⇒ 不随扫描顺序漂） | dsh 只能有一个工作目录 |
| ⭐ **`patches` / `plugin_artifacts` / `env`** | **取全部站点声明的并集**（顺序 = 站点出现顺序） | ⭐ **每个项目都要把自己的监控面板挂上** —— 一个 dsh 要能看到**所有**项目 |
| **没有任何站点声明 dsh** | 框架用默认（`command=("dsh", "web")`、`cwd=`第一个站点的 cwd、端口偏好 3081、超时 8.0） | "架构直接安排好了"：项目**可以完全不管 dsh**。⚠ **必须带 `web`**：实测 `("dsh",)` 会立刻退出（`error: --profile <name> is required`）⇒ supervisor 反复重启 ⇒ **永远没有 dsh** |
| ⚠ **已知限制** | dsh 的 `cwd` 只有一个 ⇒ **插件自己要用绝对路径**（别依赖 cwd） | 我们无法给三家各一个 cwd；⚠ 故 `patches`/`plugin_artifacts` **一律按绝对路径声明** |

⭐ 这条的**收益正是目标**：**项目只管"我的软件怎么起 + 我的面板补丁是哪些"**，
**dsh 的编排、身份一致性、插件并集，全由框架安排。**

## 2. 连接拓扑

```
              ┌──────────────────────────────────────────────┐
              │  软件进程（项目自己的线程/事件循环）           │
              │                                              │
              │  ├─ 状态（StateModel）—— 唯一所有者            │
              │  ├─ 账（Journal）—— 唯一写宿主，持写租约        │
              │  ├─ 写权闸门（Mode）                          │
              │  ├─ 能力面（Capability Surface）───┐          │
              │  │    ├─ 读 / 检视                 │ 给 AI 腿  │
              │  │    ├─ 写（影响状态；过闸门）     │（聚合端点）│
              │  │    └─ 订阅（增量流）             │          │
              │  ├─ ⭐ 控制面（Control Surface）───┼──┐       │
              │  │    └─ 切写权 / 开窗             │  │ 给人手腿│
              │  │      ⚠ **独立端点**（§7.1.1）    │  │（框架/  │
              │  │      ⇒ **不给 AI 看**            │  │ 面板）  │
              │  └─ ★ GUI 窗口（PyQt，就在这个进程里）│        │
              └───────────────┬──────────────────┴────────┘
                              │ 能力面
                     ┌────────▼────────┐
                     │  AI 腿           │
                     │  dsh ─ 聚合端点  │
                     └─────────────────┘
```

⚠ **两处容易看漏，务必注意**：
1. **GUI 窗口在软件进程内**（裁决 1）⇒ 它读状态是**直接读**、改状态是**直接调**，
   ⚠ **但仍必须过写权闸门**（见 §4）；
2. ⭐ **控制面是另一条端点**（§7.1.1 定案）—— **它不挂在给 AI 的那条路上**。
   本图早期版本把"控制（切写权）"画在能力面里，⚠ **那与 §7.1.1 矛盾**（已改）。

## 3. ⭐ 两个用户裁决（**连同理由与代价，一起记档**）

### 裁决 1 · **GUI 窗口开在软件进程内**（不是独立客户端）

**理由（用户给的，很关键）**：
> *"当我要频繁热更新时，通常是 AI 模式下，GUI 根本不开。"*

⇒ 这句话**消掉了"独立客户端"唯一的大好处**：
独立客户端的主要优势是"软件重启时窗口不死"；
而**热更新发生在 AI 模式、GUI 根本没开** ⇒ 那个场景**不会发生**。

**换来的好处**（都是真的）：

| | |
|---|---|
| 窗口与状态**同进程** ⇒ 读状态是内存读取、改状态是函数调用，**没有通信层要设计** | |
| **不需要为 GUI 单独设计一套"怎么探活/怎么握手"** —— 它随软件就绪 | |
| ⭐ 与公理 A1 **字面一致**："状态在软件线程内" | |

**代价（如实记）**：
- 软件重启（热更新）时窗口会**跟着一起死** —— ⚠ 但**这正是裁决 1 之所以成立的前提**：
  热更新通常发生在 **AI 模式、GUI 根本没开** ⇒ 那个代价**不落在真实场景上**
  （⚠ 所以 §7.1 **禁止"AI 模式下也一直开窗"**，否则这个前提就没了）；
- 要在**跑业务逻辑的进程里启动 Qt** ⇒ ⚠ **每家各有自己的 native×Qt 雷，
  而且它们不是同一条**（我早期把两家的混成过一条，这里更正）：

  | 仓 | 那条雷 | 状态 |
  |---|---|---|
  | **EL** | **QThread 生命周期 / `0xc0000409`**（`energy-level/docs/GUI界面-专家手册.md:233-234`） | ⚠ **未充分实测**（步骤 0 只覆盖 offscreen + 单次演化，见 §11 口径 2） |
  | **ML** | **lightgbm（经 methods 顶层导入）必须先于任何 PyQt5 模块**，否则其 OpenMP 与 Qt 冲突 ⇒ fit 时 access violation | ⚠ **未实测**（ML 还没做进程内开窗） |

- ⚠ **"两条腿同门"要靠纪律守**：窗口**能**直接调内部函数而不走闸门 ⇒
  **必须有一条判据**钉住"GUI 的写也过闸门"（不许长后门）——
  ✅ EL 已落（`checks/inprocess_gui_selfcheck.py` 组 ③：GUI 的写**账里有它**且带 `actor=gui`）。

### 裁决 2 · **写权依靠"本机可信"，不专门做防护机制**

**用户原话**：
> *"写权不用专门写机制防着，默认 AI 会配合，这不是安全问题只是工作需要，依靠'本机可信'即可。"*

**⇒ 因此**：切写权的通道**不做凭证**、不做"人侧/侧"鉴权，**本机发起的请求即可切**。

⚠ **如实记下这让渡了什么**：
框架原有的硬规则是 **"只有 human 侧能切模式；AI 不能给自己解锁"**
（`authority.py::switch_mode` 的 `side != "human"` 判定，注释写着 *"护栏仍在：AI 面改不了 mode"*）。
**本裁决显式放开它** —— 理由是本生态是**单用户开发环境**，
**默认 AI 配合**，这是**协作问题不是对抗问题**。

⚠ **但不许把它记成"我们忘了做安全"**：
- 这条是**显式裁决**，有理由（单用户、协作、默认配合）；
- ⚠ **触发条件**：将来若某项目要跑**不受信的内容**（多用户 / 联网服务 / 第三方插件），
  **必须重新裁决**这条，而不是沿用它；
- ⇒ 实现上**保留那个参数**（`switch_mode` 的 side 判定**别删**），
  只是**本生态默认不启用**它 —— 这样将来要收紧，**是一行开关的事，不是重写**。

## 4. 能力面：**门和账只有一个，形状可以多**

> ⭐ **先说清这一节最容易读错的地方。**
>
> ⚠ **早期版本这里写的是"两条腿共用同一个面"** —— 那句**过头了**，与 §7.1.1 冲突。
> 按框架的**核心原则 2**（`使用模式与核心原则.md`），原文是：
>
> > **"一条路"不是说"所有功能长一个样"。形状可以多……该长什么样就长什么样；
> > 门和账只有一个 —— 不管什么形状、谁在调，都过同一道门、落同一本账。
> > ⇒ 同一套治理 ≠ 同一个形状。**
>
> ⇒ **正确的说法**：

| | |
|---|---|
| **门 / 账 / 监控面 / 能力面这四件** | ⭐ 是**软件自己的**，**不因操作者而存在**；人和 AI 是它的**两条腿**，**它不归任何一条腿** |
| **形状（谁能调什么、面怎么分）** | ⭐ **可以多** —— ⚠ **控制操作就是另一种形状**（走独立端点，§7.1.1），**这不违反原则 2** |

### 4.1 形状一：能力面（给 AI 腿的那一条）

| 类 | 例子 | 谁能调 |
|---|---|---|
| **读 / 检视** | `read_state` · `inspect(page)` · `query_runs` | AI 腿 + 人侧读 |
| **写（影响状态）** | `set_param` · `run` · `cancel` | ⚠ **过写权闸门**（谁都一样） |
| **订阅（增量流）** | `subscribe(since)` → 事件流 | AI 腿 + GUI |

### 4.2 形状二：控制面（给人手腿的那一条）

| 操作 | 例子 | 谁能调 |
|---|---|---|
| **控制** | `set_write_authority(mode)` · `open_manual_surface()` | ⭐ **只有框架 / 面板 / 人手腿** |

⚠ **为什么它必须是另一种形状（独立端点）**：见 §7.1.1 ——
"**AI 看不见切写权那个操作**"要靠**端点的存在性**保证，**不能靠记得加过滤**。

### 4.3 ⚠ 一条不许破的纪律（即使不做安全）

**GUI 的写必须与 AI 的写走同一道门、记同一本账**（"人机同门"）。
理由不是安全，是**可追溯**：人改了什么、AI 改了什么，**在同一本账上分得清**
（`Channel.actor` 区分 `gui` / `mcp`，`side` 记录写权归属）。
⇒ **要有判据**：GUI 的写**必须**在账里出现，且**带它的 actor**。

⚠ **同一纪律也管控制操作**：`set_write_authority` / `open_manual_surface`
**也必须落账**（§7.1.1 的契约里已写）。否则"**谁在什么时候把写权切走了**"查不到 ——
那正是**原则 2 说的"绕过去的路"**（`使用模式与核心原则.md` §3 原则 2）。

## 5. 写权的语义（在裁决 2 下的最终形态）

```
出厂：LOCKED（nothing ships enabled —— 保留）
初始化：由【启动者】在 spawn 时声明（人是启动者 ⇒ "我起它就是要用"）
运行中：任何本机客户端都可请求切（裁决 2）
        ⇒ 切完【立刻生效】（下一次 gate 判定就用新值）
```

⚠ **"立刻生效"是可判的**，应写进判据：
切到 `HUMAN` 之后，**AI 的下一次写必须被拒**（`authority_mode_mismatch`），
而**人在同一条腿上立刻能写**。不许有"等一拍"的模糊语义。
✅ **已实测成立**（§11 的 P2：同一条 MCP 会话不重连，当场被拒）。

### 5.1 ⭐ `initial_mode` 用什么通道交给软件 ⇒ **环境变量**（定案）

| 变量 | 含义 | 谁读 |
|---|---|---|
| `MECHA_SOFTWARE_ROOT` | 这份软件的数据根（≈ `Service.data_root`） | 软件进程 |
| `MECHA_INITIAL_MODE` | 启动者声明的初始写权（`locked`/`human`/`ai`/`open`） | 软件进程 |

**为什么是 env 而不是 argv**（三条，缺一不可）：

1. ⭐ **与各项目的参数风格无关** —— 三家的 CLI 风格完全不同（`argparse` / `typer` / …），
   env 是**唯一**对三家都一样的通道；
2. 它**不占**软件的参数面（不会与项目自己的 `--mode` 之类打架，也不用改各自的解析器）；
3. 符合语义：写权是**运行环境给的**，不是用户敲的命令行参数。

**框架侧责任**：`spawn` 软件时注入这两个，走**已统一的注入点**
（与 `PYTHONIOENCODING` 同一处 ⇒ 天然带"**空串 = 显式取消该变量**"的语义）。

**软件侧责任**（步骤 2 的项目活）：**读** `MECHA_INITIAL_MODE`，装配闸门时**应用**它。

⚠ **框架只声明 `initial_mode`、不 spawn 软件进程内的闸门** ——
闸门在**软件进程内**（公理 A3）⇒ **送到**软件是双方约定，**应用**它是软件的事。

## 7.1 ⭐ 窗口**按需开**，不是启动就开（**被识破的矛盾**）

裁决 1 选"窗口开在软件进程内"的**唯一理由**是用户那句：

> *"当我要频繁热更新时，通常是 AI 模式下，**GUI 根本不开**。"*

⇒ ⚠ 所以 **"AI 模式下窗口也必须一直开着"是自相矛盾的** ——
那样热更新时窗口会**总是**跟着重启，等于把当初要避开的代价请了回来。

⇒ **定论**：

| | |
|---|---|
| **默认** | 软件进程 **headless**（不开窗）—— 这才是"AI 组"的常态 |
| ⭐ **开窗的时机** | **切到手动时**（与"写权切到 HUMAN"**同一个按钮**触发的两件事） |
| 机制 | ⭐ **软件暴露一个控制操作**（人侧调用）⇒ **软件在它自己的进程内开窗**（复用已装配的那份桥） |
| ⚠ 为什么"开在软件进程内" | 公理 A1（状态所有者是软件）⇒ 窗口拿到的必须是**那一份**状态，不是另建一份 |

✅ **那个控制通道已经落地**（本文 §7.1.1 定案：独立端点 `.control-port`；
框架提供**唯一实现** `mecha/software_control.py`，三家只交 3 个回调 + 2 个值）。
⚠ 原句「那个通道今天还没有 ⇒ 登记为下一轮的阻塞项」**已过期**，这里改准。
⚠ **不许做半成品**：半成的控制通道比没有更坏（会让人以为"切手动已经能开窗了"）。

### 7.1.1 为什么控制操作不该混进 AI 看到的那条腿

⚠ 控制操作（切写权 / 开窗）**不是给 AI 用的**。若把它们塞进**聚合端点导出的工具表**，
AI 就会看见并可能调用它们 —— 这**违背"AI 不许给自己解锁"的意图**（哪怕本生态裁决 2
放宽了"本机可信"，也**不该主动递给它**）。

⇒ **两条腿各自的可见面应当分开**：

| 腿 | 看见什么 |
|---|---|
| **AI 腿**（经聚合端点） | 能力面里**该给它**的部分（读 / 写 / 订阅） |
| **人手腿**（框架 / 面板 / GUI 窗口） | 能力面 **+ 控制操作**（切写权 / 开窗） |

⚠ 但它们**必须走同一道门、记同一本账**（§4 的纪律：可追溯，不是安全）。

#### ⭐ 落地方式：**两条端点**（已核查，不是"加个过滤"就行）

我核过框架现有的可见性机制，结论是"**用 scope 过滤**"**做不到**：

| 事实 | 出处 |
|---|---|
| `ToolDefinition` **有** `scope` 字段，注释说它是"投影期按 `ScopePolicy` 过滤的依据" | `mecha/tools.py` |
| `projection.py:89` 确实按 `policy.allows(side, s)` 过滤 —— ⚠ **但那只作用于命令投影** | `mecha/projection.py` |
| ⚠ `build_mcp_server(...)` **吃整个 `registry`**（`for schema in registry.schemas()`） | `mecha/providers/mcp.py:523` |
| ⚠ 所以**一条端点等于一个面**，无法在同一个 registry 上按 side 给出两套可见面 | （同一处） |

⇒ **定案：软件**可以**额外暴露一条**控制端点**（人侧专用）**：

| 端点 | 谁连 | 暴露什么 |
|---|---|---|
| 能力面端点（已有，端口文件 `.mcp-port`） | AI 腿（经聚合端点）+ 人侧读 | 该给 AI 的那部分 |
| ⭐ **控制端点**（新增，**独立端口文件**，例如 `.control-port`） | **只有框架/面板**（人侧） | `set_write_authority` · `open_manual_surface` … |

⚠ **"独立"是本质**：控制端点**不导出给 AI** ⇒ AI **看不见**切写权那个操作
（可见性由**端点的存在性**保证，不靠记得加过滤）；
⚠ 但**两条端点共用同一份 `Gate`/`Authority` 与同一本账**（§4 的纪律仍然成立）。

⚠ **替代方案（为什么不选）**：把控制操作放进能力面、再让聚合端点**不投影**它们 ——
那要给 `Aggregator` 加一层"按名字/标记过滤"，而这层过滤**只在这一处**有效，
**别的消费者**（任何直连 `:mcp-port` 的人）**仍然看得见**
⇒ "**忘了过滤**"会**静默**发生，而两条端点是**结构性**的。

#### ⭐ 控制通道的契约（定案，两端按此实现，**别各写一套**）

| 项 | 约定 |
|---|---|
| **端口文件** | `<svc_root>/.control-port`（⚠ **与 `.mcp-port` 并列、同名族**；写在软件根，与别的端口文件同源习惯） |
| **传输** | MCP over streamable-http（⭐ **复用已有那一套**，不发明第二种协议） |
| **谁连** | **只有框架 / 面板 / 人手腿** —— ⚠ **不导出给 AI**（AI 拿不到这个地址，也不经聚合端点） |
| **操作名** | `set_write_authority(mode)` · **`read_write_authority()`** · `open_manual_surface()` |
| **`set_write_authority` 的入参** | `mode`：`locked` / `human` / `ai` / `open`（⚠ **裸值**，见 §5.1 那条 `.value` 的坑） |
| **记账** | ⚠ 两个操作**都必须走同一道门、记同一本账**（§4 的纪律）—— 与 AI 的写**同一本** |
| **失败** | 未知 mode / 没有 manual 面 ⇒ **响亮失败**（不许静默）；⚠ 不存在的软件由**框架侧**在调用前判 |

##### ⭐ `open_manual_surface` 的三种结局（**"人面常开"不是失败** —— 2026-10-09 补，实测踩到）

⚠ 上面那行"没有 manual 面 ⇒ 响亮失败"**只属于真的没有人面的项目**，
而**人面一直开着的项目**（GP 的人面是**浏览器里的 Web 工作台**，随服务常在）
**不该**走那一条 —— 否则面板上每次点「切到手动」都会红一次"**窗口没开成**"，
而人面**早就在那儿**（⭐ 假故障：本工程最忌的"看着像坏了"）。

| 项目的形态 | `open_manual_surface()` 应当回什么 | 例子 |
|---|---|---|
| 需要"开"的面（进程内窗口） | 第一次 `opened`，之后 `already-open`（**幂等**） | EL · ML |
| ⭐ **人面常开**（随服务一直在） | ⭐ **恒为 `already-open`（幂等成功）** —— ⚠ **不是** `no_manual_surface` | GP（Web 工作台） |
| **真的没有人面** | **响亮失败** `no_manual_surface` | `has_gui=false` 的项目 |

⚠ **三者都是"如实"**：判据是"**报的必须与真实形态一致**"，不是"失败才诚实"。
⚠ 随之 **`has_gui` 的语义仍是"有没有人操作的那个面"**（GP=True 是对的）；
变的只是"**它需不需要被开**"——那是**项目自己的知识**，框架只转交。

##### ⭐ 写权自省**上升进框架**（GP 已有成熟实现，照抄并推广 —— **别让三家各写一遍**）

⇒ ⭐ **把 GP 这套上升为框架的标准件**，三家只做"注册"，不各写一遍。

| 项 | 定案（**照 GP，不发明**） |

| **返回字段** | ⭐ `mode` · **`ai_can_write`** · **`human_holds`** · **`how_to_open`** |

##### ⭐ AI 面**怎么拿到**它（定案：**一个聚合工具**，不是每个软件一个）

⚠ 施工方（框架侧）留了一条未决：`register_authority_read` 已就位但**未接线** ——
"聚合端点自动把 `read_write_authority` 挂到 AI 面"需要一条"**从软件进程读当前写权**"的通路。

**定案**：**聚合端点暴露一个 `read_write_authority`**，一次报**全部在跑的软件**的写权：

```jsonc
// 返回形态（示意）
{ "ok": true,
  "services": [
    {"id": "ML", "mode": "ai",   "ai_can_write": true,  "human_holds": false},
    {"id": "EL", "mode": "human","ai_can_write": false, "human_holds": true }
  ],
  "how_to_open": "…"        // ⚠ 由【项目声明】给（见下），框架不写死
}
```

⚠ **四条要点**：

| # | 要点 |
|---|---|
| **1** | ⭐ **不要缓存**：AI 有需要才调；控制调用是 loopback、很便宜。⚠ 缓存会带来"**失效策略**"这个**新的复杂度面**，而它换来的只是省一次本机往返 |
| **2** | ⭐ **`how_to_open` 由项目声明提供**（在 `Service` 上加一个"怎么切到人工"的**自由文案字段**）—— 框架里**不许写死任何项目名/路径**（领域知识不进框架） |
| **3** | ⚠ **只报在跑的软件**：没起来的**不编造**（"读不到" ≠ "确实没有"，铁律 8） |
| **4** | ⚠ **与"每个软件自己在能力面注册"不冲突**：两者都行，但**AI 经过聚合端点** ⇒ 聚合那个是 AI 实际会用的那一个。⇒ ⭐ **GP 收敛（4f）时要注意**：GP 现在自己注册的那个 `read_authority` 与聚合这个**会并存**，收哪个、怎么收，**得先看清楚**（它可能有自己的字段/消费者），**不许盲删** |

⚠ **"只有框架连"这件事由什么保证**：由**地址的传递**保证 ——
`.control-port` 只被框架读（它在软件的启动环境里、由框架 spawn 时确定），
**AI 腿拿到的只有聚合端点的地址**。⚠ 本生态裁决 2 不做口令（"本机可信"），
但**不许因此把 `:control-port` 写进任何给 AI 的文本/工具输出**。

#### ⭐ 端到端的样子（三种操作各走哪条路，方便施工方对齐）

```
① 存活（起/停软件）     面板 → supervisor.start/stop            （框架内，已有）
② 切写权               面板 → .control-port → 软件内 ModeController（★ 本轮要做）
③ 按需开窗             面板[切到手动] → ②之后 → .control-port
                                    → 软件在本进程内开窗（复用已装配的桥）  （★ 与②同一个按钮触发）
```

#### ⚠ 控制端点**不按 `has_gui` 门控**（定案，回答施工方 EL 的未决）

施工方 EL 提了一条：*"控制端点现在每个 `--mcp` 进程都起（含 headless）——
若要'仅 `has_gui` 才起'，一行即可。"*

**定论：不门控，所有 `--mcp` 进程都起控制端点。** 理由：

| | |
|---|---|
| ⭐ **写权与"有没有窗口"是正交的**（§1 的三个生命周期） | 门控会把它们**耦合**起来 —— 正是 A3 要拆开的那件事 |
| ⚠ 而且**会造出一个盲区** | `has_gui=false` 的项目**再也切不了写权**；而人可能仍想"先把写权收回" |
| **没有 manual 面时怎么办** | ⭐ `open_manual_surface()` **响亮失败**（`no_manual_surface`）—— ✅ 已落；**不靠"端点不存在"来表达** |
| 代价 | 多一条**空闲**的 loopback 端点 + 一个端口文件；⚠ 与本架构换来的东西相比**可忽略** |

⚠ **与"AI 看不见"不冲突**：门控与否，控制端点的地址**都只给框架**（本文的"地址传递"保证）。

##### ⚠⚠ 但**那个盲区还是出现过** —— 换了一扇门（2026-10-09 审计抓到，本节据此补全）

⚠ **这一小节是补写的**：上面那条裁决**只落到了"端点起不起来"**，
而**框架的面板逻辑**把两件事又焊了回去：

```
write_authority_state()  一见 has_gui=False  ⇒ 直接回 ok=False「无手动面」
control_write_authority() ⇒ 一见 ok=False     ⇒ 当场放弃
⇒ ⭐ has_gui=false 的项目【还是切不了写权】 —— 正是上面那条裁决要避免的盲区
```

⭐ **教训**：裁决写在"端点"这一层，**同一件事在"控制器"那一层又长回来了**。
⇒ "**别锁大门**"这句话不够，得说清"**也别锁里屋的门**"。

**★ 定案（把两件事拆开报）**：

| 问的问题 | 取决于 | 谁来答 |
|---|---|---|
| **能不能切写权**？ | ⭐ **控制端点通不通** | 控制器如实报（`ok`） |
| **有没有"手动面"可开**？ | ⭐ **`has_gui`** | 控制器如实报（`has_gui`） |

⚠ ⚠ **两者正交**：`has_gui=false` **不再**意味着"不能切写权"。
⇒ 面板据此给**两个不同的动作**（⚠ 名字不同，因为它们**干的事真的不同**）：

| `has_gui` | 面板按钮（归人） | 实际做什么 | 反向按钮 |
|---|---|---|---|
| **true** | 「**切到手动**」 | ① `set_write_authority(human)` ② `open_manual_surface()`（⚠ **两步分开报告**） | 「交还给 AI」⇒ `set_write_authority(ai)` |
| **false** | 「**收回写权（冻结）**」 | ⭐ **只** `set_write_authority(locked)` —— ⚠ **不调** `open_manual_surface`（它没有面，调了只会响亮失败） | 「交还给 AI」⇒ `set_write_authority(ai)` |

⚠ ⚠ **为什么 `has_gui=false` 用 `LOCKED` 而**不是** `HUMAN`**（这一条要想清楚，别照抄有窗口那样）：

`Mode.HUMAN` 的语义是"**人侧通道可写**"。而**没有手动面的软件里，
人根本没有一条可写的通道** ⇒ 给它 `HUMAN` 等于**贴一个"写权归人"的标签、
实际上谁都不能写** —— ⚠ **那是骗人的标签**（本项目最忌的"看着像真的"）。
⇒ 这种情况人的真实意图是**"先把写权收回"**（文档上面自己写的那句），
而 `LOCKED` 的语义正是"**谁都不能写**（维护/急停）" ⇒ ⭐ **`LOCKED` 才是老实的那一个**。
⚠ 按钮因此叫「**收回写权（冻结）**」而**不叫**「切到手动」—— 后者会让人以为"接下来我能点着写"。

⚠ **§7 那条"按钮只在 `has_gui: true` 上显示"仍然成立**：它说的是**「手动面」那一档**
（"开窗"这件事）⇒ `has_gui=false` 的项目**没有"手动面"这一档**，
但它**有"收回写权"这一档** —— 两者**不是同一件事**（这正是本节要拆开的东西）。

⚠ **同一本账照旧**：`freeze` 走的也是控制端点、也落 `Gate.record`（§4.3）。

#### ⭐ 必须有 `read_write_authority()` —— **否则面板就是第二份真值**（定案）

⚠ 施工方（框架侧）报到一条未决，它说得对：

> *"契约没有'读当前写权'的查询 ⇒ 面板显示的是**自己的意图**并如实标注
> （显示猜的值更坏）"*

**⇒ 定论：补一个读操作，名字叫 `read_write_authority()`。** 理由三条：

| # | 理由 |
|---|---|
| **1** | ⭐ **铁律 7 单一真值来源**：写权**住在软件进程内**（公理 A3）。面板若只记"我设过什么"，那它**就是第二份真值** —— ⚠ 软件自己切换、或**软件重启**（热更新！）之后，面板**必然显示错** |
| **2** | ⭐ **框架不能替它猜**：框架连写权都改不了（只能请求软件改）⇒ 它更没资格**报**当前值 |
| **3** | **命名法**：`get_*` 是被禁的（工具命名守卫）⇒ 官方惯例 **`get_* ⇒ read_*`** ⇒ 用 **`read_write_authority()`** |

⚠ **操作名因此定为三个**：`read_write_authority()` · `set_write_authority(mode)` · `open_manual_surface()`。

⚠ **面板的正确形态**：写权栏显示的是 ⭐ **从控制端点读回来的当前值**，
不是"上次点过什么"；读不到时**如实说"读不到"**（铁律 8：**读不到 ≠ 确实没有**）。
EL 实现时踩到并解决了一个**会自锁**的形状：

> `set_write_authority` **不能**过普通的写权门（`Gate.set`）——
> ⚠ **切写权本身就是它要改的那个东西**。
> 若它过门：切到 `ai` 之后，**人侧再也记不了账、也切不回来** ⇒ **死锁**。

⇒ **正确做法**：走 `Gate.record`（**只记史、不过写权门**）——
⭐ **仍然是同一本账**（§4.3 的纪律满足：查得到"谁在什么时候把写权切走了"），
但**不受被切的那个闸门约束**。⇒ 框架侧实现控制客户端时**别改成过门**。

#### ⚠ 两条实测踩到的坑（施工方 EL 记下的，**给下一位**）

| # | 坑 | 现象 |
|---|---|---|
| **1** | 在 **MCP 服务器线程**上直接建 Qt 窗口 | ⚠ **挂死**（Qt 要求 GUI 对象属于创建 `QApplication` 的那条线程）⇒ 必须**递队列回主线程** |
| **2** | 子进程用 `stdout=PIPE` 而判据正阻塞在 MCP 调用上 | 子进程日志把管**写满** ⇒ **卡在 write**；⚠ **现象像"开窗挂死"**（误诊风险）⇒ 输出**必须落文件** |

## 7.3 ⭐ **多项目监控面板**的形状（2026-10-09 用户裁决 + dsh 契约核准）

### 7.3.1 用户要什么（原话）

> *"我希望**开了几个项目就有几个监控面板侧边栏**，**对话框上面的按钮还是只有一个**，
> 但是**唤起的是所有监控面板**。从监控任务本身来讲，各算各的账，应该没有矛盾。"*
> *"不是说目前这次修改要减少各项目修改量，而是说**把框架和接口整理好，
> 未来新增一个项目接入，接入负担尽量低**。"* · *"自定义保留为可选是对的。"*

⭐ **判据是"接口干不干净 + 新项目接入要写几行"，不是"这三家少改几行"。**

### 7.3.2 ⛔ 先说清**已经踩到的三个坑**（都实测/核过，别再重踩）

| # | 坑 | 事实 |
|---|---|---|
| **1** | "没有每项目一个按钮" | ⛔ **错**。**每家都在浏览器那一半注册了一个**：<br>`dsh/src/client/index.ts` → `ctx.slots.inject('conversation.session.header.actions', …)`<br>⇒ **N 个项目 = N 个「◈ 监控」按钮**（就在**对话框上面**） |
| **2** | 修了 host 半就够了 | ⛔ **不够**。面板 UI 在 **client 半（浏览器 bundle）**，那是**另一个模块实例**<br>⇒ host 半的 `openPanelConfig` **到不了它** |
| **3** | ⭐ **dsh 契约本身**：`sidebarRightTabs` **拒绝重复 `id`**、**拒绝同一 tier 里同一 `kind` 的第二次注册**<br>且 **`title` 是"每次使用都重读的 thunk"** | ⇒ ⚠ **"N 个服务 ⇒ N 个 tab"用"一个 `kind` 一个 `id`"的形状做不到**；<br>⚠ 而 thunk 正是 `title: () => panelConfig().title` **在渲染时读到栈顶那个人**的原因 |

（出处：dsh 源码拷贝 `deepseek-harness/.agents/notes/implemented/architecture/2026-09-05-sidebar-tab-types-and-navigation.zh.md`）

### 7.3.3 ★ 定案：**命名与归属**（这一节是施工的脊柱，先定死再动代码）

| 项 | 定案 | 为什么 |
|---|---|---|
| ⭐ **每个服务一个 `kind`** | `kind = "mecha:<svc_id>"`（如 `mecha:ML`） | ⚠ 契约拒绝**同 tier 同 kind 二次注册** ⇒ kind 必须**逐服务**区分 |
| ⭐ **每个服务一个 `id`** | `id = "mecha-panel:<svc_id>"` | ⚠ 契约拒绝**重复 id** |
| **正文/标题的 slot key** | 用**该类型的 `id`**（`sidebar.right.pane.tab` / `…tab.title`） | 契约如此；⚠ **这就是"各算各的账"的落点** |
| ⭐ **按钮** | **框架提供唯一一个**；语义 = **"把监控面带到眼前"** ⇒ ⭐ **打开右栏那个内置的「guide」页**（`sidebarRight.openTab('guide')`），⚠ **不是** 裸 `layout.openRightbar(...)` | 用户："唤起的是**所有**监控面板" ⇒ 按钮**不该挑某一个 tab**。⚠ **2026-10-09 实测更正**：`openRightbar` **只开栏、不选任何页** ⇒ 用户看到的是**空栏**（"点了一个都没开启"）；而 guide 页**正好**列出所有投过 `guide` 条目的监控 tab |
| ⭐ **每个监控 tab 投一个 guide 条目** | 注册 tab 类型时带 `guide: [{id, order, title}]`（`order` = **声明顺序**） | ⭐ 这是"**一个按钮、N 个面板**"的**唯一原语**（dsh 的 `defaultSeed()`：**guide 条目 0 个或多个 ⇒ 右栏默认页 = guide 页**）；⚠ 不投条目 ⇒ 那个项目**不上那一页** |
| ⭐ **参数从哪来** | **声明**（`mecha_site.py`）⇒ 框架**起 dsh 时生成**、经 env/argv 递给框架自己的插件 | `mecha_site.py` **本来就是框架↔项目唯一那份契约**；⚠ **端口号不许进给 AI 的文本** |
| ⭐ **框架自己的 dsh 插件** | 由**框架的 patch** 带上（`launch.py::merge_dsh` 已经在合并 patches ⇒ 天然能带） | ⚠ 否则"新项目还得自己挂框架插件" = **没预付** |
| ⚠ **自定义 UI** | **保留为可选**（项目仍可贡献自己的 tab/插件，如 GP 的"简报" iframe） | 用户明确保留；⚠ 但**默认那条路必须零 dsh 代码** |

⭐ **目标**：**新项目接入监控面板 = 在 `mecha_site.py` 声明几行，dsh 侧一行都不用写。**

### 7.3.4 施工分两段（⚠ **每段完就 commit**，别混）

| 段 | 内容 |
|---|---|
| **① 先修对** | 资产 **client 半**让配置**跟着那次注册走**（与 host 半 `openPanelConfig` 对称）；<br>⭐ **按钮归框架**（唯一一个，"开右栏"语义）；三家删掉各自的按钮那段 |

### 7.3.5 判据（⭐ 三条都要求**真装两份**来验，不许只用替身；⚠ 红证要实测能红）

1. ⭐ **按钮恒为 1 个**（装 N 个服务 ⇒ 会话头部**只有一个**监控按钮）；
2. ⭐ **N 份配置并存、各读各的**（**标题与取数路由都不许**落到别人那份）；

其中三份项目隔离 overlay 都改**同一个 `id: webserver`**（**整块替换**）⇒ **谁的块最后生效取决于并集顺序**；
⚠ **"三家 dsh 插件是否都真加载"验不了**（要真 dsh + `--dump-config`）⇒ **留给用户的真机测试**。

### 7.3.6 ⭐ 阶段②-1 定案：**监控声明住在 `Service` 上**（字段形状）

⚠ **先定形状再动代码**（本节就是那份形状）。⭐ 唯一原则：**端点的地址/标题/额外页
只能有【一处】真值 —— 声明里**；框架只**生成与转交**，**不解释**、不写死任何项目值。

```python
@dataclass(frozen=True)
class MonitorSpec:
    """一个服务的**监控面**声明（它自己有监控端点时才写）。"""
    #: host 半注册的只读路由；client 半 fetch 同一个串。**必填**。
    route_path: str
    #: 权威写的**监控端口文件名**（相对 `cwd`）或绝对路径。**必填**。
    port_file: str
    #: 面板标题（纯展示；模型不读它）。缺省 ⇒ 用 `Service.id`。
    title: str = ""
    #: 该项目**自己的**附加页（如 `[{id, label, path}]`）。缺省 ⇒ 无。
    extra_pages: tuple[ExtraPage, ...] = ()
```

`Service` 上加**一个可选字段**：`monitor: MonitorSpec | None = None`。

| 为什么这样 | 理由 |
|---|---|
| **一个 `monitor=` 子结构**，不是把 3~4 个字段平铺到 `Service` | 它们**同生同死**（有监控面才有路由/端口文件）⇒ 子结构让"没监控面"= `None` **在类型上可表达**，平铺则要 4 个各自校验"要么都填要么都不填"（那正是两份真值的温床） |
| **必填只有 two**（`route_path` / `port_file`） | 就是资产 `PanelOptions` 那三个里**项目特有**的两个；`title` 缺省用 `svc_id`（人看的，不必逼项目编一句） |
| `title` **缺省不是资产的中性默认** | 资产**不给默认**（未注入即抛）是刻意的；这里的缺省是**框架从声明推出来的**（`svc_id`），⇒ 仍然只有一处真值 |
| **`extra_pages` 进声明**（原在项目的 `extraPages.ts`） | 那本来就是**数据**（`id`/`label`/`path`）；住进声明 ⇒ 阶段② 的"零 dsh 代码"才成立 |

**框架生成的那份参数**（起 dsh 时，经 env 递给自己那份 client 插件；⚠ **不含端口号**）：

```jsonc
// MECHA_PANEL_SERVICES = [{id, kind, tabId, routePath, portFile, title, extraPages}]
// ⚠ 只含**声明了 monitor 的服务**；END 端口号由 host 半的只读路由现取（动态端口，不进这里）
```

⭐ **新项目接入要写的行数**（目标，阶段②-2 完成后）：`mecha_site.py` 里 **3~5 行**
（`monitor=MonitorSpec(route_path=…, port_file=…)`，有附加页再给 `extra_pages`）。

### 7.3.7 ⚠ 阶段②-2 的**真实门槛**（我在实现前查到的，必须先裁决）

⭐ **"项目 dsh 侧一行都不写"在当前加载方式下【做不到】**：项目的 client 半不是被 dsh
动态加载的，而是**项目自己的 bundle**（`package.json` 的 `exports["./client"]` →
`lib/client.js`）——它**在项目 `npm run bundle` 时静态打包**，本项目 import 什么就进什么。
⇒ 框架的 client 插件**不在那个 bundle 里**就不会跑（这与 host 半不同：host 半是
`cordis.patch.yml` 里 `- id: … name: './lib/index.mjs'` 能指的独立包）。

| 选项 | 项目要写的 | 评价 |
|---|---|---|
| **A. 项目 bootstrap 一行 import**（框架 patch 带插件，但 client bundle 仍需 import 一次） | `+1 行`（`import '@mecha/dsh-panel/auto'`） | ⭐ **推荐**：真实、可验；"零 dsh 代码"退让为"**一行 import**"，其余全归声明 |
| B. 让 dsh 支持"从 patch 动态加载 client 插件" | 0 行 | ⚠ 要**改 dsh 本体**（不是本生态的仓）⇒ 超出本工程边界，且我**未核实**它是否已有此机制 |
| C. 框架改 patch 去注入 client bundle | 0 行 | ⚠ patch 能改的是**配置**，不是**已打包的 JS** ⇒ 结构上不成立（与 B 同因） |

##### ★ 裁决（2026-10-09）：**选 A** —— "零 dsh 代码"如实退让为"**声明 + 一行 import**"

**为什么不是 B**：B 要**改 dsh 本体**（那是**另一个项目**，不在本生态四仓里），
而且它的机制**未核实**。⚠ 我们**依赖** dsh；为了省项目那一行 import 去 fork/改它，
是**把便宜占在自己这边、把风险推给上游**。
**为什么不是 C**：patch 改的是**配置**，不是**已打包的 JS** ⇒ 结构上不成立。

⇒ ⭐ **A 为准**：项目侧 = **声明 3~5 行** + **一行 bootstrap**

### 7.3.10 ⭐ 定案：**AI 的工具表是"活的"**（2026-10-10 用户裁决 = 方案 B）

> 用户原话：**"我不要绕开 ②③，就按照最正规的方式来，不要在一次工具调用里顺手发"**。

**问题（真机实测）**：AI 手里那张工具表**永远停在"端点启动那一刻"** ⇒ 软件的工具一个都看不到；
而且连框架自己的元工具都**调不动**。三件事缺一不可：

| # | 要什么 | 做法 | 实测证据 |
|---|---|---|---|
| ① | **表真的会变** | ``McpEndpoint.publish_tools`` **幂等对账**（多退少补、描述变了的重铺 ⇒ 墓碑语义保住）；改表在**端点自己的事件循环**上跑（不与并发的 ``tools/list`` 抢） | 修前：``Aggregator`` 里有全部工具、端点只发元工具 |
| ② | **声明能力** | ``declare_tools_list_changed``：在 initialize 里声明 ``capabilities.tools.listChanged``。⚠ 客户端 SDK **只在服务端声明了才挂**通知处理器（*"silently skipped"*） | 修前实测声明是 ``False`` |
| ③ | **服务端主动广播** | ``notify_tools_changed``：给**每个活连接**发 ``notifications/tools/list_changed``；活连接由**包 ``Connection`` 的两个公开工厂**登记（``for_loop`` / ``from_envelope``） | dsh 侧链路**现成**：``connection.ts:263-269`` → ``refreshTools`` → 两阶段换表 |

⚠ **顺序**：先改表 → 再广播（客户端收到通知会**立刻** ``tools/list``）。

**为什么必须包 SDK 的工厂**（方案 B 的代价，如实记）：MCP Python SDK 在 streamable-HTTP 这条路上
**没有**"连接建立/关闭"的公开回调（``ServerRequestContext.session`` 只在请求期可达、**每请求新建**；
``Connection`` 不挂在任何拿得到的地方；streamable 的 lifespan 是**管理器级一次**）。
⇒ 包 ``Connection.for_loop`` / ``from_envelope``（**都是公开类方法**）是"不重写传输层"的唯一办法。
⚠ **SDK 一改形状就失效** ⇒ 判据 ``checks/aggregate_tools_hot_sync_selfcheck.py`` 钉住
"包装在位 + 客户端真收到 + 经端点真调"；替换点写在 ``providers/mcp.py`` 那两个函数头上。

⚠ **通知是 best-effort**（SDK 原话）：没有独立 SSE 通道的连接天然收不到 ⇒ 我们**INFO 记一笔**，
不假装发了。

⚠ **顺带修掉的两条真 bug**（都是真机跑出来的）：
1. ``launch`` 里那个活表门面缺 ``execute`` ⇒ **连元工具都调不动**（``AttributeError``）；
2. ``sync_backends`` 用 ``attached()`` 判"要不要重挂"，而它**含墓碑** ⇒ **软件重启后工具回不到可用**
   （现象：进程 ready、工具全是墓碑）。⇒ 改用 ``states()``，并要有界重试 ``unreachable`` 的后端。

**"软件起来了 AI 就能用它的工具"**：``supervisor`` 的 ``ready``/``gone`` 钩子接到
``sync_backends``（不用再让人手动动一下滑块）。
