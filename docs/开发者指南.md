 # mecha 开发者指南

 mecha 是面向长期运行软件的操作者治理与能力投影层。它把软件状态、业务动作、事实记录、长任务、产物和监控连接成一套可由人、AI、CLI、GUI 和调度器共同使用的边界。mecha 不拥有项目领域模型，也不要求项目采用某个计算引擎。

 ## 1. 设计原则

 ### 状态归属

 长期状态属于软件本身。会话、AI 对话和 GUI 只是访问入口。软件重启后，配置、运行记录、任务事实和产物引用仍应能被查询。

 ### 动作单一来源

 人、AI、CLI 和 GUI 使用同一条命令执行路径。工具层只做参数投影和协议适配，不能重新实现领域动作。

 ### 事实优先

 History 和项目账本保存发生过什么；监控摘要、面板数据和缓存是派生读模型。派生模型可重建，原始事实不能被摘要替代。

 ### 权限先于副作用

 写权、审批、参数校验和操作理由在动作进入领域代码前完成。只读查询不应为了展示而获得写权。

 ### 框架提供机制，项目提供语义

 mecha 负责命令、查询、任务、产物、操作关联、作用域、写权和宿主投影。项目负责数据结构、参数含义、算法、业务校验、恢复策略和领域解释。

 ### 先消除错误空间

 优先用清晰的 API、不可混淆的身份、结构化回执和正确的生命周期减少错误，再对高风险路径增加必要的结果检查。文档、check 和门禁不应代替架构。

 ## 2. 核心对象

 | 对象 | 主要文件 | 作用 |
 |---|---|---|
 | Software | mecha/software_control.py | 把状态、Gate、History、命令、Jobs、产物和监控组装成运行实例 |
 | Authority | mecha/authority.py | 保存人类、AI、共享等写权模式 |
 | Gate | mecha/gate.py | 在状态写入前执行权限和领域校验，并记录归因 |
 | History/Event | mecha/history.py、operations.py | 追加事实、操作号、调用号、操作者和理由 |
 | Surface | mecha/surface.py | 注册和分派查询、类型、钩子等可组合能力 |
 | CommandRegistry | mecha/commands.py | 注册具名动作、参数、回执、作用域、估时和取消契约 |
 | JobRegistry | mecha/providers/jobs.py | 后台任务、进度、取消、终态和结果引用 |
 | ArtifactStore | mecha/artifacts.py | 托管大文本、文件、图表和二进制结果 |
 | ToolRegistry/ToolHost | mecha/tools.py、toolhost.py | 把项目能力投影到 AI、MCP 或本地宿主 |
 | Monitor/Cockpit | mecha/monitor.py、cockpit.py | 只读查看状态、事实、任务和派生摘要 |
 | Assembly | mecha/assembly.py | 装配上述对象并生成角色和服务清单 |

 框架级别没有 Engine。项目可以有自己的协调器，但它不是 mecha 的公共抽象。

 ## 3. 运行时关系

 ~~~text
 操作者
   -> ToolHost / CLI / GUI / Scheduler
   -> CommandRegistry 或 Surface 查询
   -> Authority / Scope / Gate
   -> 项目动作
   -> History + 项目账本 + Job + Artifact
   -> 结构化回执和监控投影
 ~~~

 查询直接读取软件和项目的只读事实。命令创建 operation 关联，带着 actor、reason、scope、call_id 进入执行路径。长任务把同步动作包装到 Jobs，但领域实现保持同一份。

 ## 4. 状态、事实和项目投影

 History 是追加事实流，不是所有项目状态的替代品。事件应包含：

 - seq：单调序号；
 - event_type：稳定的事实类别；
 - payload：可序列化的领域数据；
 - operation_id：一次命令或组合动作的关联；
 - call_id：宿主调用关联；
 - actor：操作者；
 - reason：动作意图；
 - created_at；
 - role：操作、业务变化或派生判断等角色。

 项目可以把更丰富的账本放在自己的数据库中，再通过 adapter 把操作号和事件类型关联起来。项目状态与账本需要在同一事务边界或等价的可靠协议内落地。

 fold 适合从明确的事件前缀重建派生状态，不适合成为任意业务事务的唯一实现。对于复杂项目，应由项目维护自己的物化表、版本和投影重建过程；mecha 只提供事实关联和通用记录机制。

 ## 5. 命令机制

 CommandSpec 描述：

 - name、summary；
 - 参数名、类型、必填性、默认值和说明；
 - writes_state；
 - side_effect；
 - risk；
 - 回执中的额外字段。

 CommandRegistry 负责：

 1. 根据声明规范化参数；
 2. 检查作用域和前置条件；
 3. 建立 operation；
 4. 调用项目处理函数；
 5. 统一错误包装和结果引用；
 6. 写命令审计事件；
 7. 返回稳定的结构化回执。

 命令处理函数应保持领域语义清晰。它可以调用项目服务、事务账本和 Jobs，但不应直接解析 MCP 请求或 GUI 参数。

 命令命名使用项目词汇。mecha 不定义 set_config、run_sim 等通用业务名，也不要求所有项目暴露 run。

 ## 6. 查询机制

 Surface.QUERY 适合：

 - 当前配置和只读状态；
 - 能力描述；
 - 运行、任务、产物和账本摘要；
 - 领域对象的分页读取；
 - 监控所需的派生数据。

 查询回执应包含身份、状态、分页事实和字段说明。大结果通过 ArtifactStore 或项目结果引用返回。查询不应产生隐式写入、隐式提交任务或改变当前配置。

 ## 7. Jobs 和 ExecutionContext

 长任务使用 JobRegistry.submit。ExecutionContext 提供：

 - job_id；
 - cancel_requested；
 - progress(name, value, extra)；
 - 任务日志上下文；
 - 结果引用和终态协作。

 项目决定并发上限、资源预算、检查点和恢复语义。mecha 负责任务状态、通用取消请求、等待、终态和工具投影。

 任务必须区分：

 - queued：项目资源队列中；
 - running：任务线程或进程正在执行；
 - done：领域动作完成；
 - failed：任务异常或领域失败；
 - cancelled：协作式取消完成。

 等待超时是调用方的等待边界，不是任务失败。取消请求也不等于已经终止。

 ## 8. 产物机制

 ArtifactStore 用非透明引用管理长文本、文件、图表、模型、数据数组和日志。回执只返回：

 - artifact_id 或 result_ref；
 - kind；
 - size、mime、shape 等元数据；
 - 可选摘要；
 - 读取方式。

 项目可以保留自己的结果目录，但应通过统一引用让 AI 和监控面获得一致的定位。禁止把大数组、完整日志或二进制直接塞进操作回执。

 ## 9. 作用域、写权和审批

 ScopePolicy 把能力划分到读、写、运行、管理等范围。Authority 表示当前操作者模式；Gate 决定具体写入是否允许。

 常见边界：

 - 查询只需要读作用域；
 - 配置写入需要项目写作用域；
 - 删除、撤回、取消和外部副作用需要更高作用域；
 - 审批 provider 可在命令前要求明确确认；
 - fail-closed provider 在无法判断时拒绝写入。

 项目不要在工具闭包里自行维护第二套权限布尔值。所有写入都通过 Gate 或项目明确绑定的写入入口。

 ## 10. 宿主投影

 ToolRegistry 保存结构化工具定义。ToolHost 可以把它投影到：

 - 本地进程内调用；
 - MCP streamable HTTP；
 - CodeAct 或动作解释器；
 - GUI/面板的动作目录；
 - CLI 和脚本。

 工具描述应面向任务，包含参数、结果和失败建议。投影层可以分页、pick、summary，但不能改变命令语义。

 ## 11. 装配顺序

 典型 assembly 顺序：

 1. 解析项目根、数据根和身份；
 2. 创建 History、ArtifactStore、Authority 和 Gate；
 3. 创建 Surface 和 CommandRegistry；
 4. 注册项目查询；
 5. 注册项目命令和作用域；
 6. 创建 JobRegistry 并绑定结果落点；
 7. 注册工具和宿主 provider；
 8. 创建 Monitor、Cockpit 和站点声明；
 9. 返回 Software 实例和 disposer；
 10. 关闭时逆序释放任务、HTTP、文件和数据库资源。

 装配函数应可在测试中单独调用，不把 GUI、网络服务器和训练线程作为导入副作用。

 ## 12. 项目接入约束

 接入项目至少要提供：

 - 一个稳定的项目根和数据根；
 - 项目状态对象或数据库；
 - 查询注册函数；
 - 命令声明与执行函数；
 - 领域校验；
 - 长任务策略；
 - 大结果引用策略；
 - 面向宿主的能力说明；
 - 关闭和恢复路径。

 项目可以只接入查询，也可以只使用命令和 Jobs。没有长期状态的纯函数不需要完整装配。

 ## 13. 测试重点

 测试应按真实风险选择：

 - Surface 查询是否可发现、可序列化、无副作用；
 - CommandSpec 与真实写入是否一致；
 - 写权、作用域和审批是否在副作用前生效；
 - operation_id、call_id、actor 和 reason 是否贯通；
 - Jobs 的终态、等待、超时、取消和队列事实是否准确；
 - ArtifactStore 引用是否可读且不会泄漏大结果；
 - ToolHost 与 MCP 投影是否保持参数和回执一致；
 - 关闭和重复装配是否释放资源；
 - 项目账本和 History 是否能按 operation 关联。

 只为实际风险保留验证。文档格式、重复注册、可由类型系统保证的低价值问题不应继续扩大门禁。

 ## 14. 修改决策

 改动落点按以下规则判断：

 - 通用治理、操作关联、Jobs、产物和宿主投影：mecha；
 - 数据、算法、状态机、物理量和业务规则：项目；
 - 只在一个项目成立的运行协调器：项目内部；
 - 至少两个项目真实共享且语义一致的机制：考虑提取；
 - 仅为某个历史问题增加的检查：先问能否用边界或对象设计消除错误空间。

 接手代码时先从 assembly 反向追踪对象，再从命令和查询追踪领域服务，最后阅读面板和协议层。
