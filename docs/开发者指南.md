# mecha 开发者指南

mecha 让 AI 深度接入自行维护状态、执行任务的软件。人借助 AI 操作软件，项目负责领域状态与执行，框架提供可复用的协作基础。长期设计取舍见[设计愿景](设计愿景.md)；本文说明当前实现，接入示例见[接入指南](接入指南.md)。

## 1. 核心对象与职责

| 对象 | 主要文件 | 当前职责 |
|---|---|---|
| Software / assemble | `mecha/assembly.py` | 创建默认运行对象，持有公共入口 |
| SoftwareControl | `mecha/software_control.py` | 跨进程访问软件控制面；不是 Software 装配对象 |
| Authority | `mecha/authority.py` | HUMAN、AI、OPEN、LOCKED 写权模式 |
| Gate | `mecha/gate.py` | 写权检查、默认键值状态校验与写入、审计记录入口 |
| History / Event | `mecha/history.py` | 追加状态及历史事件，通过 LogSink 持久化 |
| operation | `mecha/operations.py` | 当前执行上下文中的操作身份与归因 |
| Surface | `mecha/surface.py` | 注册 query、hook、custom_type；持有命令注册表 |
| CommandRegistry | `mecha/commands.py` | 声明与执行命令，检查策略、参数键和回执键，记录审计 |
| JobRegistry | `mecha/providers/jobs.py` | 本地线程任务、进度、取消请求、等待和结果引用 |
| ArtifactStore | `mecha/artifacts.py` | 按不透明 locator 存取字节与元数据 |
| ToolRegistry / ToolHost | `mecha/tools.py`、`mecha/toolhost.py` | 工具定义、调用与传输接入 |
| Monitor / Cockpit | `mecha/monitor.py`、`mecha/cockpit.py` | 摘要与原始状态对照、只读 HTTP 投影 |
| Site / Aggregate | `mecha/site.py`、`mecha/aggregate.py` | 项目声明、后端发现、工具聚合 |

框架没有要求项目实现的通用 Engine。领域组件、自动化、毫秒级控制、资源调度和恢复策略属于项目。

## 2. 默认装配与生命周期

`assemble()` 要求 `root`、`data_dir_name`、`summarizer` 和 `validate`，可指定项目名、mode、审批决策器、迁移链和 `log_sink`。默认使用 JSONL History、本地线程 Jobs、本地文件 Artifacts 和本地 ToolHost；`software.commands` 与 `software.surface.commands` 是同一对象。

默认写权为 LOCKED。项目可显式选择 OPEN 等模式，不必为了共享使用而人为轮换人机写权。审批、写权和领域校验是不同职责。

目前 `log_sink` 可从装配函数注入，Jobs、Artifacts 等默认实现仍在装配函数内创建。`Software.close()` 只关闭 History；任务、设备、HTTP 服务等资源的生命周期仍由接入方管理。不要把完整的可替换 provider 装配和统一资源释放写成已经完成的功能。

## 3. 命令执行边界

`CommandSpec` 使用 `name`、`description`、`parameters`、`output_schema`、`side_effect`，另有 `scope`、`estimate_sec`、`cancel_supported`、`approval_required`、`wants_channel`。没有 `summary`、`writes_state` 或 `risk` 构造参数。

`invoke()` 在进入处理函数前检查通道、必要的 Gate、已绑定的作用域策略、写权、审批和参数键。省略通道时统一使用 AI 侧通道，不能绕过写权检查。`wants_channel=True` 时，处理函数收到的也是这条通道。

参数检查覆盖必填键与未声明键，回执检查覆盖必填键；不自动完成整个 JSON Schema 的类型、范围校验，也不自动补齐所有声明默认值。领域校验由项目实现。

处理函数接收 `context=` 和业务命名参数，返回映射或 CommandResult。成功回执为 `{is_error: false, value: ...}`，领域失败为 `{is_error: true, error: {message, info}}`，部分失败还带已有的 value。普通编程异常通常继续上抛，由传输边界处理；当前处理函数中的 TypeError 会被归一化为参数错误。

有副作用的命令在处理函数返回或异常后写 `command.<name>` 历史事件。它不进入配置快照，也不经过配置 validator。执行前被拒的调用不写这条审计。审计失败不能撤销已经发生的外部动作，当前也没有覆盖进程骤停的完整开始/结束记录协议。

## 4. 状态、账本与关联

Event 的实际记录字段为：

- `seq`、`kind`、`op`、`target`；
- `after`、`before`；
- `actor`、`reason`、`call_id`、`ts`；
- `undoable`、`operation_id`、`role`。

`kind` 区分 `state` 与 `history`。默认 fold 只将 state 事件折叠为键值状态；命令审计等 history 事件不改变这个快照。`undoable=None` 表示未声明，不等于不可撤销。

History 可以直接注入自定义 fold，但 `assemble()` 尚未透传该选项，Monitor 目前仍使用默认 fold。已有领域数据库不必依赖这份键值快照；项目负责自己的状态、事务和物化读模型。

operation 使用上下文变量，嵌套调用复用当前操作身份，不自动建立子步骤树。后台线程不会自动继承它。项目应显式将操作号传入需要关联的执行和账本路径。调用回执也不会自动附带所有框架关联字段。

跨设备动作与本地记账不能天然原子提交。需要根据项目实际能力表达请求、设备确认和测量结果，不能将超时或缺少记录解释成“没有发生”。

## 5. Jobs 与 Artifacts 的当前边界

`JobRegistry.submit(fn, command=..., cancel_supported=..., result_ref_fn=...)` 每次创建一个 daemon 线程。状态为 pending、running、done、failed、cancelled；pending 不是资源队列承诺。任务记录和 ID 属于当前注册表实例，不提供跨进程重启恢复。

ExecutionContext 提供 `cancelled`、`request_cancel()`、`report_progress(frac, stage)` 和 `progress()`。Job 持有 ID、时间、结果及结果引用。没有通用的日志尾接口。

当前终态判定有明确限制：函数抛异常才归为 failed，普通返回值中的业务失败不会自动被识别；收到取消请求后正常返回也可能归为 cancelled，不能据此证明实际工作被中断。失败或取消路径不会统一提取部分结果引用。项目需要补充领域事实，不能只凭任务标签判断设备状态。

`ArtifactStore.put(bytes, kind=..., name=...)` 返回 locator；`retrieve()`、`describe()`、`exists()` 用于读取。默认实现将文件与元数据落盘，但 locator 映射在内存中，重新创建 store 后不能直接解析之前的 locator。需要长期可发现结果的项目应保留持久索引。

## 6. 监控与领域界面

Monitor 对照项目 summarizer 和默认 fold 得到的原始状态；摘要故障可降级显示。Cockpit 通过 MonitorSource 获取事件、快照、写权模式和项目提供的 schema/status 信息。

`/history` 原样保留 Event 记录，包括 before、kind、operation_id、role 和 undoable；不按 target 重建前像。`/activity` 使用轻量字段，仍保留事件类型、动作和操作关联。HTTP 响应按 seq 升序，筛选 since_seq 后最多取最近 100 条。

兼容提醒：这两条接口曾将 kind 固定输出为 `set`，现在使用账本的 `state` / `history`；需要判断设置动作的消费者应读 `op == "set"`。旧记录没有保存的 before 保持 None，不推测补值。

项目页面可以读取这些关联字段，但框架尚未自动将操作、所有后台任务、产物和领域页面组织成一个完整视图。基础观察与领域可视化应共享事实，专业解释仍由项目负责。

## 7. 工具与连接恢复

工具定义与协议接入分开。`projection.project()` 投影命令声明，并要求提供 execute 回调；查询和命令不会仅因注册而自动成为宿主工具。MCP、dsh 与 Codex 接线复用后端能力，宿主差异在适配层处理。

BackendConnectError 当前涵盖连接建立失败和调用中途断线，无法证明请求尚未发送。因此聚合层会尝试 resync 恢复后端发现，但不重放原调用，并返回 `backend_outcome_unknown`。这也意味着当前只读调用在该路径上不会自动重试；需调用方明确发起新请求。

超时保持 `backend_timeout`，也不表示远端动作失败。后端恢复可用只证明连通性恢复，原操作结果需要查询任务、记录或实际状态。以后若增加自动重试，需要可验证的发送阶段、幂等声明或去重能力。

## 8. 修改与验证

优先修复真实行为和既有承诺之间的差异。新的公共抽象应来自实际项目的共同需要；不要为接入再复制业务执行器或领域数据库。

本轮操作边界回归集中在 `checks/operation_boundary_selfcheck.py`，覆盖漏传上下文、忠实事件投影和回执丢失后不重复执行。相关既有检查是 phase6 命令面、phase11 监控 HTTP 和 aggregate 聚合检查。HTTP 与 Windows asyncio 检查需要允许本地回环套接字。

`docs/history/` 保存历史设计与决策，不作为现行 API 使用说明。修改公开接口时同步维护本指南、接入示例及相关行为检查；设计愿景保持目标层次，不混入当前缺口清单。
