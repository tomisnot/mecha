 # mecha 接入指南

 本指南用于把一个已有软件接入 mecha，让人、AI、CLI、GUI 和调度器共享同一套能力、写权、任务、产物和事实边界。接入时保留项目自己的领域模型，mecha 只承接通用机制。

 ## 1. 先判断是否适合接入

 适合接入的项目通常具备：

 - 持久配置、运行记录或长期业务状态；
 - 多种操作者；
 - 可拆分的只读查询和有副作用的动作；
 - 需要后台任务、结果文件或监控；
 - 希望 AI 与人工使用同一条业务路径。

 一次性纯函数可以只使用 ToolRegistry，不需要完整软件装配。

 ## 2. 建立项目边界

 准备三个概念：

 1. project root：代码、配置和身份；
 2. data root：运行、账本和产物；
 3. software state：项目自己的当前状态或数据库。

 不要把状态放在 AI 会话变量或工具闭包中。显示名可以变化，内部身份必须稳定。

 ## 3. 最小装配

 ~~~python
 from pathlib import Path
 from mecha.assembly import assemble

 software = assemble(
     root=Path("."),
     data_dir_name=".mecha",
     project="my-project",
     summarizer=lambda events: summarize_project(events),
     validate=validate_project_write,
 )
 ~~~

 项目应提供真实 validate 函数，并在进程关闭时调用 software.close。装配不应因为导入 GUI 或训练模块而启动后台资源。

 ## 4. 注册查询

 查询适合配置、状态、能力、运行和监控：

 ~~~python
 software.surface.register_query(
     "describe_state",
     describe_state,
     summary="读取当前项目状态",
 )
 ~~~

 查询函数接收规范化参数，返回 JSON 可序列化对象。列表应支持 limit、offset 或 cursor，并明确 total、next_cursor 和是否截断。

 查询不要：

 - 修改当前状态；
 - 自动创建运行；
 - 自动写操作理由；
 - 把大文件内联返回；
 - 暴露数据库连接和线程对象。

 ## 5. 注册命令

 每个副作用动作由 CommandSpec 声明，再绑定执行函数。声明至少写清名称、参数、作用和回执。项目命令可以增加 side_effect、writes_state、risk 和 scope 元数据。

 处理函数的推荐结构：

 ~~~text
 规范化参数
   -> 领域校验
   -> 项目事务/服务
   -> 写业务事实
   -> 写结果引用
   -> 返回小回执
 ~~~

 命令实现不要从 request、MCP 或 GUI 读取参数；所有入口都应把输入转换为同一个命令参数对象。

 ## 6. 写权和作用域

 为每类动作定义作用域，例如 read、write、run、admin。命令注册时声明需要的作用域，写入统一通过 Gate。

 领域校验负责“值在业务上是否有意义”，Gate 负责“当前操作者是否能进行这次写入”。两者不要重复实现相同规则。

 ## 7. 操作关联

 命令执行期间使用 operation_id、call_id、actor 和 reason。领域账本的事件应保存 operation_id，便于从监控回到业务事实。

 reason 是动作意图说明，不是强制写一篇文档。对 AI 和人工都提供合理默认值，只有在删除、外部发送等高风险场景才要求明确理由。

 ## 8. 长任务

 长任务使用 software.jobs.submit：

 ~~~python
 def work(ctx):
     for item in items:
         if ctx.cancel_requested:
             return {"status": "cancelled"}
         ctx.progress("item", current, {"total": len(items)})
         process(item)
     return {"status": "completed"}

 job = software.jobs.submit(work, title="build-index")
 ~~~

 项目负责：

 - 并发上限；
 - 资源预算；
 - 检查点和恢复；
 - 业务失败与成功判定；
 - 结果落点。

 mecha 负责任务状态、取消请求、等待接口和基础回执。取消应在循环、批次或安全点检查，不要假定线程可以强杀。

 ## 9. 产物

 长文本、文件、图表、数据数组和模型都交给 ArtifactStore 或项目结果存储。回执给引用：

 ~~~json
 {"ok":true,"result_ref":{"kind":"file","id":"artifact_...","size":1234}}
 ~~~

 引用必须能在后续查询中读取，且带类型、大小或形状。不要让每个工具定义自己的下载协议。

 ## 10. AI 工具投影

 先注册查询和命令，再用 ToolRegistry 投影。工具说明写：

 - 什么时候使用；
 - 参数含义和约束；
 - 返回的身份和状态；
 - 失败时下一步怎么查；
 - 大结果如何读取。

 read 工具可以提供 pick、limit、summary 和 compare。写工具不能通过这些参数绕过 Gate 或改变命令语义。

 ## 11. 组合动作

 组合动作可以调用多个查询或命令，但每一步都应有稳定名称、结构化结果和错误边界。若组合动作包含写入：

 - 明确哪些步骤已完成；
 - 为每步保留 operation 或子结果引用；
 - 中途失败时返回可继续的状态；
 - 不要假装有跨项目事务，除非项目真的提供补偿或事务协议。

 ## 12. 监控和站点

 监控只读。项目提供事件摘要和当前状态，mecha 负责统一展示 operation、actor、reason、job 和 artifact。站点声明描述服务、端口和能力，不应把业务执行重新写在页面路由中。

 ## 13. 接入验收

 至少验证：

 - 软件可重复装配和关闭；
 - 查询在没有 AI 的情况下可调用；
 - 命令参数和回执可序列化；
 - 未授权写入在领域动作前被拒绝；
 - operation_id 能关联项目账本；
 - 长任务能报告进度、取消和终态；
 - 产物引用可读取；
 - MCP/本地 ToolHost 与直接命令结果一致；
 - 失败回执包含明确的 kind、hint 或 suggest。

 ## 14. 常见误区

 - 为 GUI、CLI 和 AI 各写一套业务实现；
 - 用当前会话变量代替软件状态；
 - 把所有动作都命名为 run；
 - 用 Engine 作为框架接入条件；
 - 将完整日志和数组放进 AI 回执；
 - 把查询做成隐式写操作；
 - 用大量结构 check 补偿不清晰的对象边界；
 - 把项目特有语义硬塞进 mecha 核心。

 接入完成后，项目的开发者文档应说明自己的领域结构、命令和查询；mecha 文档只需要描述接入边界和通用服务。
