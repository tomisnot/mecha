# mecha v2 规范框架修订提案：基于 DSH 0.1.7-rc.1 与 Energy Level 再审视

> 状态：**proposal / 复审结论**，不是当前 ADR，不直接覆盖 `docs/v2/架构总纲.md`。
> 证据基线：DSH `dsh-v0.1.7-rc.1`、HEAD `46a7f68b0922371ce7144b668b90e377d8e799f4`；Energy Level 当前源码；mecha `master` HEAD `6a6d2cf7ca6da6e17417081f4c640ba091b6e801`。
> 外部深研：[DSH 深研](外部实践研究/DSH-0.1.7-rc.1深研.md)、[Energy Level 深研](外部实践研究/Energy-Level-深研.md)。

## 1. 复审结论

mecha 当前方向正确，但成熟度必须重新表述：

> **mecha 的目标应正式定位为“AI 接入项目规范框架”；当前实现是“规范草案 + 可运行参考原型”，还不是可由多个项目一致实现并通过 conformance 判定的成熟规范框架。**

已经成立的价值：唯一 Gate、StateHistory、能力三角色、可逆注册、具名装配、call_id 互引、真实 MCP、EL 首个 Provider 和较严格的真实组合判据。

尚未达到规范框架的原因：

1. 规范核心仍是 Gate/History/Surface/Monitor 四件与工具形状，没有形成统一的状态、执行、查询、产物、监控五边界。
2. `assemble()` 没有装配唯一完整 capability graph；生产路径会再创建 Surface/ToolRegistry/roles 状态。
   **（实测证据与状态：审查《边界机制三件交付落地》§2.1 缺口 B 量出"声明 19 条 vs
   运行时 3 条"，根因 = `bridge.serve_mcp → _build_gui_tools` 裸建 `Surface(engine)`
   丢弃装配点带角色的那份——与本条断言同一件事的两种说法。已修：ADR
   `边界机制补三洞-运行时图与声明表一致`（1a surface 穿线 + 1b 运行时图⊇声明表守卫 +
   完整性守卫 + EL 真表并表），capability_map_selfcheck 钉成永不再犯。）**
3. 工具是 capability 的第二实现，部分查询直接调用 Engine，声明与执行可能漂移。
4. GUI 与 AI 存在两套物理执行器，违反“每种副作用一个 executor”。
5. 生命周期没有统一 quiescent close；watcher、executor、Job、MCP/HTTP server、lease 各自管理。
6. Gate/History 没有库内线程安全和持久化事务，sink 失败会内存/磁盘分叉。
7. 没有正式 Artifact、OperationLog、Query descriptor、runtime generation/scope。
8. 没有规范条款矩阵与分级 conformance suite；现有门禁不能证明多项目一致符合。

## 2. 正式定位建议

建议将项目对外定位写成：

> **mecha 是 AI 接入项目的规范框架与最小运行时参考实现。它规定项目如何把领域能力、状态、执行、查询、产物与证据接入 AI 和其他操作者，并要求适配器、生命周期、错误、权限、并发、迁移与真实装配可验证。**

框架不是 AgentPlatform、模型 SDK 或聊天 UI；它提供的是：

- 规范条款（Normative Clauses）；
- 最小运行时端口（Runtime Port）；
- Conformance Suite；
- Reference Adapter；
- Reference Project 证据。

## 3. 规范条款 N1–N12

### N1 能力三角色与唯一能力图

- 每项能力必须同时声明 Definition、Provider、Consumer；单角色不是 seam。
- runtime 维护唯一 CapabilityRegistry。
- tool schema、MCP list_tools、scope visibility、skill catalog、capability map 都从同一注册项生成。
- RuntimeManifest 至少记录 capability id、provider identity、consumer、raw/public id、version/generation、lifecycle owner。

### N2 显式 request/spec 与一次执行多投影

- `resolve(request, context) -> immutable spec` 负责默认值、上限、配置与敏感信息清洗。
- `execute(spec, control) -> outcome/handle` 是副作用唯一 executor。
- 同步、QThread、local job、sweep、MCP 只改变等待和投影方式，不重写领域分派。

### N3 CallContext 是一等规范值

至少携带：opaque call_id、actor/side、provider raw id、public capability id、scope、request fingerprint、generation、deadline/cancel handle、adapter metadata。

### N4 工具是 capability 的受限投影

- tool execute 只能调用已注册 capability，禁止复制业务实现。
- Provider raw response 是内部规范值；canonical snapshot → output schema validate → pure render/meta → deep freeze。
- 模型只看 public projection。
- 任意 throw 归一为稳定 ErrorCode；模型文案与机读 code 分离。

### N5 可逆注册、scope 与 generation

- register/effect/restrict/unregister 返回精确 disposer。
- scope 销毁后 capability 立即不可见、不可 dispatch。
- capability 更新按 generation 整代构建和验证，再原子 swap；失败保旧代；迟到响应不得覆盖新 generation。

### N6 生命周期必须 quiescent

统一 `Runtime.close()`：

1. 停止接收新请求；
2. 撤销 generation/visibility；
3. cancel/abort 在途工作；
4. 等待 engine/job/server/stream/child settle；
5. flush/close sink/artifact；
6. 释放 lease/port/token；
7. 保证 close 幂等、无迟到副作用。

### N7 单一状态真值与事务

- 所有改变未来领域结果的持久状态经 State Gate。
- Gate 自身提供锁和事务，adapter 不持有“局部真源锁”。
- batch 与 durable journal 必须全成或全败。
- mode、view state、query profile、execution control、artifact bytes 不进入 StateHistory。

### N8 执行与查询是不同端口

- Execution：resolve → execute，产生 operation lifecycle。
- Query：QuerySpec + QueryDescriptor，声明 cost、thread affinity、sync/async、spillable/artifact、cache policy、estimated cost。
- 便宜 query 同步；重 query 必须显式 async/handle，不得阻塞 MCP/GUI 事件循环。

### N9 Artifact 是一等边界

ArtifactStore 提供 put/get/head/list 和 opaque handle。Manifest 至少含 artifact_id、config fingerprint、provider/tool version、operation_id/call_id、format version、labels、array keys/shapes/dtypes、warnings、status、checksum、created_by。

Spill 只是大文本旁路，不等于 Artifact。

### N10 OperationLog 与 Monitor evidence

- StateHistory 只记录持久领域状态。
- OperationLog 记录 execution/query/artifact 生命周期：PENDING/RUNNING/DONE/FAILED/CANCEL_REQUESTED/CANCELLED、progress、warnings、error、artifact refs、generation。
- Monitor 聚合 StateHistory、OperationLog、ArtifactManifest、Authority/ConnectionStatus 和 warnings。
- Claim 必须携带 EvidenceRef，可回到原始证据；冲突时原始证据胜出。

### N11 发布格式与迁移保源字节

- released artifact 不覆盖、不删除、不重命名；
- 使用相邻版本、有状态 migration；
- 转换、保留、拒绝都要证明源字节/hash 不变；
- 坏数据不能静默跳过而无证据。

### N12 规范必须可验收

建立矩阵：

`Requirement ID → Rationale → DSH Source/Symbol → mecha Clause → Acceptance Test → Evidence`

最低证据：真实 composition、并发/故障注入、取消与 quiescence、generation rollback、scope visibility、真 MCP required/缺参、真实 DSH 连接、EL 活体。

## 4. 五边界目标模型

### 4.1 State

职责：领域 schema/validator、唯一可写状态、事务、StateHistory、config fingerprint。

建议端口：`describe_state()`、`validate(patch)`、`apply(CallContext, StatePatch) -> StateReceipt`、`snapshot/read`。

不含：mode、UI 控件态、query profile、execution control、artifact bytes。

### 4.2 Execution

职责：build/resolve immutable spec、check/warnings、唯一领域 dispatch、progress/cancel、Operation lifecycle、artifact refs。

建议端口：`resolve(ExecutionRequest) -> ExecutionSpec`、`execute(ExecutionSpec, ExecutionControl) -> ExecutionOutcome`、OperationHandle。

### 4.3 Query

职责：只读计算、注册元数据、cost/affinity；不写 StateHistory，可产生 Operation/Artifact refs。

首批 EL：list_levels、estimate、preview、get_waves、spectrum、AC sweep、pair eigen/map。

### 4.4 Artifact

职责：二进制/大结果持久化、manifest、安全读取、retention、version、checksum、provenance。

LocalArtifactStore 可使用 trusted npz/pickle；pickle 不越过信任边界。

### 4.5 Monitor

职责：只读聚合 StateHistory、OperationLog、ArtifactManifest、Authority/ConnectionStatus、Warnings；派生 Claim 携带 EvidenceRef。

Authority、CallContext、Capability/Scope、Errors、MCP/DSH adapters、FormatMigration、Lifecycle 是横切面，不是第六业务边界。

## 6. EL 暴露的框架级缺口

### P0

1. 生产装配不唯一。
2. 状态并发和持久化事务缺失。
3. GUI/AI 执行双轨。
4. 无正式 Artifact，人机不共有同一结果证据。
5. 无 OperationLog，Monitor 不能回答“AI 做了什么、结果在哪里”。
6. 无统一 quiescent lifecycle。
7. MCP required/缺参、并发 client、真实 DSH 连接证据不足。

### P1

8. Query descriptor/affinity 缺失，static/spectrum/AC/pair/sweep 未进入统一操作者面。
9. Authority 不协调 in-flight execution。
10. Spill/Artifact、Job/Sweep、State/Query 类型混淆。
11. Tool runtime validation、raw/public identity、generation 不完整。
12. Visibility 与真实注册链断开。
13. State History 与 operation/artifact 状态边界不清。

## 7. 迁移路线

### M0 规范冻结与 characterization

- 写 N1–N12、五边界词汇表和兼容策略。
- 建 Requirement→DSH source→mecha clause→test 矩阵。
- 记录当前 Runtime identity graph 和 EL 能力全集。
- 为现有行为补 characterization test。

### M1 修地基

- Gate/History 锁与事务；
- sink fault injection；
- 精确 disposer/generation；
- watcher/MCP/Qt/lifecycle 基础修复；
- close 基础设施。

### M2 CallContext + RuntimeManifest + CapabilityRegistry

现有 Gate/History/Tool/Surface 注册接唯一 registry，保留兼容 adapter。

验收：生产只有一套核心实例；list_tools/visibility/roles/map 同源；迟到 generation 不覆盖。

### M3 State 边界定型

引入 StatePatch/StateReceipt/StateProvider；EL GUI 非标量立即过 Gate；bootstrap seed 受控。

### M4 Execution 边界统一

引入 resolve/execute/OperationHandle；ElEngine 迁移；删除 ElOps 物理 executor；同步/QThread/job 只是 host。

### M5 Query 与 EL 操作者面补齐

引入 QueryDescriptor；补 static spectrum/AC/pair/eigen/map/sweep；重 query 显式异步。

### M6 Artifact 正式化

ArtifactManifest/Handle/Store；EL run/sweep/static 统一落产物；Spill 分离。

### M7 OperationLog + Monitor aggregator

状态史与 operation 史分立；Monitor 汇聚多类 evidence。

### M8 MCP/DSH adapter 升级

真 input/output validation、raw/public id、server reservation、generation swap、connection supervisor、quiescent close。

### M9 Conformance 分级与兼容层淘汰

- Level 1 Core Composition
- Level 2 Transactional/Lifecycle
- Level 3 Adapter Protocol
- Level 4 Reference Project

通过后删除旧 Engine/Summary/Visibility/第二装配兼容层，bump 版本并保留迁移。

## 8. Conformance 证据包

### E1 规范矩阵

每个条款有 Requirement ID、规范文字、Rationale、DSH source、mecha port、acceptance test、证据命令/文件。

### E2 真实装配

从唯一 production entry 导出 RuntimeManifest；断言全进程只有一套 Gate/StateHistory/ExecutionPlane/QueryRegistry/ArtifactStore/OperationLog/ToolProjection/JobHost。

### E3 并发与故障注入

多线程 set/batch/load；seq 单调；snapshot=journal；sink 各阶段故障全成或全败；取消后无新副作用；迟到响应不覆盖新 generation。

### E4 生命周期

close 前后 active request=0、operation settled、线程 join、server/child/network closed、lease released、port/token removed；重复 close 幂等。

### E5 真协议与 DSH

MCP 缺参/unknown tool/任意异常/output 违规/并发 client/raw-public identity/restart-reconnect；真 DSH 模型仅看 schema/description 首次完成工作流。

### E6 EL 活体与数值证据

GUI/AI 同 spec 数值对拍；状态即时互见；static/run/sweep/artifact 同证据；Monitor Claim 可追 EvidenceRef；Qt 线程 ID 可证。

### E7 迁移证据

released artifact 源字节 hash 不变；转换/保留/拒绝各有 corpus 和原因。

## 9. 需要委托方裁决的事项

1. **Authority 接管策略**：人在 AI job 运行中夺权时，继续、drain、暂停还是 cancel？
2. **Artifact 默认格式**：trusted-local NPZ/Zarr/HDF5，还是允许 pickle 但严格标本地可信？
3. **兼容期长度**：旧 Engine/Surface API 是否需要迁移窗口，还是直接按 0.3.0 破坏性升级？
4. **Query 阻塞策略**：重 query 默认必须异步，还是允许宿主显式声明同步阻塞？
5. **Conformance 强制程度**：首个 EL 项目必须达到哪一级，还是先发布 Level 1？
6. **规范治理**：DSH 风格 Agent Note 是否替代现有四态 ADR，或保持 ADR 并增加 clause/evidence 字段。

## 10. 接管决策建议

- 保留愿景，不保留假完成：正式宣布目标是规范框架，但当前成熟度是草案+原型。
- 把四件升级为五边界；Authority/工具/Scope/DSH adapter 作为横切面。
- 当前最高优先级不是继续加工具名，而是：唯一装配、状态事务、统一执行、OperationLog、Artifact、quiescent lifecycle、真实 composition evidence。
- 任何 P0 没有独立可观察证据前，不宣称“AI 接入项目规范框架已建成”。
